## 1. Scope and ownership

Deliver **Persistent**, rollout position **6 of 12**, inside the shared Week frame. Players resolve carried persistent events in rules order, see the buyoff cadence and each event's projected result, enter checks or a reasoned table ending, and understand when Activity or Event has already ended an event. This is an implementation issue produced by [Write the Persistent implementation spec](https://github.com/AndreasUnunger/EverythingPath/issues/128), outside the authoring map; it does not authorize merging a prototype.

[Week frame](https://github.com/AndreasUnunger/EverythingPath/issues/137) owns Phase View navigation, fixed Persistent Phase Eligibility, all-phase Phase Readiness, This phase, reference values, shared save/recovery feedback and the next-week transition. This issue supplies Persistent's facts and editor. [Upkeep](https://github.com/AndreasUnunger/EverythingPath/issues/140) owns the shared dice-total contract and compatibility; consume it without introducing another format. [Activity](https://github.com/AndreasUnunger/EverythingPath/issues/142) owns Reduce Danger and its Action Slot. [Event](https://github.com/AndreasUnunger/EverythingPath/issues/143) owns same-week occurrences, their nested persistent inputs and High Morale. Persistent and Event share the one-event-per-week Overseer allocation.

[Review & confirm authoring](https://github.com/AndreasUnunger/EverythingPath/issues/129) owns the subsequent Summary, Table Adjustments and Confirmation redesign. Continue to support the current Summary and Confirmation until that issue ships. [Militia corrections](https://github.com/AndreasUnunger/EverythingPath/issues/139) owns source correction/reference-repair recovery; [Characters & officers](https://github.com/AndreasUnunger/EverythingPath/issues/141) owns the later kind/role/Hit Dice migration and must update this consumer. Their current editors remain reachable throughout. No new schema, query/mutation argument, result shape or Weekly Resolution rule change is approved in this issue.

### Main-column behavior

1. Lead with one wrapping buyoff overview: first buyoff availability, current projected cost, four-week cadence, and **Next buyoff week N** including accepted staged buyoffs. Derive these from the same Resolution Preview as Confirmation, including rank changes and earlier expenditure. Show an honest pending value when earlier preparation prevents calculation; never substitute a mock cost or assume the starting treasury/rank is the final value.
2. Render one numbered section per **week-start carried event**, ordered by `startedWeek`, then stored `order`, then stable `eventId` as the existing tie-breaker. Show name, started week, weeks elapsed, recorded within-week order and named targets (Militia if untargeted). Retain distinct instances with the same type/name. Do not let decision array order, a sort by label or remote edits reorder the sections.
3. Each section header has a concise projected result: e.g. **Ends · buyoff 160 gp**, **Stays · keeps 90% of this week's gains**, **Stays · officer check pending**, or **Buyoff needs a Rules Exception**. The section number becomes a check only when the preview actually stages an ending. These are forecasts until Confirmation; a selected card or entered reason alone is not proof an event ends.
4. Offer playing-card choices **Leave it**, **Loyalty check (this week only)** for Theft / **Officer check to end it** for Rivalry, **Buy off · <cost>**, and **Ended at the table**. Types without a supported check, including Low Morale and Double Agent, have no invented check card. Cards have concise rules notes and a visible selected state, support tap and keyboard, and allow scrolling that starts over them. No drag is necessary for this approved choice-card layout.
5. Put the selected decision's fields below its cards, followed by its results, warnings and Rules Exceptions. Keep relevant field-level errors within their field containers. Put missing-decision summaries and **Earlier phases still need preparation** in the frame's This phase/stepper/footer surfaces as well; no separate competing readiness system.
6. An event already ended by a resolved Activity/Event consequence remains in its original section and shows the source and a working change link, e.g. **Ends this week · staged by Reduce Danger in Activity slot 2. Change it in Activity.** It offers no redundant Persistent decision. Use actual source identity and outcome, not the mere presence of a Reduce Danger card or a High Morale roll. An incomplete, unsuccessful, negated or unselected source cannot hide an outstanding decision. A Table Adjustment applied after the Rules Baseline is not an earlier Activity/Event ending.

Keep the route presentational, orchestration in focused hooks, writes behind the existing gateway, and display/readiness derivations in pure shared helpers. Do not use effects to maintain duplicate derived outcomes.

- Carried rows come from `draft.context.carriedEvents`. Preserve event identity/type, start/order, targets, source IDs and recorded mitigation facts. Corrections do not make these editable carried-state fields; the Militia page displays carried state read-only.
- Use existing `persistent_decision`, `clear_persistent_decision`, `rules_exception`, `clear_rules_exception` and the already-supported event edits as appropriate. Keep stable event, acknowledgement, modifier and exception identities; they are not list indices. Existing `persistent_decision` routing stores a current occurrence's decision on that occurrence and carried decisions in the Persistent collection; preserve this behavior and replay/conflict targets.
- Same-week events stay under their owning Event occurrence (including Activity-origin candidate occurrences). Retain their existing `persistent`, `persistentDecision`, targets/checks and required exceptions there. They do not add a carried row or unlock an ineligible Persistent step this week. Their surviving carried state is available in next week's context after Confirmation. Do not drop same-week inputs merely because the Persistent page is locked, migrate them to `persistent.decisions`, or manufacture a second decision for their ID.
- A missing decision and explicit `unattempted` keep their existing unattempted semantics. **Leave it** writes `{ kind: 'unattempted', eventId }` and stops using the prior decision's rolls/ending/buyoff; it must not reset another event, the entire week or unrelated Rules Exceptions.

Ordinary edit preserves sibling values; explicitly changing decision kind is a deliberate replacement.
- Source labels and target options use the existing source/preview facts, including entities produced earlier in the draft. Preserve distinguishable unavailable-target states. ### Checks and adjudication

Theft's DC 20 Loyalty check gives mitigation for this week only: a successful check retains 90% of applicable incoming gains, and the event remains. A failed or unattempted check retains the normal loss; next week needs its own mitigation. Use the existing whole-week projection so temporary mitigation updates dependent treasury calculations in the proper order, including buyoff affordability; do not locally patch just a header percentage.

Rivalry exposes character selection with role context, Diplomacy/Bluff/Intimidate, signed whole-number skill bonus, and one d20 total. A zero skill bonus is valid; empty bonus is incomplete. Preserve the existing non-officer exception path, unavailable character validation and DC 20 success/failure. This is the chosen character's skill check, not an organization check: do not add militia officer/Overseer bonuses to it. Two distinct stored team targets and their restrictions stay visible and rules-validated. Ending it does not retroactively erase an earlier restriction contrary to existing weekly ordering.

Theft shows the calculated organization bonus and named contributions such as **Officers +2 · Overseer +3**, plus entered modifiers with reasons. Keep the applied non-stacking officer, queued, Helpful, one-use and custom-source rules; no double-counting a source that is already calculated. Rivalry's breakdown uses its skill and applicable custom modifiers. Provide custom modifier add/edit/remove with stable source identity, signed amount and reason; no new numeric Table Adjustment control here.

**Ended at the table** reveals **How it ended** and the required `persistent-ending` Rules Exception reason. Preserve acknowledgement identity on edits and set `subjectId` to that exact event. The existing strict acknowledgement requires nonempty outcome text: opening an empty card form is local editing intent, not a valid saved `end` payload. Retain the last accepted decision until valid input can be sent, communicate unsaved/invalid form state, and do not invent an empty acknowledgement or change the schema. Write the valid ending and exception through existing operations; pending/partial failure is visible and repairable, and Confirmation cannot use an incomplete or unreconciled result. Clearing the exception revokes its permission and restores the requirement; Leave it resets the decision. The narrative outcome and exception reason remain distinct facts. A Rules Exception permits the choice; changing numeric results remains a Table Adjustment in Review & confirm.

### Buyoff and removed amount compatibility

The buyoff card writes `{ kind: 'buyoff', eventId }`. Display **Buyoff cost N gp (2 × minimum treasury) · taken from the treasury at Confirmation**. Currency is presentation over integer copper; display existing precision accurately and never write a rounded amount. The resolver still computes cost from the current rules/rank, handles the first buyoff immediately, enforces the four-week wait for later ones, resolves events oldest first, and requires existing `buyoff-cooldown`/`treasury` exceptions where applicable. Do not disable valid table exceptions merely because funds or cadence differ from rules; do not mark an unmet exception as an ending.

Keep legacy `costCopper` parse/read support. Opening a draft, navigating or reading a record never strips or rewrites it. A deliberate new buyoff selection writes the approved amount-free form; other event edits preserve their stored data.
