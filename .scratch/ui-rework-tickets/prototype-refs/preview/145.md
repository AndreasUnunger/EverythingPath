### Main-column acceptance

- At the top retain **Review the week**, **Required decisions**, all **Warnings**, stale-review alert with **Review updated week**, and **Confirm week**. Required decisions identify the actual missing choice/reason, with **Go** to its phase and relevant item; Summary-owned forms receive local focus. Links use the frame's local navigation and never change another player's Phase View. Warnings remain advisory unless the existing resolver also supplies a requirement.
- Remove the review block's ready/needs-attention sentence and explanatory applies-the-entire-week note. Keep a disabled button reason next to Confirm and in the frame's corresponding footer/status presentation: e.g. **2 decisions left**, **Review will be ready when your changes are saved.**, or the actual stale-review/local-form reason. When confirmable, no readiness sentence is shown. The frame already removes the Summary step caption and ready/needs-attention footer; do not reintroduce either in phone sheets or desktop rail.
- Below, render exactly **1 Upkeep, 2 Activity, 3 Event, 4 Persistent, 5 Table Adjustments, 6 Result · week N+1 begins**. Sections 1–4 are expanded, in that order, even when one has no consequences; give an honest empty/not-applicable/incomplete line. Their header chips show net phase changes derived from existing plans; each consequence shows named subject, check detail and its effect, in actual rules order. Event includes reactive Sabotage under its occurrence, not a seventh phase. Same-week persistent decisions belong to their Event source; carried-event decisions belong to Persistent. Do not double-count one effect in both sections.
- Under each consequence, show its warning in amber, Rules Exception with rule chip and inline reason, and recorded outcome as a quoted line. Each fact remains separately identifiable, including identical messages attached to distinct subjects. An exception whose original item is gone remains visible in its phase. An obsolete action-allowance exception retains its explanation and **Remove obsolete exception**; a reason never makes an unavailable slot usable. Phase owners retain outcome-entry controls; Summary presents those outcomes and links back for repair.
- Section 5 says **applied after the Rules Baseline, in this order**. Each numbered adjustment shows effect chip, kind, inline reason, Edit and Remove. Earlier/later controls appear only with more than one adjustment, with inaccessible moves disabled at the ends. Four playing-card choices below the list—**Militia value**, **Team condition**, **Settlement reputation**, **End persistent event**—open a form with **Save** and **Cancel**. With none: **No Table Adjustments. The Final preview equals the Rules Baseline.**
- Section 6 has columns **Value / Now / Rules Baseline / Final**. Default to rows changed between Now and baseline or baseline and Final, including a change later reversed by an adjustment. Highlight Final only where it differs from baseline; also describe the difference in text. **Show all values** reveals every existing militia fact plus roster, officers and next-week context. It toggles local presentation only. No new collapsed phase sections or prototype-only value subset.

- **Warnings only appear in the top block, never under their item.** The Fangwood Rangers recovery-cost warning never appears in amber under its Upkeep line, and the 'Team already acted' warning disappears when the exception is removed. Attach each warning to its consequence through code/subject conventions, with a phase or unassociated fallback, and keep distinct identical messages separate. §1 bullet 4, §5 warnings paragraph, SUM-09.
- **Blank reasons are saved as shared state.** `ReasonField` on adjustments and exceptions dispatches `adjust:update`/`exception:reason` on every keystroke, including an empty string. The prototype's × "Clear reason" writes `reason: ''`. - **A missing adjustment reason points to Persistent.** `project()` gives adjustment-reason requirements `phase: 'persistent'`, so the Go link reads "Go to Persistent →" and the Persistent step shows "1 to decide" (see `170-focus.png`). Summary-owned forms get local focus, and the requirement names the actual adjustment. §1 bullet 1, SUM-02.

Use react-hook-form + zod with `noValidate`, keep missing separate from malformed, and convert exact signed gp to copper (−0.07 gp → −7 copper). Use only the existing statuses: `active`, `disabled`, `missing`. The reputation list should come from the shared domain enum, not the mock's five literals. §5 adjustment table.
- **Readiness is inferred from the requirement count.** `ready = requirements.length === 0 && !forecastPending`, and Confirm is enabled whenever `blocker` is null. `canConfirm` comes from the existing accepted review, identity and revision. Local form gating can only disable Confirm further. The prototype's *Review updated week* button does nothing and its state list is incomplete. §5 Confirmation contract, SUM-03/04/05.
- **The mock reducer mutates arrays directly, with no conflict handling.** `adjust:*` and `remote` splice the in-memory list. ## 5. Data, payloads and rules

**No schema, query/mutation argument, result-shape or Weekly Resolution change is approved here. No Ruleset Version bump.** Consume the version current when this ships; retain every old record's recorded version. History listing/date changes belong only to Finished weeks. New presentation types/adapters are client code over existing data, not persisted fields or API additions.

### Six-section presentation contract for live and historical consumers

Use shared pure renderable data for ordered phase sections/items, check descriptions, phase changes, item-attached warnings/exceptions/outcomes, ordered adjustment effects and comparison facts. Identities are internal stable keys, never user-facing strings. The renderer receives those facts and explicit editing capabilities; it must not query live campaigns, call a resolver, or infer its mode from today's militia.

**Live adapter:** consume the current workspace source, optimistic Weekly Draft, canonical Resolution Preview and the accepted-review/pending state. Existing seams are `summary-facts.ts`, `summary-messages.ts`, `summary-view.tsx`, `summary-outcome.tsx`, `summary-adjustments.tsx`, `types.ts` and the workspace store. Derive Now from this current week's source snapshot; Rules Baseline and Final come from the same preview and must not mix revisions. Read all effects (including `effects.sabotage`) and nested context without losing information hidden by the current generic fact renderer. Incomplete preview is visibly incomplete: null/unavailable outcome is not zero, unchanged or a fabricated week N+1 result. Preserve available partial consequences, disclose unavailable comparison facts, and keep requirements/repair reachable.

Map subjects using stored IDs and known semantic subjects, including Activity choice and `special:`/reaction prefixes, Event occurrences/candidates/Roll Twice children, nested persistent decisions, Sabotage, Upkeep transfers/team decisions and carried event instances. Use plan provenance and real execution order rather than UI card order or alphabetic object traversal. Place phase totals from phase plans before Table Adjustments; do not apply adjustment deltas a second time. Retain action/event/team/settlement names and distinguish repeated same-type occurrences by recorded order/context. Avoid opaque IDs in labels and errors.

Warnings in records have code/message and optional rule source, not a subject field. Use known code/subject conventions for association; never add a backend subject to make the layout easier. A fact whose item is missing stays as a standalone row at the end of its known phase. If even the phase cannot be determined from existing facts, retain a clearly labelled unassociated-facts group within the six-section presentation rather than discarding it or inventing a target; live aggregate Warnings retains that entry too. Preserve distinct warnings sharing text. Do not use fuzzy string matching to attach a warning to the wrong person/event.

**Frozen-record adapter contract for Finished weeks:** input is only the selected immutable `CanonicalResolutionRecord`, using `source`, optional `sourceMilitiaSnapshot`, `baselinePlan`, `finalPlan`, `finalOutcome`, `adjudication`, `warnings` and `successorContext`. Use existing artifact `formatVersion` support and record-local names. Read the stored plans/outcomes, never run the current rules engine, borrow current officers/character labels or fetch today's militia to fill gaps. Missing old facts get a truthful **Not recorded**/existing unavailable explanation and remain readable; retain readable fallback for supported legacy artifact shapes. Historical rendering cannot import a live draft store or editing callbacks. The owning history spec integrates this adapter and its list/audit controls later; deliver the shared boundary and fixtures here so that integration is independent of live projections.

Both modes use the same section numbering, consequence order, check details, warning/exception/outcome positions and ordered adjustment list. Historical exceptions and reasons are quoted read-only text, with no clear/reorder/edit/Confirm control. History labels are **At confirmation** instead of Now, **Result · week N+1 began**, and **No Table Adjustments. The Final outcome equals the Rules Baseline.** Show all also includes recorded Operating from, uneventful-week carry, first-Upkeep skip and officers at confirmation; live Show all shows the corresponding available source/next-week facts. Frozen records retain historical differing-buyoff-cost warnings and source amounts even though Persistent removes that warning from the live presentation. Do not mutate or rewrite a record while reading it.

Result comparison must retain the union of facts from source, baseline and Final, including added/removed teams/events/settlements and nonnumeric values. Compare semantic values/identities, not formatted text; show additions/removals and reversals honestly. Show all preserves rank, training, treasury, notoriety, focus, settlements/reputation, team conditions/managers, roster/officers/characters, bonuses, event benefits, economy/assets/delivery, carried events, queued effects and remaining week context represented by current schemas. Old forms or unknown supported facts must remain readable through the existing general fact fallback rather than be silently dropped.

### Complete Table Adjustment and reason forms

Keep `tableAdjustmentSchema`'s entire discriminated union:

| Kind | Required fields and choices |
| --- | --- |
| `militia_value` | Stable adjustment identity; `training`, `treasuryCopper`, `notoriety` or `rank`; `add` or `set`; signed integer value; nonblank reason. Preserve negative and zero values, including structurally valid out-of-rules results. Default the existing new Militia value form to Treasury/Add. |
| `team_status` | Exact campaign team, every existing status (`active`, `disabled`, `missing`), reason. |
| `settlement_reputation` | Exact campaign settlement, every reputation from the shared domain enum, reason. |
| `event_end` | Exact applicable persistent event instance, reason; preserve duplicate event types as separate choices. |

Money displays and inputs use gp over stored integer copper. Convert exactly, including negative amounts and one-copper precision; e.g. −0.07 gp writes −7 copper. Reject malformed/unsafe/excess-precision values with a field error, never silently round or coerce blank to zero. Other militia values remain signed whole numbers. Rule deviations are advisory or use existing required Rules Exceptions; this presentation does not tighten existing schemas or turn warnings into blockers.

Save through the existing `table_adjustments` edit containing the full ordered list. Add once with a stable ID; edit preserves identity; remove affects only that ID; reorder preserves all other values/reasons. Build the operation against the latest accepted/optimistic list and retain existing revision/operation conflict behavior. Do not send a stale array captured when a form opened over another player's changes, invent a batch endpoint, or silently retry conflicting intent. On conflict reconcile, show the accepted state and keep recoverable local intent/errors; a remote edit never erases an unrelated adjustment. Cancel sends no edit and does not undo accepted remote changes.

Exception reasons use existing `rules_exception` and `clear_rules_exception` operations, preserving exception/subject/rule IDs. Clearing an exception with × revokes its permission and restores the underlying required decision; it does not save an empty strict exception. Do not edit an obsolete action-capacity exception into permission. Missing/blank adjustment reasons remain invalid **local form state**: the strict saved adjustment cannot contain an empty reason. Keep the last accepted adjustment while editing, mark the field amber with textual error and surface the local required decision; block this device's Confirm until valid Save or Cancel/removal. Never fabricate invalid saved records or automatically delete an adjustment because the reason was cleared. Unsaved local changes are not shared facts and do not block another device from confirming its accepted reviewed week. If another member confirms, retain no editable stale form against the successor; frame transition resets it by draft identity.

`react-hook-form` and `zod` validate forms with styled field errors and `noValidate`; separate missing from malformed values. Meaningful local incomplete forms, save failures and remote conflicts must remain visible and prevent accidentally confirming their old accepted values on that device. Do not replace raw typed invalid input on every subscription refresh. Successful Save/Cancel clears the relevant local-only state; identity-keyed resets handle a different draft/item. Changes accepted elsewhere continue to update preview and invalidate stale reviews through the existing store. If a target disappears, show its unavailable-target state and recovery link; preserve corrections' complete-reference repair limitations instead of promising unrelated writes can bypass orphaned references.

### Confirmation contract and shared transition
