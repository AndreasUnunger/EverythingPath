## 1. Scope and ownership

Deliver guided **Militia Setup** at `/campaigns/<id>/setup`, for both a new militia and an existing campaign's current table state. This is shipping area **8 of 12**, after Review & confirm and before Militia corrections. This issue implements the approved design; its authoring task is [Write the Setup implementation spec](https://github.com/AndreasUnunger/EverythingPath/issues/130) in [Rework the militia UI for ease of use](https://github.com/AndreasUnunger/EverythingPath/issues/99).

Own the nine steps, free navigation and status, browser-resumed unfinished input, inline Add character, defaults, structural validation, section warnings, review/start, initialization feedback, live setup collision and already-started page. Establish reusable section editors and client validation/warning routing consumed by Militia corrections. Setup initializes facts and an ordinary Weekly Draft; it neither resolves a week nor starts a separate gameplay model.

The [Navigation shell implementation](https://github.com/AndreasUnunger/EverythingPath/issues/135) owns routes, campaign access, organization/account controls, the maintenance banner and shared failed-load component. Setup owns its skeleton and failure content inside that shell. Week frame owns Phase View eligibility, setup-note display and shared weekly editing after entry. Militia corrections owns section merging, correction reasons/conflicts and draft-reference warnings; Characters & officers owns later kind/Hit Dice/manager-rule changes and migration of every Setup consumer. No correction-history feature, shared setup draft, new authorization role or character builder is included.

Buttons, status text and error links remain keyboard and screen-reader usable. Long names, nested repeatable entries and errors wrap without horizontal page overflow or row misalignment; all controls stay above or scroll clear of the shell's fixed phone tabs.

- **Switching New/Existing wipes the form.** The `scenario` action with `key: 'mode'` in `mock.ts` returns `initialState(...)`, which resets the draft, the step and the visited statuses. New/Existing must keep entered facts. The only allowed change is that switching to Existing clears the first-militia-week skip. Mode changes must never overwrite an intentional edit. See §4 SETUP-01 and §5 "Validation".
- **PC/NPC kind toggle and Hit Dice with a level fallback.** The People & officers rows use a `pc | npc` radio, and Hit Dice shows the level as its placeholder. Keep character-record `pc | officer_npc`, roster `pc | officer_npc | other_npc` and the required commandant Hit Dice until Characters & officers migrates them. - **A reduced Add character dialog that writes into the local draft.** The dialog has only Name, Level and Cha modifier. It adds the row straight to `draft.people` with `onRoster: true` and `kind: 'npc'`. Instead, reuse the full existing dialog: name, kind, level, six ability scores, notes and validation. Create through `character.createCharacter`, and let `options.characters` deliver the record reactively. Roster inclusion stays explicit, and a failure keeps the dialog values. See §4 SETUP-26, CHAR-03 and CHAR-07, and §5.
- **"Another player finished setup" discards input and lands on Militia.** The banner reads "Your entries here are discarded and the week opens in a moment". A 2.5 s timer then switches to the Militia screen, and our own *Start militia week* also goes to Militia. A live external completion must open that campaign's accepted current week. Our own success must open the requested eligible phase exactly once. See §4 SETUP-27 and NAV-14, and §5 "Start/race state machine".
- **No started page.** The prototype has no "This militia is already set up." page with *Open week N* and *Open militia*. A first visit to a started militia must show that page, even when a stale browser envelope exists, and must not redirect automatically. See §4 SETUP-22 and the [#119 approval](https://github.com/AndreasUnunger/EverythingPath/issues/119#issuecomment-5846266381).
- **Start is instant.** `startMilitia` dispatches synchronously. It has no "Starting militia…" pending state, no protection against duplicate submission, and no failure/retry that keeps values. Implement those, and keep the same attempt ID and source on retry. See §4 SETUP-21 and §5 "Start/race state machine".
- **Simplified mock fields are not the field list.** Examples:
  - Conditions offer only `captured / in_refuge / missing`.
  - Settlements lack Reduce Danger and refuge weeks.
  - Orders lack due day/Activity week, delivery days, enchantment value and receipt.
  - Items lack weight.
  - Caches lack return week and contents.
  - Marketplaces lack availability and sale percentages.
  - Queued effects are a free-text "Effect".
  - Persistent events have no targets or Theft mitigation.
  - Skill benefits take free-text characters.

  Every field in §4 SETUP-05…SETUP-17 stays. §4 says: "omission from simplified prototype data is not approval to remove a field".
- **Whole-number-only validation with no reference checks.** `errorsFor` rejects anything that isn't `/^-?\d+$/` ("must be a whole number"), which would reject decimal enchantment values. It also has no hard reference checks: missing carried-event targets, incomplete order delivery facts, and foreign or impossible IDs. Use react-hook-form + zod with the shared validators. See §5 "Validation", SETUP-12 and SETUP-20.
- **Error links only switch step, and the setup chrome is not the shell.**
  - `ErrorSummary` calls `go(stepForProblem(p))`. It neither focuses the field nor, on phone, expands the row. See §3 and §8.
  - The prototype's top bar shows only "Set up militia" and "Not started yet". Use the shell, which keeps normal navigation and all sections available. See §1 and §7.
  - Hard-coded `text-amber-300`, native checkboxes and raw `<button>` radios must become shadcn/ui components and theme tokens. See §3.

## 5. Data, payloads and rules

**No backend schema, query/mutation argument or result-shape change; no Weekly Resolution change, Ruleset Version bump or database migration in this issue.** Reuse `canonicalSetup.options({ campaignId })`, `canonicalSetup.initialize({ campaignId, initializationId, setup })`, the existing `MilitiaSetup` schema, `newMilitiaSetup` and `prepareMilitiaSetup`. Member authorization and campaign-scoped references remain server-enforced. Setup choices remain personal until initialization; no shared setup persistence or locks are added. Inline character creation is already shared immediately and is independent of starting the militia.

Read the current seams before implementation: `src/components/militia-setup/{screen,form,fields,roster,world,effects,assets,carry}.tsx`, `src/lib/canonical-setup.ts`, `canonical-roster.ts`, `canonical-weekly-source.ts`, `weekly-draft-references.ts`, `src/components/character-manager.tsx`, its form/types, `sharedQueries.ts`, and `convex/canonicalSetup.ts`. Read `convex/_generated/ai/guidelines.md` before backend-related work. Keep routes thin, use focused form/controller and mutation hooks, and keep defaults/rules/warning derivation pure; effects are for external persistence/subscription boundaries, not duplicated derived state.

**Shared editor contract:** one typed form model retains all values while steps unmount. Split the present composite editors only as needed to expose the nine step boundaries (for example People versus Teams, Settlements versus persistent events, conditions versus benefits). Editors bind existing field paths, use shared field controls, accept authorized character choices, and do not perform backend saves. Share field-level and cross-reference validators with correction consumers. Create client warning descriptors with stable section keys/message/optional field target for Starting point, Week, People & officers, Teams, Settlements, Character conditions, Assets and Carried effects; correction callers can additionally select asset/benefit subsections. Preserve the existing `prepareMilitiaSetup(...).warnings` string/result contract and backend responses; enrich or derive section metadata locally without introducing a wire field or classifying English strings by fragile substring matching. Map root/cross-section reference errors to their relevant section and retain a visible summary fallback. Militia corrections later owns latest-snapshot merging and conflicts; its existing full correction form remains usable through this refactor.

**Validation:** react-hook-form + zod, `noValidate`, styled field messages and links. All steps are freely reachable; only Start is blocked by invalid data. Distinguish required/empty from invalid type/format, preserve valid decimals where supported, stable entity IDs/order and current hard reference checks (missing carried-event targets, incomplete order delivery facts, foreign records, impossible enum/ID types). Rules mismatches such as rank/training, caps, notoriety and manager limits stay advisory with values preserved; no acknowledgment box or extra required notes. Use existing deterministic defaults from rules utilities, never overwrite an intentional edit when navigating or changing mode. Do not silently relax required current commandant facts before the named migration.

**Browser resume:** persist a versioned client form envelope scoped by account/organization/campaign, including raw editable values and initialization identity; validate the envelope separately from submit validity so “invalid” and empty numeric edits survive reload for repair. Restore only after authorized campaign/options resolve and before writing defaults. Navigation away/back or reloading preserves unfinished input. Invalid/corrupt envelopes cannot crash the page, be auto-submitted or leak into another campaign; storage unavailable must not prevent entering or starting setup, and a persistence failure gets concise outcome-oriented feedback. Do not clobber active inputs on options refresh. Once setup is authoritatively started, retire its unfinished envelope; later visits must not resurrect it. No autosave to Convex or cross-device form mirroring.

**Start/race state machine:** resolve first authoritative options result before deciding entry state. If it is already started, render the two-link page, even when a stale local envelope exists. Obtain N from an existing authorized current-week read (`canonicalDraftPersistence.workspace` via the established campaign context); `options` currently has no week field, so do not extend its result for the label. If options was unstarted and the form is open, a subsequent started transition navigates automatically to that campaign's current week. On this player's successful submission, preserve the requested eligible phase rather than letting a racing options update redirect to Upkeep first. An external winner opens its accepted current week with the usual default Phase View. Initialization retries preserve the same attempt ID and submitted source; retain the server's same-ID/same-source idempotence and changed-source/competing-request rejection. Disable duplicate submissions while pending; an unknown acknowledgment cannot justify submitting a different source under an already-accepted identity. Failure retains fields and normal retry feedback; authoritative started state wins over a transient error. Starting never overwrites another player's accepted militia or advances the week.

**Character creation and later migration:** reuse/extract the existing dialog/form and `character.createCharacter`; preserve all fields/errors and let `options.characters` deliver the created record. Creating a record does not automatically assign roles or a manager; roster inclusion remains explicit. Refresh available records without wiping local choices; current stale-reviewed-character rejection remains safe and recoverable. This shipping stage retains character-record `pc | officer_npc`, roster `pc | officer_npc | other_npc` and required commandant Hit Dice. The later Characters & officers implementation must update Setup's schema/validation, roster kinds mirrored from authoritative character records, any character-option data source (current options omits kind), inline dialog, manager warnings/calculations, optional Hit Dice with level fallback, current drafts and persisted browser envelopes. Dropping roster kind is not approved. That later owner allocates the next unused Ruleset Version for changed resolution behavior and preserves older Resolution Records; Setup must not pre-apply the prototype's incompatible enum or fallback.
