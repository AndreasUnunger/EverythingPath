## 1. Scope and ownership

Deliver **Campaign list and home, rollout position 12 of 12**: the organization’s campaign list and selected campaign home are one screen, with creation in the pane, description/date editing, Continue week, militia summary, latest three finished weeks and character access.

This implementation issue is outside the [Rework the militia UI for ease of use](https://github.com/AndreasUnunger/EverythingPath/issues/99) planning map; authored by [Write the Campaign list and home implementation spec](https://github.com/AndreasUnunger/EverythingPath/issues/134). Main was inspected at `eef41f7bad19e63ecce858e7a4490c937a4ece89`; the planning branch adds inventory accounting, not implemented UI.

Use [Navigation shell](https://github.com/AndreasUnunger/EverythingPath/issues/135) for scoped routes, organization/account controls, membership boundary, maintenance banner and shared failed-load component. Use [Week frame](https://github.com/AndreasUnunger/EverythingPath/issues/137) for client-derived all-phase Phase Readiness and Persistent Phase Eligibility; [Setup](https://github.com/AndreasUnunger/EverythingPath/issues/138) owns starting/resuming a militia, [Militia corrections](https://github.com/AndreasUnunger/EverythingPath/issues/139) its full details/corrections, [Characters & officers](https://github.com/AndreasUnunger/EverythingPath/issues/141) its destination and role semantics, and [Finished weeks](https://github.com/AndreasUnunger/EverythingPath/issues/146) the single listing query and immutable history destination.

Own only two backend changes: `createCampaign` returns its inserted ID, and a campaign-description mutation. Reuse the date mutation and history listing contract unchanged. No campaign rename/delete/archive, automatic organization switch, new summary query, new weekly editor, historical reconstruction/correction, role restrictions, theme change or prototype merge.

### Campaign selection and creation

- `/campaigns` and `/campaigns/<id>` render the same list/home screen. The bare list selects the first campaign in the existing query order; a chosen row updates `/campaigns/<id>` and displays that pane in place, without opening the week. An explicit ID is never silently replaced by the first campaign when unavailable. Direct links, reload and Back/Forward retain selection. Selecting an existing row exits the local create form; Cancel restores the previous available selection, or the empty-organization create entry.
- Tablet landscape has a 320px left index headed **Campaigns**, an accessible **New campaign** plus button, and rows with name and **Week N** or **Not set up**. Resolve those labels from existing campaign-scoped workspace reads; loading/failure is not Not set up. The selected pane is on the right. A single campaign uses this same layout, without a special redirect or auto-start.
- **New campaign** selects a ghost New campaign row and puts Name, optional multiline Description, Create and Cancel in the pane. Creation starts with an empty name and description; it never creates a default-named campaign as a side effect of navigation. Name validation distinguishes **Enter a name.**, **Name must be at least 2 characters.**, and **Name must be 50 characters or fewer.** Preserve the 2–50 character contract; use react-hook-form/zod and field-contained styled messages, not browser popups. No organization ID fallback of an empty string.
- Only a valid submission in an authorized active organization writes. Show pending/error/success state and suppress duplicate submissions while pending. After acknowledgement, select the returned campaign ID and show its home with **Set up militia**. Wait for the authorized campaign-list observation if it has not arrived yet; do not momentarily label the newly created campaign unavailable or select a different row. Never match by name: duplicate names can exist. Keep submitted values on a definite failure.
- An empty authorized organization shows **No campaigns yet** in the list and the form headed **Create a campaign to get started.** The New/Cancel path must remain usable without producing an empty dead end or a fake campaign row. Empty is distinct from no selected organization and access failure.

### Home pane

- Header: campaign name, readable Golarion **in-game date** when recorded (for example 12 Pharast 4717), full multiline description, **Edit**. Missing description/date is an ordinary empty value, not a fabricated date or description. The desktop index preview may truncate its description, but the pane must expose it in full.
- **Edit** replaces the header with Description textarea, the existing **In-game date** fantasy date picker, Save and Cancel. Name stays read-only. Populate current saved values; Cancel before submission makes no writes. Missing/cleared dates remain supported by the existing optional field. Preserve the date picker’s stored date-only representation and calendar conversion; do not replace it with a Gregorian browser date input or a timestamp derived from the current day.
- With a militia, a large **Continue week N** opens the first eligible phase that is not ready in rules order: Upkeep, Activity, Event, Persistent, Review & confirm. Skip Persistent when the week’s fixed eligibility is false; a same-week event cannot unlock it. When every preparatory phase is ready, open `summary` for review. Reuse the Week frame’s readiness computation over current accepted workspace/draft data; warnings alone do not mean not ready. Do not fabricate a target from a stale week while data loads. This button navigates only: it neither saves a Phase View nor confirms the week. There is **no next up caption**.
- A **Militia** card has one compact line: rank, focus, team count with disabled/missing counts, officer roles filled out of six, and settlement attitudes, plus **Open militia**. Count occupied role categories, not holders (multiple commandants do not make more than six roles). Use the current stored militia and shared rule/formatting helpers; do not use projected next-week values or reinterpret character kinds locally. Wrap long content; keep the complete summary accessible. Detailed values/Now–After comparisons remain in Week’s reference panel and full Militia.
- **Recent finished weeks** shows up to three latest effective weeks, latest first, with week labels, supported compact headlines and **Corrected** or **From setup** provenance as supplied by the history contract. Corrected takes precedence for a superseded chain; From setup represents an uncorrected reconstruction, not every record created around setup. Each row links to `/campaigns/<id>/history?week=<n>`; **All finished weeks** links to `/history`. Zero rows shows **No finished weeks yet.** with that destination still reachable; one/two rows are valid. A preview failure stays local with Try again and does not block Continue week or character access. No correction notes or full historical record renderer in this pane.
- **Characters & officers** opens `/characters`. Without a militia, the pane contains only the header, **Set up militia** to `/setup`, and **Characters** to `/characters`; skip militia/history queries that require a militia. Creating a character does not require starting a militia. If another player finishes Setup, switch the observed home to the started form; do not repeat initialization. Setup owns its browser-resume and already-started behavior.

### States and local editing

Render the shell immediately. List/home loading uses layout-shaped skeletons with **Loading campaigns…** available to screen readers. No organization: **Choose an organization to see its campaigns.** with the shell switcher. Explicit no-access list response: **You don’t have access to this organization’s campaigns.** Failed list: **Campaigns could not be loaded. Please try again.** and **Try again**. Use the shell’s signed-out and neutral unavailable campaign states for direct invalid/deleted/nonmember/wrong-organization IDs; never reveal that an inaccessible campaign exists. A list error does not become an empty organization. Scope/cancel subscriptions and local forms when organization, campaign or access changes, so previous names, descriptions, dates and history cannot flash in the new scope.

Remote accepted edits refresh read-only home/row values and receive concise accessible acknowledgement without moving the player’s selected campaign or focus. Keep unsaved local header values intact; announce an observed saved-value change rather than silently resetting typed input. Submit only dirty fields and keep explicit submitted values tied to their original campaign/organization. These simple field mutations have existing last-writer semantics, not a new lock or revision-check contract. Maintenance uses the shell banner while all content remains readable; controls are not preemptively disabled and attempted writes show the server’s normal failure message.

## 5. Data, payloads and rules

Read `convex/_generated/ai/guidelines.md` before backend implementation. Current files: `convex/campaign.ts`, `src/app/campaigns/createCampaignForm.tsx`, `src/components/canonical-campaign-dashboard.tsx`, `src/components/ui/fantasy-date-picker.tsx` and the fantasy calendar helper/tests. Preserve campaign schema, ownership and organization indexing.

1. **`campaign.createCampaign`: approved result-shape change.** Keep existing `{ name, description, organizationId }` arguments and organization access/maintenance enforcement. Return the inserted `Id<'campaign'>` rather than today’s implicit null. Update typed caller callbacks and generated API through the normal workflow; audit every consumer/fixture/test, including old callers that ignore the result and `acceptedCampaign.integration.test.ts`. No extra create payload, militia creation, idempotency key or database migration.
2. **`campaign.updateCampaignDescription`: approved new mutation.** Arguments `{ campaignId: Id<'campaign'>, organizationId: string, description: string }`; empty string clears description. Match `updateCampaignInGameDate`: authorize membership using identity from context; load campaign and verify its organization matches; patch only description; return the updated campaign document. Use campaign mutation wrapper/maintenance handling and validators. No GM-only gate, owner-only restriction, name edit, caller identity or combined date update.
3. **Existing `campaign.updateCampaignInGameDate`: unchanged.** Existing `{ campaignId, organizationId, inGameDate?: string }` arguments and updated-document result remain. Read from `getCampaigns` documents and preserve existing optional date semantics; structural date validation/formatting belongs to shared picker/helpers. No date stored as localized fantasy display text or converted from a history timestamp.

### One Save, two independent mutations

Description and date save separately; a UI Save cannot make them atomic. Validate both before sending, call only dirty fields, track each request and its accepted result. Keep the form open until all intended changes have definite results. When description saves but date fails (or vice versa), show which field saved and which failed, retain the failed input for retry, and update the saved baseline for the successful field. Retry only the unresolved/failed change; never replay a successful field over a newer remote edit, run a compensating rollback, or claim neither change saved. Cancel after a partial success discards only unsaved input and shows the latest saved document; it does not undo an accepted write. The global Saved message/closing the editor requires all intended changes to be acknowledged.

While acknowledgement is pending or uncertain, report pending/unknown status honestly and reconcile with the subscription/result instead of sending another blind operation. A matching observed value can establish the current saved value, but does not establish which player wrote it. Do not promise conflict-free multi-field saves. For create, retain the single pending request and resolve the returned ID; after an ambiguous outcome do not automatically recreate or infer identity by matching a name. Refresh/read the authorized list and make any subsequent Create an explicit user action, without claiming the first request certainly failed. Keep the target organization/campaign fixed through delayed responses; navigation to another scope cannot retarget or apply stale results.

### Existing reads and the Finished weeks contract

`campaign.getCampaigns({ organizationId })` already returns authorized campaign documents including description/date, or `no_org_selected`/`no_access`; its result does not contain militia week numbers. Reuse `canonicalDraftPersistence.workspace({ campaignId })` per authorized displayed row to obtain **Week N** or null→**Not set up**. Use focused row components so subscriptions have valid hook lifetimes; only the selected campaign needs its draft observation/readiness projection and history preview. Reuse existing source key and `canonicalDraftPersistence.observe` with Week frame’s derivation; do not mount a second editable week board, persist readiness or add week/summary fields to `getCampaigns`. Current source snapshot supplies rank/focus/teams/officers/settlements. Query failures retain error/retry state rather than pretending there is no militia. No speculative query/schema expansion for optimization is approved.

For a selected campaign with a militia, call exactly **`canonicalHistory.list({ campaignId, limit: 3 })`**, without beforeWeek or selectedWeek. Finished weeks owns result `{ weeks, earlierWeek, selected }`, descending distinct weeks. Each row: `{ week, effectiveRecordId, effectiveSequence, entryCount, provenance, rulesetVersion, createdAt, headlineFacts }`. Use entryCount > 1 for Corrected and actual provenance for From setup. `headlineFacts` contains at most two `{ key, label, before, final, beforeRecorded, finalRecorded, unit }` compact comparisons. Format money from copper with existing gp helpers and names from supplied record-local labels; missing comparable facts use **Recorded outcome available**, never fabricated zero/no changes. If showing a recorded date, use its supplied epoch instant consistently with Finished weeks; it is distinct from campaign in-game date. Ignore pagination for this preview and link All finished weeks. Do not fetch three full records, add another list endpoint, scan current week minus one/two/three, recompute outcomes or return raw artifacts. Zero/one/two rows and sparse/corrected histories are valid. Do not query history without an authorized militia scope.

All reads/writes remain server-authorized for organization membership and campaign association even when invoked directly; shell gating is not authorization. All organization members can edit. Realtime observations update row week, selected summary/CTA and latest-three list after accepted Setup/Confirmation/corrections without a manual reload. Selection and unsaved forms remain device-local. No Weekly Resolution change, Ruleset Version bump or record backfill is needed; in-game date/description edits must not alter immutable Resolution Records.
