## What to build

Setup and Militia corrections share section editors, validators and typed section warnings split at the nine step boundaries, while the current Setup form and full correction form keep working unchanged.

## Acceptance criteria

- [ ] Split the current composite Setup editors only where needed to expose the nine step boundaries (for example People versus Teams, Settlements versus persistent events, conditions versus benefits). Editors bind existing field paths, use shared field controls, accept authorized character choices, preserve raw invalid input and never save.
- [ ] Extract shared field-level and cross-reference validators and client warning descriptors with stable section keys, message and optional field target for Starting point, Week, People & officers, Teams, Settlements, Character conditions, Assets and Carried effects, with selectable asset/benefit subsections. Map root/cross-section errors to their section with a visible summary fallback. Keep `prepareMilitiaSetup(...).warnings`, backend responses and wire shapes unchanged; do not classify English message text by substring.
- [ ] Rehost the existing Setup form and the existing full correction form on these editors with unchanged fields, defaults, required correction reason, validation and saves, proven by `form.test.tsx`, `canonical-setup.test.ts` and the Setup/correction E2E scenarios.
- [ ] Include the slice’s applicable tablet, phone and desktop behavior, accessibility, structural validation, membership/campaign isolation, multi-device save/failure/reload and Confirmation safeguards; retain working existing controls for unsplit capabilities. No prototype merge or unapproved contract change.
- [ ] Run `pnpm -s typecheck`, `pnpm -s lint` and relevant meaningful unit/integration/browser scenarios from the owning spec. Record actual results and environment limits; update capability inventory locations and evidence only for shipped work.
