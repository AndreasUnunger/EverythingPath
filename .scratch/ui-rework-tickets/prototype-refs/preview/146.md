### Page acceptance

- Tablet landscape: an oldest-first week index on the left, selected record on the right. Open the latest finished week by default, visibly selected at the bottom. Each row shows week number, effective record date, up to two truthful headline changes, and corrected/entry-count or reconstructed marker as applicable. End with **Week N is in progress** using the actual open week, not highest historical week plus one. Gaps and mid-campaign starts remain valid. The latest row replaces the standalone Latest finished week button.
- Previous/next arrows in the record header navigate actual recorded week numbers, skipping gaps; disable the unavailable direction. Selecting a different week selects its effective record and resets that week's audit page/disclosure and Show all state. Return to this campaign's current week stays reachable.
- Header: week, provenance, selected record date and recorded Ruleset Version. When an older record is selected, show **Earlier entry X of N** using that record's zero-based sequence plus one and the effective chain's entry count. The complete detail always belongs to that selected record; the index continues to summarize each week's effective record. No context chips under the header.
- Show **N entries** only for multiple entries. It expands an inline newest-first page of at most five audit entries, each with Entry N, provenance, its date, its recorded Ruleset Version, selected state and effective marker. **Earlier entries** loads the next page of up to five, preserving the selected record. Do not append pages into an unbounded visible list. Keep a route back to the first audit page/effective entry: reopening the disclosure resets to the newest page without changing the selected record; selecting the effective week row also resets selection. No correction notes.
- Detail has exactly **1 Upkeep, 2 Activity, 3 Event, 4 Persistent, 5 Table Adjustments, 6 Result · week N+1 began**. Sections stay expanded. Phase headers show recorded net changes; ordered consequences show recorded checks and effects. Rules Exceptions, warnings and recorded outcomes appear under their items; detached facts are preserved through the shared contract. Same-week persistent decisions and reactive Sabotage stay with their Event source, while carried-event decisions stay in Persistent. Nothing is double-counted.
- Table Adjustments retain their original order, effect, kind and quoted reason. With none: **No Table Adjustments. The Final outcome equals the Rules Baseline.** History has no reason fields, add/edit/remove/reorder controls, obsolete-exception removal or Confirm controls.
- Result columns are **Value / At confirmation / Rules Baseline / Final**. Default to facts changed between source/baseline or baseline/final, including changes reversed by an adjustment. Final differences use text as well as color. **Show all values** reveals every recorded value, roster/officers, recorded Operating from, uneventful carry, first-Upkeep skip and the successor context. Context is not deleted when moved here. Treasury display uses copper-exact gp formatting.
- One footer line replaces the two old notices: **Read-only. Recorded when the week was confirmed. Corrections to a finished week aren't available yet.** Retain the prominent provenance label for reconstructed/corrected entries; never imply an earlier audit entry is effective.

## 5. Data, payloads and rules

### Approved boundary and current implementation

Only the approved new finished-week listing query and **record creation dates in query results** ship here. No storage/schema change, new history mutation, correction notes, history rewrite, Weekly Resolution change or Ruleset Version bump. Keep all old Resolution Record payloads byte-for-byte unchanged. Do not add timestamps inside `CanonicalResolutionRecord`; use query envelope metadata from Convex document `_creationTime`.

Current seams: `convex/canonicalHistory.ts`, `convex/lib/canonicalDraftStorage.ts`, `convex/lib/canonicalStorageValidators.ts`, `src/lib/canonical-resolution-record.ts`, `src/components/historical-week/{screen,record-view,record-facts}.tsx`, plus the shared presentation introduced by Review & confirm. Read `convex/_generated/ai/guidelines.md` and the Convex skill before backend edits. Use object-form functions with argument/return validators.

Current `canonicalHistory.read` already accepts campaignId, optional week, recordId and beforeSequence; it returns one selected record, effective ID, adjacent recorded weeks and up to five audit entries. Audit entries currently contain only recordId, sequence and provenance. The existing index `by_campaignId_and_week_and_sequence` supports effective tips, sparse adjacent weeks and bounded chain paging. `by_recordId` supports scoped selected-document lookup. Append-only storage requires each new sequence to supersede the previous effective tip and increments sequence from zero: **effective sequence + 1 is the entry count**; selected sequence + 1 is Entry N. Do not count by collecting every correction.

### One shared listing query

Add `canonicalHistory.list` with:

- `campaignId: Id<'campaign'>` required; optional nonnegative integer `beforeWeek` (exclusive descending week boundary), optional integer `limit` (default 25, 1–50), optional nonnegative integer `selectedWeek`.
- Result `{ weeks, earlierWeek, selected }`: `weeks` contains at most limit distinct finished weeks in descending week-number order; `earlierWeek` is the oldest returned week when another older week exists, otherwise null, to pass as the next beforeWeek; `selected` is that exact selectedWeek's effective row or null. Without selectedWeek it is null. It is independent of the list window, allowing a deep-linked older record to get accurate entry-count/header metadata without loading every intervening week. If selectedWeek is already in weeks, reuse that same row.
- Each row is `{ week, effectiveRecordId, effectiveSequence, entryCount, provenance, rulesetVersion, createdAt, headlineFacts }`. `createdAt` is the effective document's `_creationTime`, an epoch-millisecond instant; provenance/ruleset come from that same effective record. No duplicate row for each audit entry. A corrected row's date is the effective record's creation date, not a fabricated original Confirmation date. Corrected marker uses entryCount > 1; an uncorrected reconstruction uses its actual provenance.
- `headlineFacts` is **at most two compact comparison facts**, each `{ key, label, before, final, beforeRecorded, finalRecorded, unit }`; before/final are scalar string/number/boolean/null values, unit is `number | gp | text`. Key is an internal stable semantic key, never displayed. Treasury values remain integer copper when unit is gp. Null and recorded flags distinguish an absent entity/value from an unavailable legacy fact. Label uses record-local names or stable numbered fallbacks only.
- Select headline candidates deterministically from supported stored before/final facts: treasury, training, rank, notoriety, focus, team additions/removals/conditions, settlement reputation, then persistent-event changes, with stable recorded ordering within each family. Include only genuine known changes, not today's rules predictions; extract current artifact facts from stored source/plan-before and finalOutcome/plan-after, retaining supported legacy extraction. The client formats signed deltas, changed text or added/removed subjects from these pairs. If the record lacks comparable facts, headlineFacts is empty and the client shows **Recorded outcome available**; do not assert No changes or calculate a delta from missing zero. Full facts stay available through the selected-record reader.
- Do not return full source choices, snapshots, plans, raw records or all corrections merely to draw two headlines. This query exposes only the compact projected comparisons and metadata above. Projection reads the effective record; it does not call a rules resolver or fetch today's labels.

Implementation uses bounded index seeks: find newest effective tip below beforeWeek, then repeatedly seek strictly below the returned week for the next tip. Each seek skips that week's entire correction chain; do not scan a page of raw audit documents and mistakenly treat it as a page of weeks. Fetch one additional tip for the older-page indicator. selectedWeek uses an exact-week indexed descending first query. Validate every returned tip against the authorized campaign/militia scope. No unbounded collect, count scan or added table/index is needed.

History loads the newest page, sorts its rows ascending for the approved oldest-first index, and prepends older pages on **Earlier weeks** at the top. All finished weeks remain reachable; every displayed segment is oldest-first, and latest stays the bottom row. This bounded loading control is an implementation detail for the newly approved list, distinct from the fixed five-entry **Earlier entries** audit control. On direct links outside the loaded window, render selected metadata/detail immediately and load the relevant index window without sequentially fetching every intervening page; gaps and omitted pages must never be presented as absent records. Keep the cached newest row visible at the bottom as the Latest finished week selection; it restores the newest index window. Mark omitted ranges with a load-more control rather than inventing missing weeks. Merge repeated/reactive rows by week, using effective ID/sequence to update a row rather than duplicate it.
