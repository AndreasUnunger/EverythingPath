## 5. Data, payloads and rules

### Approved dice-total contract and compatibility

Today `src/lib/weekly-draft-facts.ts` uses one strict raw-roll object: `dice: number[]`, `sides`, `provenance`, `modifiers`. Upkeep and Activity require exact array lengths; Event/related checks access `dice[0]`. The same schema is nested in stored draft operations, canonical Resolution Record sources and structured Event/Persistent details. Replacing only Upkeep's inputs will break these consumers.

Implement an additive, unambiguous roll representation within the approved total change:

- Legacy form retains `dice`, `sides`, `provenance`, `modifiers` unchanged.
- New total form uses `diceTotal`, `diceCount`, `sides`, `provenance`, `modifiers`; it does not also contain `dice`. Both alternatives stay strict. `diceTotal` is a finite nonnegative safe whole number, `diceCount` a positive safe whole number, and existing sides/provenance/modifier structural constraints remain. Count/sides are the roll specification, not user-adjustable rule settings in ordinary roll controls.
- `diceTotal` is the **sum of dice only**; rank, organization bonuses, officers, selected one-use sources and entered modifiers remain separate and count once. For a required 2d4 the usual total range is 2–8; for 2d6 it is 2–12; for 1d20 it is 1–20. Out-of-range whole totals, including zero, save with advisory warnings. A wrong expected count/sides remains an incomplete/inapplicable input, not a range override.
- Normalization for calculation returns expected count, sides, dice total and the natural value for single-die rolls. A natural 1/20 is the unmodified one-die value in either form; a multi-die sum equal to 1/20 is never a natural d20 result. Preserve all original provenance and modifiers when editing the number.
- A complete legacy array displays its sum in the new field without rewriting on read, and produces exactly the same outcome and applicable legacy per-die warning as before. An incomplete old array remains incomplete, with a visible indication that its recorded dice need a complete total; do not sum partial input as if complete, fabricate missing dice, or cast `[total]` as two dice. Keep the original data until the player supplies/replaces/clears that roll. Branch changes recalculate the required specification without treating a stale differently specified roll as ready.
- Newly edited roll fields write the total alternative. Clearing deletes/nulls through the existing relevant edit operation and preserves clear semantics; never save NaN, an empty array as a valid total, or an invented zero. All current roll controls, including generic nested Event/Persistent rolls, must render/edit both forms by the end of this delivery. Their page layouts may remain old. Custom modifiers, officer/target choices, acknowledgement and structured list operations remain available.

The field names above concretize the already-approved dice-total payload, not a new endpoint or unrelated migration. Share a pure helper/adapter rather than adding phase-specific coercions. Complete this compatibility work before any new writer is enabled:

### Approved transfers and rule behavior
