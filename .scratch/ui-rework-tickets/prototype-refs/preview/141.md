## 1. Scope and ownership

Implement **Characters & officers**, position **10 of 12** in the [agreed rollout](https://github.com/AndreasUnunger/EverythingPath/issues/122#issuecomment-5846600504), at `/campaigns/<id>/characters`. Deliver the six officer cards, character records, roster membership and two separate reasoned correction modes. Own the approved `pc | npc` migration, roster-kind mirroring, role-based manager limits and commandant Hit Dice fallback, including every already-shipped consumer.

[Militia corrections](https://github.com/AndreasUnunger/EverythingPath/issues/139) owns Teams and manager editing, section conflict/reference-repair primitives and other militia sections. [Guided Setup](https://github.com/AndreasUnunger/EverythingPath/issues/138) owns initialization and shared form primitives; this issue updates them for the migration. [Navigation shell](https://github.com/AndreasUnunger/EverythingPath/issues/135) owns campaign access, routes, account/organization controls and maintenance; [Week frame](https://github.com/AndreasUnunger/EverythingPath/issues/137) owns weekly feedback/readiness. Activity owns staging Change Officer Role: this page shows pending actions but never stages them. No correction-history query, full character builder, new manager editor here, hard deletion or history rewrite.

Acceptance for the page:

- Tablet landscape: Officers header with militia focus, six role cards in a 3×2 board, then one alphabetical character table. Each role remains visible when vacant and shows its rule, current effect, holders, source and relevant pending actions. Characters has Add character, Show archived, Pending this week with Go to Activity, and columns On roster, Character, Kind, Hit Dice, Officer roles, Teams and Edit. Preserve access to six ability scores and notes through the full record dialog.
- Correct officers enables Assign and holder menus in place. Assign lists roster people grouped PC/NPC with the effect each candidate brings compared with the current effect. Move to… replaces that holder's selected role; Remove removes that assignment; Assign can add another role without removing existing ones. No duplicate character/role pair. Chips in character rows navigate/focus the corresponding role card.
- Correct roster enables only On roster and optional Hit Dice override. Joining uses the record's kind without asking again. Leaving removes that person's officer assignments and clears their team managers in the same correction; warn with the affected role and team names before Save. The record, character conditions, items and historical facts remain. Add character is an immediate record operation, followed by explicit roster inclusion as a separate correction.
- One correction is open locally at a time; dim the other correction section. Both support Save/Cancel, one required reason and editable quick-pick reasons: Story change, Fixing a mistake, New officer joined, Character left. This approved exception to Militia's no-preset-reasons pattern applies only here. Save-point warnings, strategist before/after action allowance and conflict presentation sit above the reason. No per-assignment saves or claims/locks.
- Add/Edit uses one dialog for name, PC/NPC, **Hit Dice**, STR/DEX/CON/INT/WIS/CHA and notes; the existing numeric `level` field remains the record storage. An existing record also offers Archive/Un-archive. Archiving never removes roster membership, roles or manager assignments. Show archived reveals archived rows; occupied role cards always retain archived holders and warnings, even when those rows are hidden.
- Hit Dice displays a plain effective value for everyone. Explicit roster `hitDice` overrides the record's `level`; blank means use `level`, including NPCs whose record number is presented as Hit Dice. Do not add a second character-record Hit Dice field or provenance caption. Preserve zero overrides (`??`, not truthiness), existing integer/nonnegative override validation and record number ≥1.
- Show the counting holder and non-stacking message for redundant holders; commandants total distinct holders' effective Hit Dice. Strategist shows “+1 militia action; that action gets +2”; Overseer shows the secondary-check bonus and one-event support. Derive effects from the shared rules utilities, including the best allowed ability and focus, rather than prototype arithmetic. Show concise advisory warnings for multiple roles, archived assignments and manager over-capacity. Assigning a PC includes the approved Change Officer Role/Go to Activity hint.
- “Manages N of M teams” is read-only and links to this campaign's Militia Teams. Pending Change Officer Role facts come reactively from the open Weekly Draft, display both above the table and on affected cards, and remain distinct from accepted assignments. Changes/removals/Confirmation refresh those facts; never apply pending roles early.
- Phone (<768px): two compact role cards across, Assign picker inline below them, and character cards containing all row operations/facts. The reason bar wraps chips and sits above shell bottom navigation, with scroll padding so it obscures nothing. Tablet Assign uses the approved picker sheet. Desktop (≥1280px): centered 3×2 board over table; Assign uses a floating panel. Keep state when resizing and keyboard/focus/accessible labels throughout.
- Load role-card/table skeletons with accessible status; failures use “Characters could not be loaded.” and Try again while tabs stay usable. Without a militia, character CRUD still works and all six cards show “Set up militia to assign officers.” with a same-campaign Setup path. Retain No active characters/No archived characters states. Respect shell sign-in/unavailable gates and readable maintenance banner; attempted paused writes fail normally with input retained.

Prototype: `prototype-approved/characters-officers` (`c6f90fa`), `/prototype/characters-officers?variant=B`. The behaviours marked "observed" were reproduced in the running prototype on 2026-09-27.

- **Move to… creates duplicate character/role pairs (observed).** The holder menu offers every other role, including roles the holder already has. Moving Bren from Marshal to Commandant lists him twice, and the card then reads "+14 training … (Bren Ironhand 5 HD + Bren Ironhand 5 HD + Dalla Rook 4 HD)". React also logs a duplicate-key error. Prevent duplicate pairs and count each distinct commandant once (§1 "No duplicate character/role pair"; §5 Rules semantics "each distinct holder").
- **Save silently overwrites another player's change (observed).** Open *Correct officers*, trigger "another player makes Kess the Spymaster" from the state panel, then save. The stale draft wins and Spymaster goes back to Vacant. The reducer commits the whole draft roster (`people`, `officers`, `teams`). Officer mode must replace only `roster.officers`, and roster mode only membership and overrides plus cascades. Merge unrelated sections from the latest source, and send any roster-baseline change into the conflict flow (§5 Correction projection, races and reference repair).
- **Conflict flow and wording (observed).** The "another player saves first" toggle is a scripted flag, not a baseline comparison. Its message is "Another player changed the officers while you were editing: Kess is now the Spymaster. Their change is shown; check your edits and save again." It keeps the reason, and a second Save succeeds. Use "Another player changed this section" with theirs/yours and *Start again from their values*/*Cancel*, where restarting clears the reason (§5 Correction projection).
- **Roster-leave warning names nothing (observed).** Switching Sera off the roster only says "Sera of Phaendar leaves the roster and loses all officer roles." The mock reads managed teams from the draft, where they are already cleared. The warning must name the affected roles and teams, as in "Removing Sera clears the manager of Smugglers and Town Watch." (§1 Correct roster bullet; [#114 decision](https://github.com/AndreasUnunger/EverythingPath/issues/114#issuecomment-5844673552)).
- **The table isn't alphabetical (observed).** Rows follow mock insertion order (Aria, Bren, Kess, Tobin, Sera, Grom, Old Mattock, …). The spec requires "one alphabetical character table" (§1 tablet bullet; CHAR-02 name-sorted).
- **Rules arithmetic lives in `mock.ts`.** This covers the `checkRole` ability pairs, "first holder counts" for Strategist/Overseer, `hitDice ?? level` sums that include archived holders, and the `limitOf` manager limit. The strategist preview "5 → 4" and "leaves Activity slot 5 without an action" are hard-coded strings, and the pending "(Activity, slot 3)" comes from mock state. Derive effects, ties, limits and allowance from the shared rules utilities and the open Weekly Draft (§1 "rather than prototype arithmetic"; §5 Rules semantics; §3 "Real … authoritative rules replace mocks").
- **The record dialog has no validation (observed).** It's an uncontrolled `FormData` form with `Number()`. Clearing Hit Dice and saving creates a "0 HD" record and closes the dialog, with no field errors. *Archive* fires immediately and drops unsaved field edits. Use react-hook-form/zod, `noValidate`, field-local messages, record number ≥1 and retained input on failure (§1 Add/Edit and Hit Dice bullets; §5 last paragraph; CHAR-03/04/07).
- **Don't revive the roster-owned-kind scenario.** Setting the state panel to "kind lives on the roster person" enables a per-row PC/NPC select in *Correct roster* (`setPersonKind`), and `join` carries a kind in its payload. Kind is written only in the record dialog, and the roster copy is a mirror resolved from the current record at save (§3 "do not revive … roster-owned-kind scenario"; §5 Compatibility item 3).
- **Stand-ins and missing breakpoints (observed).** `PageFrame` fakes the shell (Week 14 / Finished weeks / Militia tabs, "Saved/Not saved yet"). *Go to Activity* and *Militia → Teams* are inert buttons. The board is a fixed `grid-cols-3` table: at 390 px the page scrolls sideways by 343 px, the reason bar doesn't wrap, and desktop runs full width instead of centered. There are no loading, failed, empty or no-militia states. Integrate the real shell, the §7 routes (`/campaigns/<id>/week?phase=activity`, `/campaigns/<id>/militia`) and responsive-pages variant C (§1 phone/desktop and state bullets; §3).
- **Captions and hint placement.** The Assign sheet's subtext ("People on the militia roster. Adding a role keeps their current one.") is the kind of explanatory caption the approval removed. The Change Officer Role hint appears whenever any PC candidate exists, when it should appear on assigning a PC. The Teams column reads "Manages 1 of 1 teams" (§4 caption approval via [#113](https://github.com/AndreasUnunger/EverythingPath/issues/113#issuecomment-5844235691); §1 "Assigning a PC includes the approved … hint").

### Compatibility and migration

1. Widen live validators/readers before new writers to accept legacy character `pc | officer_npc` (including absent kind), legacy roster `pc | officer_npc | other_npc`, and new `npc`. Normalize explicit legacy NPC kinds to `npc`; missing record kind follows existing PC default. For an existing mismatch the authoritative record wins when populating the roster mirror; never infer kind from held roles. Do not add/drop memberships or assignments during normalization.
2. Migrate live character rows and live roster mirrors in bounded, resumable/idempotent internal batches. Keep authorization/campaign reference checks on public paths; migration cannot be a public bypass. Update source revision when accepted live source changes so stale reviews/corrections cannot overwrite it. Preserve IDs, order, Hit Dice overrides/nulls, archive flags, notes, stats, teams, current week and open draft contents. Missing/foreign records are integrity errors to diagnose, not permission to manufacture records or discard references.
3. Maintain the mirror atomically in every subsequent character write and live source write. The existing `updateCanonicalCharacter` already refreshes canonical facts and roster kind in the same mutation; extend that seam to the normalized kinds. Setup initialization and correction saves resolve each roster person against the campaign's current record kind before accepting the new live snapshot. Never let a stale Setup/correction payload restore the old kind. Keep stale-reviewed-character checks and exact snapshot-character protection.
4. Old clients/old forms may still submit the former enum during rollout: accept/normalize legacy kinds at the compatible boundary, while new UI only writes PC/NPC. Refresh stale clients safely; don't narrow storage/API readers while old supported writes can produce those values. Separate current-write normalization from historical parsing. Old Resolution Records, source corrections and any immutable archived payloads must stay readable without being rewritten; a blanket enum replacement in shared schemas must not make them fail to parse or transform their stored identity/source key.
5. Migrate already-saved **Setup browser envelopes** after the scoped account/organization/campaign has been authorized and current records loaded. Upgrade envelope version, map legacy values and mirror each selected record's current kind while preserving raw invalid numeric strings, other steps, IDs, initialization attempt identity, selected step/mode and explicit HD overrides. Missing records surface field errors; don't erase them or invent kinds. No automatic submission. Continue existing started-militia cleanup and same-ID/same-source retry safety; if initialization is already accepted, show/enter the accepted militia rather than resubmitting a migrated source.
6. Update all live kind readers and affected rules consumers, including Setup inline CRUD/options composition, shared roster forms, Militia Teams manager choices/warnings, Activity details and Change Officer Role checks, phase modifiers, pending-action displays, Week reference/readiness/preview, server Confirmation and test factories/fixtures. Search all `officer_npc`, `other_npc`, `hitDice`, manager-limit and commandant consumers; retain legacy adapters only where compatibility requires them. Historical displays use recorded results, never new calculations over today's records.

An extra endpoint, wire field, new stored exception marker or dropped roster field is outside approval and requires human sign-off; the paths above require none.

### Rules semantics

Use a single role-aware manager-limit utility: PC → max(1, Charisma modifier); NPC with ≥1 held role → the same; NPC with no held role → 1. Recompute using the roster at the point the rules evaluate that action, including relevant prior changes in the Weekly Draft; do not infer Officer from kind or count merely pending roles as already held on this page. Retain existing manager Charisma contribution to team checks and distinct-person counting. Going over the limit during weekly choices uses Activity's existing reasoned Rules Exception mechanism; Militia Corrections use their one correction reason, display the warning and preserve a quiet warning afterwards, with no new marker. Removing an NPC's last role warns with their new limit and managed count. A roster removal clears all that person's managers, not the teams themselves.

Commandant contribution is each distinct holder's `rosterPerson.hitDice ?? character.level`, summed for successful Drill using existing Drill semantics. Remove the old missing-HD readiness requirement and Setup blocker only for this approved fallback; missing character facts remain blocking integrity problems. Explicit overrides survive character level edits, and clearing the override resumes following the current record number. Non-stacking roles, one-event Overseer support and strategist +1/+2 rules remain as before. Rule warnings are advisory; structural/reference errors remain blocking.

### Correction projection, races and reference repair

Use existing `canonicalLedger.save` with a latest complete snapshot, expected revision and trimmed reason (nonempty, max 2,000). No new correction idempotency token or draft edit is introduced.

- At open, capture campaign/militia/week and roster baseline. These modes depend on roster people, officer assignments and team-manager edges, so compare the roster baseline to the latest roster before saving; a remote roster change enters the approved conflict flow rather than overwriting related assignments. Changes only to other snapshot sections are merged from the latest source. Character facts always come from the latest source; refreshed stats recalculate visible effects/warnings, while a kind mirror update counts as a roster change.
- Officer mode replaces only `roster.officers`. Roster mode replaces membership/overrides in `roster.people`, removes officer entries for people actually removed, and clears **only** team manager references to those people using the latest teams. Preserve every other team field and unaffected assignment. Mirror kind from current records, preserve `snapshot.characters` verbatim, and never replace a whole old snapshot/container.
- Conflict shows “Another player changed this section”, theirs/yours and Start again from their values/Cancel; restarting takes the latest baseline, clears the prior reason and requires review again. A revision race refreshes/reconciles; if roster is unchanged keep input/reason and offer retry against a rebuilt latest candidate, otherwise conflict. A week change restarts from new-week facts. Delayed work cannot target a newly selected campaign/organization.
- Named pre-save warnings include removed roles/managers, lowered capacity/strategist allowance, affected selections/required officer choices and existing/new draft-reference problems. Reuse Militia corrections' helper with candidate snapshot as both source arguments; don't claim roster removal deletes the character record or always creates an orphan. Pending Change Officer Role or an Overseer selection can become semantically invalid even while its character still exists. Link the affected Activity slot/phase using existing local focus behavior.
- Corrections may save with advisory open-week warnings. Recompute on all devices afterward. Whole-draft missing-reference checks still reject edits whose complete result remains invalid; no silently clearing staged actions, multi-edit API or relaxed server checks. A single existing edit can repair only when its whole candidate is valid. Otherwise use the predecessor's identity-preserving restoration flow. Here a removed roster person can be re-included from its existing character record through a new reasoned roster correction, followed by an officer correction if needed; then repair weekly choices normally. Missing/foreign character records cannot be fabricated via source restoration, and archive/un-archive retains identity.
