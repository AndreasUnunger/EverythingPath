# CI failure and flake policy: primary-source findings

Scope: official Playwright and GitHub documentation, reviewed 2026-08-27. The sources define the enforcement and evidence mechanics; ownership, triage SLOs, and quarantine expiry are local policy choices rather than vendor-prescribed thresholds.

## Retries must diagnose flakes, not turn them green

- Playwright retries are off by default. With retries enabled, a first-attempt pass is `passed`, an initial failure followed by a passing retry is `flaky`, and failure on every attempt is `failed`. After a failure Playwright discards the entire worker process and browser, then retries in a new worker; hooks run again. Serial groups retry together, whereas isolated tests retry independently. This supports one diagnostic retry only when reset/setup is repeatable and tests are isolated. [Playwright retries](https://playwright.dev/docs/test-retries)
- `failOnFlakyTests: true` (or `--fail-on-flaky-tests`) makes Playwright exit with an error when any test is classified flaky; Playwright calls this useful on CI. It was added in Playwright 1.52. This is the key control that lets a retry collect evidence without silently satisfying the gate. [Playwright `failOnFlakyTests`](https://playwright.dev/docs/api/class-testconfig#test-config-fail-on-flaky-tests)
- `forbidOnly: true` makes CI error if `test.only` or `test.describe.only` was committed. `globalTimeout` bounds the complete Playwright run and is explicitly intended to prevent broken CI setup from running indefinitely. [`forbidOnly` and `globalTimeout`](https://playwright.dev/docs/api/class-testconfig)
- `test.skip` and `test.fixme` do not execute the test and are reported as skipped. Tags plus `grep`/`grepInvert` can separate a quarantine lane, and annotations can carry an issue URL into the report. These are mechanisms, not safeguards: the policy must separately assert that every required journey actually ran. [Playwright annotations and tags](https://playwright.dev/docs/test-annotations)

## Failure evidence and reports

- Playwright recommends Trace Viewer over video/screenshots for CI diagnosis because traces expose the action timeline, DOM snapshots, network activity, console, source, and errors. Its documented CI default is `trace: 'on-first-retry'`; `trace: 'on'` for every test is discouraged as performance-heavy. If the initial failed attempt itself must be replayable, `retain-on-failure-and-retries` keeps failed attempts and retries, while `on-first-retry` keeps only the first retry. [Debugging on CI](https://playwright.dev/docs/best-practices#debugging-on-ci) · [trace retention modes](https://playwright.dev/docs/test-use-options#trace-modes)
- `screenshot: 'only-on-failure'` captures each failed attempt. Trace and video both support failure/retry retention modes and normally write into `test-results`; Playwright recommends traces as the primary CI evidence, so video can remain off unless traces prove insufficient. [Recording options](https://playwright.dev/docs/test-use-options#recording-options)
- Multiple reporters can run together. The HTML report is filterable by passed, failed, flaky, and skipped tests; the `github` reporter adds Actions annotations, but Playwright advises against it for matrix jobs because duplicate stack traces obscure the file view. Use a concise console reporter plus HTML everywhere, and reserve `github` annotations for the non-matrix PR job if desired. [Playwright reporters](https://playwright.dev/docs/test-reporters)
- Playwright's official GitHub Actions example uploads `playwright-report/` with `if: ${{ !cancelled() }}` and 30-day retention. Its guidance says uploaded reports/traces must go only to trusted artifact stores or be encrypted. Authentication state and secrets therefore must be excluded even when diagnostic artifacts are retained. [Playwright GitHub Actions example and artifact security](https://playwright.dev/docs/ci-intro#setting-up-github-actions)
- GitHub job summaries support Markdown through `GITHUB_STEP_SUMMARY` and are displayed on the workflow-run summary page, specifically so important test failures need not be found by digging through logs. A compact summary can name failed/flaky/skipped journeys and point to the report artifact. [GitHub job summaries](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands#adding-a-job-summary)

## Artifact retention and timeout behavior

- GitHub retains Actions artifacts and logs for 90 days by default. Organization settings allow 1–90 days for public repositories and 1–400 days for private repositories, subject to any managing organization/enterprise cap. `upload-artifact` can set a shorter per-artifact `retention-days`, but cannot exceed the configured cap. [GitHub retention settings](https://docs.github.com/en/organizations/managing-organization-settings/configuring-the-retention-period-for-github-actions-artifacts-and-logs-in-your-organization) · [per-artifact retention](https://docs.github.com/en/actions/tutorials/store-and-share-data#configuring-a-custom-artifact-retention-period)
- The official `upload-artifact` action defaults missing paths to a warning; `if-no-files-found: error` is available. For a run expected to produce a Playwright report, failing on a missing report prevents an evidence-free failure from being mistaken for a complete diagnostic result. [Official `upload-artifact` inputs](https://github.com/actions/upload-artifact#inputs)
- GitHub automatically cancels a job at `jobs.<job_id>.timeout-minutes`; cancellation interrupts running processes and unfinished steps are conditionally re-evaluated. Because Playwright's upload example deliberately excludes cancelled runs, a hard 15-minute job timeout is not by itself artifact-preserving. The actionable design is to place a shorter controlled Playwright/test-step timeout inside that outer limit, leaving time for report finalization and upload. [GitHub job timeout](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idtimeout-minutes) · [cancellation behavior](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-cancellation)

## Required-check behavior that can silently weaken a gate

- GitHub required checks must pass before merge, but `success`, `skipped`, and `neutral` all satisfy the requirement. A conditionally skipped job reports success. A dependent job can also be skipped after an upstream failure and may not block merging; GitHub recommends `always()` for required checks that depend on other jobs. Required checks must pass on the latest commit SHA. [GitHub required-check troubleshooting](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)
- A step with `continue-on-error: true` has an underlying `outcome` of `failure` but a final `conclusion` of `success`. It is therefore unsuitable for the required E2E result or for a nightly quarantine lane that must remain visibly red. [GitHub steps context](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#steps-context)
- Required job names should be unique across workflows to avoid ambiguous results. Branch protection can also bind a required check to the expected GitHub App. A stable, uniquely named aggregate E2E gate should explicitly fail unless every required matrix/dependency result is `success`; it should not accept skipped, neutral, cancelled, or tolerated failures merely because GitHub would. [GitHub protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)
- A merge queue requires the workflow to listen to `merge_group` in addition to `pull_request`; otherwise the required check is never reported for the queue entry. [GitHub merge-queue checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks#status-checks-with-github-actions-and-a-merge-queue)

## Actionable baseline supported by these mechanics

1. Use one CI-only retry, `failOnFlakyTests: true`, and `forbidOnly: true`. A retry is diagnostic evidence; both `flaky` and `failed` remain red.
2. Reset server state before every initial attempt and retry, because Playwright replaces the failed worker/browser and reruns hooks.
3. Start with `trace: 'on-first-retry'`, `screenshot: 'only-on-failure'`, and video off. Escalate to `retain-on-failure-and-retries` if investigations need failed-attempt and retry traces side by side.
4. Publish a console result, HTML report, safe setup/service logs, and a small job summary on every non-cancelled run. Exclude auth-state files, secrets, and sensitive hidden files. Use a controlled inner timeout below the 15-minute job timeout so uploads can run.
5. Require one stable aggregate PR/merge-queue check. It must reject flaky, failed, cancelled, neutral, and skipped required journeys and must never use `continue-on-error`.
6. Do not quarantine tests or commit `test.skip`, `test.fixme`, or equivalent exclusions. Keep gate and nightly membership explicit, and fail if any test assigned to a suite does not execute.
7. Set an explicit artifact retention window rather than inheriting 90 days accidentally. Playwright's example uses 30 days; that is a documented starting point, while any shorter PR/nightly split is a local cost-versus-triage decision.
