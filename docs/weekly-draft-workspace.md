# Weekly Draft Workspace and Upkeep

Issue [#81](https://github.com/AndreasUnunger/EverythingPath/issues/81) introduces the feature seam specified by [#34](https://github.com/AndreasUnunger/EverythingPath/issues/34). `useWeeklyDraftWorkspace` returns `unavailable`, `loading`, `failed`, or `ready`. Only `ready` exposes its discriminated Phase View and the semantic `edit`, `viewPhase`, and `confirm` families. It exposes domain choices, values, requirements and affordances without the synchronized draft, revision, query assembly, flushing, DOM references, or field setters.

The private Workspace store owns phase selection, optimistic projection, accepted-preview matching, save feedback, recovery, and successor observation. Each player chooses a phase independently, including while an edit is pending. A failed edit removes its forecast and restores the latest accepted values using the standard failed-save feedback. Persistent Phase availability comes from fixed week-start eligibility. A relevant source change refreshes the accepted preview; whole-week Confirmation delegates the exact-review barrier to persistence. The source subscription discovers the new empty draft after Confirmation.

The browser boundary uses the application's authenticated Convex client. `/canonical-workspace?campaign=…` is reachable only as an isolated feature surface: its backend source and write queries require the configured owned preview campaign and independent campaign membership. Unsupported campaigns receive unavailable state. The existing live board and its behavior remain unchanged; this is not a cutover or a dual write.

Upkeep presents calculated rank, training, treasury, minimum funds, check bonuses, modifier explanations and required dice. It supports missing-team return rolls, disabled-team decisions, nearest-settlement choice, staged copper transfers, rank-boon acknowledgements and reasoned Rules Exceptions. Its focused semantic roll, settlement, team and transfer edits preserve other inputs and use the same server-derived conflict checks as the existing whole-Upkeep operation. Upkeep settlement, team, officer and transfer-direction choices use selectable cards with tap/keyboard activation and pointer placement into a highlighted selection area. Invalid or cancelled drops return the card with visible feedback and preserve the prior choice. Pointer capture, geometry and click suppression stay in a browser-only adapter, outside the Workspace. Recovery costs prefill the rules baseline; a changed amount requires a reason and atomically stages a typed treasury adjustment with the team decision. The adjustment applies after the entire weekly baseline, and choosing leave or remove clears it. Summary displays both differing treasury outcomes. Advisory warnings name the affected choice and explain the departure. Activity action cards now consume their own Workspace Phase View under #82; Event, Persistent and Summary remain subsequent migration increments.

Browser forms use React Hook Form, Zod and the existing shadcn controls. Whole-number entry accepts ASCII digits or blank, retains the previous value on invalid input, preserves zero, and emits an explicit clear. Dice remain raw; calculated totals are displayed separately. Multi-die rolls are entered in order, and clearing an earlier die explicitly clears the remaining dice in that roll. Required, format and range feedback have different meanings: missing input remains a partial draft, malformed text is rejected, and out-of-range numeric dice remain entered with an advisory warning. A browser `beforeunload` handler warns only while semantic edits or Confirmation are pending; it does not block local phase navigation.

Workspace tests observe hook states, Phase Views and semantic outcomes through the public seam. They verify loading/unavailable/failure recovery, deterministic Upkeep facts, independent navigation, latest-value restoration after a real in-memory conflict, and fixed persistent eligibility. Input tests cover invalid entry, zero, clear and styled field errors. Backend integration covers the gated source, member authority and successor discovery. The shared adapter suite now includes focused Upkeep stale/disjoint operations and zero/clear, exercised in memory and the actual preview.

The required browser matrix includes a separate two-player canonical Workspace journey in addition to the supported legacy journeys and persistence contracts. QA holds a real mutation WebSocket frame while preserving query traffic, checks visible pending state, changes phase, dismisses a real page-exit warning, accepts another player's competing edit, then releases the original stale request and checks recovery. It also checks keyboard/paste entry, transfers, Summary readiness, ordinary-player Confirmation, both players reaching the successor, and tablet/phone/desktop screenshots. Missing or retried Workspace results fail the gate.

Final verification: 867 tests across 88 files, typecheck and lint pass. The rules catalog records 380 covered cases, 290 explicit gaps and zero errors. Standards and Spec re-reviews passed the application changes at `7fb3826`. Independent QA found no outstanding issues.

## Activity Workspace (#82)

Activity consumes complete typed choice facts directly from Workspace. The isolated board offers deck-to-empty staging, deck-to-occupied replacement, whole-choice movement and swapping, and clearing by dragging a staged card outside the slots. Keyboard/tap users select a card and a destination; occupied destinations distinguish replacement from swapping. Pointer capture, geometry, hover feedback, cancellation and a floating card preview remain browser concerns. There are no claims or individual confirmations on this path.

Stable choices carry their teams, raw rolls, action-specific details, copper amounts and acknowledgements together. Occupied extra slots remain visible with move/clear guidance and shared reasoned exceptions. Cards show translated rules warnings, modifier explanations and calculated costs where projection has enough facts. The cost input preserves the recorded choice amount; a differing amount is explicitly identified as separate from the rules-calculated treasury outcome.

Action-discriminated schemas drive structural validation without a second stored shape. Scalar and structured input adapters support partial choices, arrays, objects, nested event trees and discriminated destinations/decisions. Entity identities are generated at creation; reference lists offer named cards. Candidate persistent decisions bind to their owning candidate. Replacing an action creates a fresh choice, while moves and swaps preserve the entire original choice. Failed cross-field validation appears within the edited field; a failed clear preserves the current editor contents. Copper inputs preserve zero and explicit clear and reject malformed typing/paste. Weight accepts decimal entry; signed nested numeric values can be entered without pasting an entire value.

The two-player Workspace journey now checks team, subject, dice and cost retention through movement and swapping; deck replacement and outside clearing; occupied extra slots and a shared reasoned exception; and stale same-target rejection, independent navigation and a successful retry. - Receipt day and narrative notes form one complete choice edit; receipt and acknowledgement share an identity, and the acknowledgement subject is the order.

### Rules-ordered Event preparation (#163)

Event now shows numbered steps in rules order: Event chance, Automatic events, The event or Event candidates, and Week outcome. The manual Add rolled event, Add automatic event, Add Roll Twice child, Add replacement event, Remove Event and Select this Activity event controls are retired.

- **Positions come from the engine.** Event selection records a trace of the occurrence positions the rules ask for (`EventSelectionProjection.positions`). It traces the chance-triggered root, each due automatic source's count, two candidates per guaranteeing choice, the first normal Roll Twice's two children, and one replacement for an event that cannot occur. A `reroll` replacement group marks a later Roll Twice, which is rerolled in its own die and never prepared. Recording the trace does not change Weekly Resolution, and no Ruleset Version is allocated. Since #191 (below) a candidate's Roll Twice is also a `reroll` group.
- **Preparation is fill-only.** `planEventTopology` in `src/lib/event-occurrence-preparation.ts` adds only missing blank positions. The main tree uses the existing `event_tree` edit; candidates use the owner's complete `detail` edit. Identities are derived from the draft, owner or source, parent and ordinal. For example, the rolled root is `<draftId>:rolled:1`, a Roll Twice child is `<parent>/twice/1` and a replacement is `<parent>/replacement/1`. Children use `/` so that no child identity starts with its parent's `id:` requirement or check prefix. A collision gets a deterministic `~n` suffix. Recorded occurrences, their order and legacy surplus positions are never rewritten. Clearing the table roll of an otherwise empty surplus position removes it through the same existing edits.
- **The store prepares, not the view.** `createWorkspace` prepares from the accepted draft whenever nothing else is in flight, whichever phase is shown, so every device converges on the same identities. A rejected attempt is recomputed from the refreshed observation and sent as a fresh operation. After three attempts at the same intent, the workspace shows ordinary failure feedback and offers `eventPreparation.retry`.
- **No child edit before acceptance.** Until the accepted draft holds an occurrence, its block is a stable blank placeholder with `saved: false`. Its inputs are disabled, and `useEventEdits` refuses occurrence edits for it.

Later Event tickets replace parts of `EventOccurrenceEditors` inside `EventBlock`. The block owns identity, the table roll with `+ Table modifier`, status, the candidate choice and nesting. It also passes `disabled` for unsaved occurrences, so family panels inherit the acceptance gate. Blocks carry display-only hierarchical labels (`EventBlock.label`), never identities. Active top-level events are numbered in resolution order: automatic, rolled, then one number per candidate set, with its candidates lettered (Event 2A, Event 2B). Events not taking part this week are numbered after them. Nested events extend their parent's label by their position among all recorded siblings (Event 1.1, Event 2A.1, Event 1.1.1), so preparing, hiding or restoring children never relabels another event. The one exception is removing an empty surplus legacy position by clearing it, which can move its later siblings up one place. Activity's event options use the same labels. Requirement wording names the event, candidate choice or source through `EventView.messages`, and This phase shows the same wording. Rules text for every event type lives in `src/lib/event-rules-text.ts`, copied verbatim from the `## Event:` sections of `militia-rules.md`. Two sentences that file omits are copied word for word from `militia-verbatim.md`: Roll Twice's second-roll rule and Cache Discovered's no-cache Twice case. `event-rules-text.test.ts` parses both sources through an explicit per-entry mapping and fails on drift. A block exposes it as `rules`, with the Twice clause only when that clause applies to it.

### Candidate Roll Twice rerolled in place (#191)

Issue [#191](https://github.com/AndreasUnunger/EverythingPath/issues/191) (spec [#143](https://github.com/AndreasUnunger/EverythingPath/issues/143), approved in [#108](https://github.com/AndreasUnunger/EverythingPath/issues/108#issuecomment-5837858373)) applies the approved rule that a candidate which rolls Roll Twice is rerolled in place. It changes Weekly Resolution, so `CANONICAL_WEEKLY_RULESET_VERSION` is now `CANDIDATE_REROLL_RULESET_VERSION`, the version after `CHARACTERLESS_TRANSFERS_RULESET_VERSION` (7). Earlier records keep their version and their recorded expansion; they are never re-resolved.

- **Engine.** In `rules-event-selection.ts` only the chance-rolled tree can expand a Roll Twice. Every event in an Activity candidate set rerolls one in its own die, as automatic events already did. That covers the chosen candidate, the other candidate, their replacements for an event that cannot occur, and replacements found while outcomes fold (`rules-event-outcomes.ts`). Each such roll traces a `reroll` replacement group and requires `<eventId>:replacement:1` until the die changes. It spends no expansion and prepares no position. A replacement child recorded by an older client is still read as that reroll. An eligibility Rules Exception keeps an event that cannot occur, but never keeps a Roll Twice. The corpus notes this departure under Guarantee Event and Manipulate Events. The `Event: Roll Twice` text itself is unchanged.
- **Legacy expansion children.** Roll Twice children already inside a candidate set (`isLegacyCandidateExpansion` in `event-occurrence-preparation.ts`) keep their data and identities and are never rewritten on read. They take no part in resolution or readiness and count as surplus positions. In the block they sit in their own disclosure (`EventBlock.legacy`, status `legacy`, "No longer used"), apart from `hidden` children that come back when the roll does. Clearing the roll of an otherwise empty one removes it through the candidate's own `detail` edit. One with other recorded inputs stays until those are cleared too.
- **Blocks.** A candidate that rolls Roll Twice shows **Reroll** with "Roll Twice again: reroll and enter the new die", whether chosen or not, and has no children. This phase names the event, for example "Event 2A · Roll Twice: Roll Twice again: reroll and enter the new die."
- **Evidence.** `candidate-roll-twice.test.ts` holds the before/after regression and the representation-equivalence check. Its representation check shows that a reroll recorded as an older replacement child resolves exactly like the same die entered in place. It also covers the version, the unchosen candidate, ineligible replacement chains, Rules Exceptions and the replacement found while outcomes fold. `canonicalResolutionPreview.integration.test.ts` (`rules.A10.reroll-parity`) proves that browser preview and Convex Confirmation agree. `record-review.test.ts` (`rules.HIST-05.candidate-expansion`) shows that an earlier record keeps its expansion and outcomes. No browser journey covers candidates yet. The Activity and Event journey has no Guarantee Event path, and adding one would add many steps to a journey that is already near its time limit.

### Team and person target events (#164)

Missing in Action, Sickness, Turn Around and Raid have their own controls in place of the general details editor's inputs. `EventOccurrenceFacts.panel` carries them, built by `eventPanel` in `event-target-facts.ts`; other families keep `panel: null` and the existing editor until their tickets ship. The general **Edit … details** disclosure stays below every block, so Sabotage, occurrence-level Overseer support and any retained legacy field remain editable.

- **Targets.** Team and settlement targets are cards (`EventTargetCards`) that replace the target of that kind and keep other targets. Teams come from the Activity outcome's roster, marked when they acted this week. A Twice occurrence names the first occurrence's team. Raid offers settlements with an active refuge after Activity, plus a recorded settlement without one (its eligibility exception stays available). A recorded target that is no longer on the roster or in the campaign, or a surplus recorded target, stays visible with a reason and its own Clear.
- **Checks.** `EventCheckRow` (`event-check-row.tsx`) with `eventCheckFacts` (`event-check-facts.ts`) is the shared Event check row: dice total, calculated bonus, total versus DC, a named breakdown ("Rank and focus +2 · Officers +1 · Overseer +3"), a worded result, and a `support` slot for the shared Overseer toggle. A check-level Overseer selection from an older editor reads as its event's support in the shared toggle (#166); only an unattempted Raid person, which shows no check row, keeps a note with Remove. Sickness Twice's Loyalty DC 20 save is mandatory and has no Attempt it / Let it happen. The DCs and capture chances come from `SICKNESS_TWICE_LOYALTY_DC`, `RAID_SECURITY_DC` and `RAID_CAPTURE_CHANCE` in `rules-threat-events.ts`, which the engine also uses.
- **Raid per person.** Each person hidden in the raided refuge has their own Attempt it / Let it happen, Security check and capture percentile, recorded on their `targetChecks` entry. The capture roll is asked for only after a successful check. An event-level mitigation or check die from an older editor still stands in for each person until their own choice is recorded, and can be cleared. A recorded check for someone not hidden there stays visible until removed.
- **What happened and outcomes.** What happened saves and clears the `event:<id>` acknowledgement. It is marked required exactly when the engine asks for it or uses it. Outcome lines name teams and people, queued absences and returns, lost refuges, capture rolls and the next week's Rescue Character DC.
- **Wording.** Requirements for these families name the event and the team, settlement or person through `EventView.messages`. The engine reports a missing check die both as its dice and as the check's absent roll; `EventView.requirements` keeps only the dice code, so This phase lists one line per missing entry. The same rule (`roll-requirements.ts`) applies to Activity checks (`<choice>:check:1d20` with `<choice>:roll`) and Persistent mitigation checks, and Phase Readiness applies it to every step's list and to Review & confirm's count of decisions left.

### Sabotage and shared Overseer support (#166)

- **Sabotage** (`event-sabotage-facts.ts`, `event-sabotage.tsx`, `sabotage-edits.ts`). `EventView.sabotage` holds one entry per occurrence, keyed by event identity. A happening event that is not a calm week, in a militia with a Saboteurs team, shows a quiet _Sabotage this event_ button. The button only opens the reaction on this device. The first team choice records `occurrence.sabotage` under the stable identity `sabotage-<eventId>`, so two devices starting it write the same reaction. The team cards, check kind, d20 check row (DC `15 + rank`), notoriety d6, result and What happened (subject `sabotage:<event>:<choice>`) all read the engine's projection. The notoriety is added on success and failure alike, and success negates only that occurrence. A team that needs a Rules Exception reads as unavailable: nothing is rolled, spent or negated until the exception has a reason. A negated event asks for none of its own inputs. A reaction on an event that no longer happens stays visible as kept on record. _Cancel Sabotage_ clears its note, then the reaction, as two ordinary edits.
- **Overseer support** (`src/lib/overseer-support.ts`). One event a week, shared by Event and Persistent. Each event's selections read as one holder, whether they are recorded on the occurrence, a target check, the Sabotage reaction, a same-week persistent decision or a carried event's mitigation decision. `moveOverseerSupport({ to, characterId, latest, send })` is the ordered support-move service. It clears every other holder one edit at a time, then records support on `to` (the occurrence's own `overseerCharacterId`, or the carried decision's). Every step is planned from `latest()`, and the first refused edit stops the move and reports its stage. The move is not atomic. The rules still apply support to the first event only, so an interleaved double record is flagged, never counted twice. `OverseerSupportProvider` / `OverseerSupportControl` put the toggle ("Use Overseer support · +3 · one event a week", with no name or ability) in the Sickness, Raid and Sabotage check rows and in the Persistent Theft check. The board passes `latestOverseer` from the store so each step sees the newest facts. The Persistent Theft form no longer edits `overseerCharacterId` itself, and saving the form keeps the recorded support.

## Persistent Workspace (#84)

Persistent now consumes its own Workspace Phase View. Carried events remain visible in their recorded age/order with named per-instance targets, including after a staged ending. The week-start eligibility flag still governs navigation; current-week creation or ending cannot add or remove the phase. The isolated board's Persistent placeholder is removed, while the supported live board remains unchanged pending cutover.

Players can leave each event unattempted, stage its applicable mitigation, record a reasoned ending, or stage a buyoff.
