# Character access and Militia Character Facts inventory (#252)

This is the preparation inventory for [PRD #251](https://github.com/AndreasUnunger/EverythingPath/issues/251), surveyed on 2026-10-02. It records the current flat Character consumers left in place by #252 and the implementation tickets that replace or extend them. It does not activate production Character Sheets or private Characters, a new Ruleset Version or a migration. The [legacy compatibility inventory, B6](legacy-compatibility-inventory.md#b6-planned-character-sheet-release-cleanup-240) tracks the eventual storage retirement.

## Current contract and prepared seams

The persisted `character` identity stays in place. Since #260, `campaignId` and `ownerId` are optional: ordinary private Characters require a surviving owner, while ownerless campaign and inaccessible recovery records are retained lifecycle states. Legacy `level` and the six ability scores remain authoritative flat columns for militia consumers. Existing public Character mutations still accept legacy `officer_npc` and normalize it to `npc`; Setup and Militia Correction roster submissions additionally accept and normalize `other_npc`. Archiving sets `isActive` and leaves roster membership, officer roles and team management intact. Ordinary record edits refresh the current canonical militia snapshot, retaining roster Hit Dice overrides, including zero. Resolution Records keep their frozen copies.

- `convex/lib/characterAccess.ts` exposes `listAccessibleCharacters`, `requireCharacterCampaignAccess`, `requireCharacterAccess` and the campaign-only legacy writer guard `requireCampaignCharacterAccess`. Since [#260](https://github.com/AndreasUnunger/EverythingPath/issues/260), `hasAccessToOrg` requires persisted organization membership; the token-substring fallback is retired for every caller. Private access requires the current authenticated owner and a surviving user record; an asserted campaign must match the Character. `convex/lib/canonicalDraftStorage.ts` retains `requireOrganizationMembership` for canonical scope and Militia Setup. Legacy commands remain campaign-scoped, campaign deletion is refused in favor of archiving, and private deletion goes through the sheet command.
- `convex/lib/militiaCharacterFacts.ts` exposes `calculateMilitiaCharacterFacts`, consumed by `updateCanonicalCharacter` in `convex/lib/canonicalCharacters.ts`. It projects `characterId`, `level`, `strength`, `dexterity`, `constitution`, `intelligence`, `wisdom`, `charisma` and `isActive` from the existing record. Name and kind remain separate; kind still follows the record into the roster. This is the flat-record adapter, not a sheet resolver or a stored actual-Hit-Dice field.
- Refresh timing is unchanged: once canonical militia state exists, the existing refresh increments its revision even for a notes-only edit. Changed-facts-only invalidation, shared Setup calculation and sheet authority belong to later tickets. Creating a record does not put it on the roster.

The [data model](pf-character-sheet-data-model.md), [ADR 0001](adr/0001-one-character-identity.md) and [ADR 0002](adr/0002-characters-owned-by-users-move-between-campaigns.md) describe the target sheet and lifecycle contracts. The prepared seams retain flat-field militia authority; ownership transfer, campaign movement and external lifecycle processing remain later work.

## Staged Character Sheet interfaces (#256)

`convex/characterSheet.ts` adds create/read, base-score edits and Class Level add/edit/move/delete commands on the existing Character identity. Its additive `catalogEntry` and `characterSheetEntry` tables store six base Modifiers and ordered Unspecified Class Levels with stable row IDs and plain, nullable HP inputs. The base entry cannot be disabled or removed, and zero Class Levels are allowed. `src/lib/character-sheet.ts` provides the shared pure calculation interface. The public read returns calculated totals, which the client consumes directly.

Campaign sheet writes require a fixture campaign. Since #260, private creation instead requires the server-seeded `user.characterSheetDemo` marker, and private writes require `character.sheetDemo`; no public command enables either marker. Both creation paths work without a militia. Reads and writes use the shared Character access seam, deriving identity and campaign membership on the server; optional organization/campaign arguments assert the caller's route scope. Catalog Entries are checked against the owning Character, and Class Level commands only accept rows on that Character's sheet. New sheets retain compatibility flat fields; subsequent sheet edits do not update those fields or the canonical militia snapshot. `calculateMilitiaCharacterFacts`, Setup and ordinary ledger writes retain legacy authority pending the explicit release cutover. Every new writer uses the initial migration Write Gate.

The `characterSheet` harness case creates `E2E character-sheet-campaign` and `E2E character-sheet-character`, with scores of 10 and one Unspecified Class Level with empty HP. It uses the existing preview-only fixture authorization. `inspectCase` includes `characterIds` for that case; the public sheet read supplies Character Sheet Entry and Catalog Entry IDs. Bounded reset/cleanup removes owned sheet entries and character-scoped Catalog Entries, including sheets created through public commands during the test. `convex/e2eFixtures.test.ts` proves member/owner public reads, outsider refusal, retry cleanup and preservation of a comparison case. The living-sheet UI and two-session browser scenario are implemented, but browser execution remains unverified; no production activation or backfill is performed by this preparation.

`characterSheet.archive` and `characterSheet.deletePrivate` both require an already prepared sheet through `loadWritableSheet`. Archiving additionally requires a fixture campaign; private deletion instead requires the private Character's `sheetDemo` marker and refuses campaign Characters. Legacy campaign Characters without prepared sheets remain on `character.archiveCharacter`, which does not require sheet preparation. Both archive entry points preserve the existing canonical militia refresh behavior.

### Modifier and personal adjustment preparation (#263)

`characterSheet:createPersonalAdjustment`, `editPersonalAdjustment` and `removePersonalAdjustment` extend the same fixture-only sheet API and Write Gate. Each adjustment owns a Character-scoped `manual` Catalog Entry and a Sheet Entry; edits retain its durable rule identity, and removal deletes both. The sheet loader validates every adjustment definition against the owning Character before returning it or resolving its Modifiers. Newly introduced condition references must belong to that Character. A saved reference whose target was removed stays conditional and does not prevent editing the remaining adjustment. Activation changes patch only the active flag, preserving concurrent content edits. This schema widening requires no existing-row backfill.

The shared calculation interface expands closed parent targets, resolves numeric bonus/penalty stacking and effective Sources, and reports applied, suppressed and conditional contributions. The sheet controller exposes the calculated breakdowns and adjustment commands. Editable base scores come from the base Catalog Entry, so an adjustment never becomes part of the saved base score. Formula evaluation, ability damage/drain and permanent projections remain #298's scope. Presentation of breakdowns and the adjustment editor is handed to the separate UI agent through `/tmp/ep-orch/briefs/263/ui-contract.md`; #263's implementation brief assigns that markup and browser interaction evidence separately.

## Characters navigation (#297)

`characterSheetPath` now builds `/characters/<id>` for every Character. Its optional origin records a recognized app page and source organization; an explicit personal origin restores the personal account on Back. The former `/campaigns/<campaignId>/characters/<characterId>` route redirects to that independent URL with a Characters & officers origin. The militia ledger lives at `/campaigns/<campaignId>/officers`; `/campaigns/<campaignId>/characters` lists the campaign's accessible Characters.

The Characters area lists owned accessible Characters through `character.listOwned`, grouped No campaign first, then campaign/organization. `character.listCampaignCharacters` supplies owner and roster information, including archived Characters. `campaign.getNavigationContexts` supplies lightweight militia existence and open-week information independently of initialization. All campaign reads remain membership-scoped; a Character's owner grants no campaign access by itself.

The shell uses a shared navigation model and session-persisted per-organization last campaign and per-campaign last militia page. Independent sheets derive their campaign from the authorized sheet response and select its organization once on opening. Origin shell context and Back survive manual organization changes; the picker continues to list the active organization's campaigns. Back waits for in-flight automatic activation, restores its source organization, then navigates through the departure guard. Failed automatic changes offer retry without losing the origin.

Prepared personal and campaign creation open a Full sheet. Movement and Add from my characters remain in #316. Existing Write Gate and isolated-fixture eligibility are unchanged; this navigation slice does not activate production sheets.

Public seams are covered by `campaign-routes.test.ts`, `app-navigation.test.ts`, `use-app-navigation.test.ts`, `use-character-sheet-navigation.test.ts`, the Character list/controller tests, shell/route presentation tests and `convex/characterNavigation.integration.test.ts`. The `characterNavigation` browser journey is registered in the browser matrix; running it remains an orchestrator check outside the sandbox.
