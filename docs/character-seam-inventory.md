# Character access and Militia Character Facts inventory (#252, #256, #260, #261, #262)

This is the preparation inventory for [PRD #251](https://github.com/AndreasUnunger/EverythingPath/issues/251), updated on 2026-10-03. It records the prepared sheet interfaces, retained production flat Character consumers and implementation tickets that replace or extend them. It does not activate production Character Sheets or private Characters, a new Ruleset Version or a migration. The [legacy compatibility inventory, B6](legacy-compatibility-inventory.md#b6-planned-character-sheet-release-cleanup-240) tracks the eventual storage retirement.

## Current contract and prepared seams

The persisted `character` identity stays in place. Since #260, `campaignId` and `ownerId` are optional: ordinary private Characters require a surviving owner, while ownerless campaign and inaccessible recovery records are retained lifecycle states; `level` and the six ability scores retain flat authority in ordinary campaigns. Only initialized sheets in fixture campaigns supply calculated facts; `sheetMode` alone never activates candidate data. Existing public Character mutations still accept legacy `officer_npc` and normalize it to `npc`; Setup and Militia Correction roster submissions additionally accept and normalize `other_npc`. Archiving sets `isActive` and leaves roster membership, officer roles and team management intact. Ordinary record edits refresh the current canonical militia snapshot, retaining roster Hit Dice overrides, including zero. Resolution Records keep their frozen copies.

- `convex/lib/characterAccess.ts` exposes `listAccessibleCharacters`, `requireCharacterCampaignAccess`, `requireCharacterAccess` and the campaign-only legacy writer guard `requireCampaignCharacterAccess`. Since [#260](https://github.com/AndreasUnunger/EverythingPath/issues/260), `hasAccessToOrg` requires persisted organization membership; the token-substring fallback is retired for every caller. Private access requires the current authenticated owner and a surviving user record; an asserted campaign must match the Character. `convex/lib/canonicalDraftStorage.ts` retains `requireOrganizationMembership` for canonical scope and Militia Setup. Legacy commands remain campaign-scoped, campaign deletion is refused in favor of archiving, and private deletion goes through the sheet command.
- `convex/lib/militiaCharacterFacts.ts` exposes asynchronous `calculateMilitiaCharacterFacts(ctx, character, preparedSheet)`, consumed by canonical refresh and both Setup options and review checks. `convex/lib/preparedCharacterSheet.ts` owns bounded sheet/definition loading and the shared pure calculation. Prepared ledger reads use that same calculation and verify every referenced definition belongs to the Character. The optional third argument has explicit authority semantics: `undefined` loads eligible prepared data, while `null` keeps legacy flat authority; an already-loaded sheet avoids duplicate reads. All currently supported base, Class Level and personal adjustment inputs are permanent, so ordinary sheet totals and ordinary permanent totals agree. When #298 lands, this async facts helper selects `calculateCharacterSheetProjections(input).permanent` from those same authorized inputs; Setup, refresh and Confirmation keep calling this single seam rather than introducing another facts calculation. Temporary Effects, including linked contributions, must be excluded transitively by that projection, and a viewed Combined Form must never select militia facts. Facts remain `characterId`, `level`, six scores and `isActive`, with optional fixed `racialHitDice` prepared in #312; name and kind stay separate. Zero racial counts keep the existing facts shape and source revision. The rules compute total Hit Dice from Class Levels and racial inputs, preserving the roster override including zero, rather than storing a derived total. Frozen snapshots without racial inputs retain zero racial Hit Dice. Version 10 is reserved for computed Hit Dice, while version 9 and legacy Character authority remain active until initial cutover. Companion-specific inputs remain later work.
- `updateCanonicalCharacter` patches current facts and mirrors roster kinds in the same transaction, advancing the revision only when either changes. Notes, names, recorded HP, row order and presentation changes preserve reviewed weeks. Creating a record publishes its facts without enrolling it. Sheet initialization and every existing sheet writer refresh through the shared persistence seam; frozen records are never rewritten.

The [data model](pf-character-sheet-data-model.md), [ADR 0001](adr/0001-one-character-identity.md) and [ADR 0002](adr/0002-characters-owned-by-users-move-between-campaigns.md) describe the target sheet and lifecycle contracts. Production retains flat-field militia authority until explicit initial cutover; isolated prepared fixture sheets supply calculated facts without activating production. Campaign ownership reassignment is prepared for fixture campaigns in #300, while campaign movement and external lifecycle processing remain later work.

## Staged Character Sheet interfaces (#256)

`convex/characterSheet.ts` adds create/read, base-score edits and Class Level add/edit/move/delete commands on the existing Character identity. Its additive `catalogEntry` and `characterSheetEntry` tables store six base Modifiers and ordered Unspecified Class Levels with stable row IDs and plain, nullable HP inputs. The base entry cannot be disabled or removed, and zero Class Levels are allowed. `src/lib/character-sheet.ts` provides the shared pure calculation interface. The public read returns calculated totals, which the client consumes directly.

Campaign sheet writes require a fixture campaign. Since #260, private creation instead requires the server-seeded `user.characterSheetDemo` marker, and private writes require `character.sheetDemo`; no public command enables either marker. Both creation paths work without a militia. Reads and writes use the shared Character access seam, deriving identity and campaign membership on the server; optional organization/campaign arguments assert the caller's route scope. Every campaign reader and writer requires persisted organization membership, including legacy records. Catalog Entries are checked against the owning Character, and Class Level commands only accept rows on that Character's sheet. New sheets retain compatibility flat fields; subsequent prepared sheet edits update their canonical facts atomically and leave those compatibility columns unused. Ordinary campaigns continue using flat facts in Setup, the ledger and canonical refresh pending explicit release cutover.

The `characterSheet` harness case creates `E2E character-sheet-campaign` and `E2E character-sheet-character`, with scores of 10 and one Unspecified Class Level with empty HP. It uses the existing preview-only fixture authorization. `inspectCase` includes `characterIds` for that case; the public sheet read supplies Character Sheet Entry and Catalog Entry IDs. Bounded reset/cleanup removes owned sheet entries and character-scoped Catalog Entries, including sheets created through public commands during the test. `convex/e2eFixtures.test.ts` proves member/owner public reads, outsider refusal, retry cleanup and preservation of a comparison case. The living-sheet UI and two-session browser scenario are implemented, but browser execution remains unverified; no production activation or backfill is performed by this preparation.

`characterSheet.archive` and `characterSheet.deletePrivate` both require an already prepared sheet through `loadWritableSheet`. Archiving additionally requires a fixture campaign; private deletion instead requires the private Character's `sheetDemo` marker and refuses campaign Characters. Legacy campaign Characters without prepared sheets remain on `character.archiveCharacter`, which does not require sheet preparation. Both archive entry points refresh current canonical facts only when the facts or mirrored roster kind differ.

### Modifier and personal adjustment preparation (#263)

`characterSheet:createPersonalAdjustment`, `editPersonalAdjustment` and `removePersonalAdjustment` extend the same fixture-only sheet API and Write Gate. Each adjustment owns a Character-scoped `manual` Catalog Entry and a Sheet Entry; edits retain its durable rule identity, and removal deletes both. The sheet loader validates every adjustment definition against the owning Character before returning it or resolving its Modifiers. Newly introduced condition references must belong to that Character. A saved reference whose target was removed stays conditional and does not prevent editing the remaining adjustment. Activation changes patch only the active flag, preserving concurrent content edits. This schema widening requires no existing-row backfill.

The shared calculation interface expands closed parent targets, resolves numeric bonus/penalty stacking and effective Sources, and reports applied, suppressed and conditional contributions. The sheet controller exposes the calculated breakdowns and adjustment commands. Editable base scores come from the base Catalog Entry, so an adjustment never becomes part of the saved base score. Formula evaluation, ability damage/drain and permanent projections remain #298's scope, integrated through the existing async Militia Character Facts seam described above. Presentation of breakdowns and the adjustment editor is handed to the separate UI agent through `/tmp/ep-orch/briefs/263/ui-contract.md`; #263's implementation brief assigns that markup and browser interaction evidence separately.

## Prepared militia ledger interfaces (#261)

`character:createCharacter` initializes a Militia-only sheet only in an isolated fixture campaign that already has a militia. `character:listByCampaign` returns calculated statistics plus ordered `classLevels` (`entryId`, `position`, `name`, `classEntryId`) and the existing sheet revision for prepared records; ordinary/candidate records retain flat fields and omit `sheetMode` and Class Level metadata. Only prepared fixture sheet loading is bounded to 256 Characters and reports overflow rather than truncating; legacy campaign ledgers retain their flat authority without that limit.

`character:updateCharacter` keeps metadata editable and delegates prepared statistics to `convex/lib/characterMilitiaOnlySheet.ts`. Increasing the level appends Unspecified Class Levels within the 4,096-entry prepared sheet cap, counting the base entry, existing Class Levels and personal adjustments. Every decrease requires exact ordered `confirmedRemovedLevelIds` and `expectedSheetRevision`, naming the current trailing classes in the client confirmation. Concurrent changes to those rows invalidate the reviewed removal. Permanent-score edits apply the displayed total difference to the base Modifier. Ability-score inputs, ability-target personal adjustment values and resolved ability scores must satisfy `Number.isSafeInteger`, matching the canonical snapshot's Zod integer constraint; fractional, non-finite and unsafe-integer values or arithmetic results are rejected. Fractional nonability adjustments remain supported. These are structural score constraints, independent of advisory rule limits. Full level/scores reject ledger writes; roster Hit Dice overrides, including zero, remain editable through canonical Militia Corrections.

`characterSheet:buildOut` permanently changes presentation to Full, keeping the Character ID, all sheet entries and calculated facts. An already Full Character is an unchanged retry. It uses the existing campaign Write Gate and actual-membership/fixture checks, accepts the injected `writeEpoch`, and appears in the migration writer inventory. Notes/metadata-only edits and Build out do not invalidate a week unless facts or a roster kind changes.

`canonicalLedger:save` continues checking the supplied facts against the current projection, and Confirmation checks the reviewed current source. `canonicalHistory.ts` reads selected frozen records; the authorized append seam retains historical snapshots for effective and superseded records. There is no registered public History Rewrite publication endpoint yet. Its future writer must select active calculation inputs without recalculating frozen history and must enter the Write Gate inventory.

## Campaign ownership reassignment (#300)

`character.reassignOwner` accepts a Character, asserted campaign, optional asserted organization, recipient user ID and operation ID. In a prepared fixture campaign, any surviving current organization member may assign to any surviving current member, including themselves. The transaction derives the actual organization and rechecks both accounts and membership; the previous owner's account or membership is not required. Private Characters cannot be reassigned. Companion Relationship status is reconciled in the same transaction, and the relationship never grants endpoint access. Both ownership reassignment and the member picker require `requireFixtureCampaign`, including legacy flat Characters. Production campaigns retain legacy ownership and flat militia authority until explicit cutover; preparing the membership directory does not enable either capability. Prepared fixture legacy records support ownership-only edits without changing flat militia authority. Prepared sheet writes use the same fixture eligibility; they update the in-memory owner, prune stale Accepted Warnings, preserve unchanged warning acceptance and record the sheet change. The migration Write Gate covers both paths.

`character.listByCampaign` adds `owner: { userId, name, isMine } | null` to each Character document; `character.listCampaignCharacters` and `characterSheet.read` expose the same projection at their response root. The campaign list retains `ownerName` for its existing navigation contract. Owner profiles are loaded once per distinct owner in a list, not through per-row client subscriptions. Names are trimmed, with “Unnamed member” for an empty name. A surviving departed owner still displays their name; a missing owner/account displays “Needs an owner”. Character documents retain `ownerId` and `isActive`, including archived records. Optional `ownerLastOperationId` records the most recent assignment operation for local/remote feedback correlation; absence on legacy records is supported and it is never player-facing copy.

`character.listOwnerCandidates` authorizes the campaign and checks fixture eligibility before paginating `organizationMembership.by_organizationId_and_userId`, projecting `{ userId, name, isMine }` only after rechecking the surviving user's current `orgIds`. Page sizes are limited to 1–100 and each query scans at most 100 membership rows. Stale/deleted profiles are omitted without losing native cursor or split metadata; a page can be empty with more pages remaining. There is no account-table scan or fallback. The additive index is a directory projection, never authorization authority. Accepted ordered user/membership webhooks and real fixture user writers update it in their own gated transaction. Existing accounts require the bounded, gated `organizationMembership.backfill` described in the [Write Gate inventory](initial-character-migration-write-gate.md#organization-membership-directory-backfill-300).

`requireCharacterDepartureAccess` in `convex/lib/characterAccess.ts` loads the current Character, surviving caller and current organization membership and permits only the authoritative current owner. This is the #316 hook point, not a public query or a move. The future movement implementation must call it inside its final publication transaction, after preparation; a cached owner cannot authorize publication. Taking ownership immediately passes this check and invalidates the prior owner's authority. Integration tests call the helper in authenticated `t.run` transactions. System-initiated access-loss completion must use its separate trusted lifecycle policy, since this helper deliberately requires the requesting member's access.

`useCharacterOwnership` receives ownership eligibility from the existing campaign list model or authorized sheet campaign projection, with unresolved or nonprepared campaigns unavailable. No per-row campaign subscription is needed. Losing eligibility hides the owner assignment control, closes the visible picker, skips member pagination and blocks assignment. It supplies scoped member pagination, local saving/error acknowledgement, maintenance disabling and remote owner-change feedback from the existing list/sheet owner projection. Independent campaign sheets supply their persisted campaign ID without needing a selected organization; the server derives campaign organization access, while a supplied organization must match. `convex/characterOwnership.integration.test.ts` proves shared editing, recipient/account/scope refusals, stale owner/recipient cases, ownerless assignment, private refusal, departure authority, fixture isolation, owner/archive projections and warning preservation. `convex/organizationMembership.integration.test.ts` proves bounded resumable backfill, idempotence, ordered webhook updates and maintenance/epoch refusals. Fixture tests prove membership replacement removes stale directory rows. `use-character-ownership.test.ts` proves the browser adapter behavior without a deployment. No campaign transitions, departure corrections, homebrew detachment or external lifecycle handlers are implemented by this slice.

## Race selections and Racial Traits (#304)

`characterSheet.selectRace`, `chooseRacialAbilityScore`, `setRacialTraitSelected`, `setRacialTraitReplacements` and `editRaceStatistics` use the legacy-Character Write Gate class and reconcile warning acceptances in the same transaction. Standard Racial Traits are Grants; the dedicated trait writer and generic `selectEntry`/`editSelection` writers reject their selections by Rule Identity, including Catalog Copies. Only alternates are chosen as Selections. Manual adjustments cannot use the catalog-only `ability.$choice` target.

`calculateCharacterSheetProjections` resolves race facts, standard Grants, alternate replacements, recorded score choices and racial Hit Dice budgets alongside skills and conditions. Replacement names are resolved by import/curation into catalog references; runtime matches preserved Rule Identities without guessing from names or from alternate eligibility. Racial rank budget and rank cap mismatches remain advisory.

`resolveCharacterSheetRacialFacts` and the tested pure `satisfiesRacialPrerequisite` prepare both `race` and `racialTrait` prerequisite clauses. There is no prerequisite-engine caller yet: #313 must consume these facts in current and recorded-level checks, preserving the exclusion of dormant and replaced entries. This slice does not implement prerequisite warnings.
