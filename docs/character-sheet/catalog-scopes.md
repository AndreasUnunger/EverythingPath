## Catalog scopes

Catalog Copy preparation (#308): `convex/catalogCopies.ts` exposes `createOneOff`, `editDefinition`, `saveToCatalog`, `customizeForCampaign` and `detach`, plus read-only `list` and access-filtered `advisories` queries. The additive `catalogEntry` schema supports global, campaign and Character scopes with optional scope references, immediate `copiedFrom` provenance and a copy-time `copiedFromFingerprint`; scope lookups use `by_scope`, `by_campaignId_and_scope` and `by_characterId`. Prepared writes retain the existing private-demo/fixture restrictions, current-owner or campaign-membership authorization, and the legacy Character maintenance/epoch/authority gate. Copies keep durable rule identity and effective Source while their editable definitions remain independent. Only Customize for campaign sets the optional `campaignPreference` marker that replaces its global origin in pickers and projects global parents for future Grants. Save to catalog rescopes and shares homebrew without replacing original definitions or changing other sheets; Detach removes this marker. Provenance alone never selects a preference; customization records the chosen campaign copy on affected current Grants, including dormant state, without creating Selections or rewriting copied parents’ frozen global references. Later parent customization keeps those choices. Copies capture their persisted origin’s fields and fingerprint, and uncustomized global dependencies remain live; an advisory compares the accessible origin with its copy-time fingerprint without updating the copy. This prepares local definitions and copy operations; production sheet activation remains separate work. Prepared campaign departure now follows the #316 workflow described below.

The Catalog controller selects existing definitions through `characterSheet.selectEntry`, with acknowledgement beside the selected definition and a created-row focus target. Only selectable kinds are offered; Classes use the Class Level workflow. New Selections resolve an explicit campaign preference even when an in-flight picker submits its previous global ID, while choices, notes and active state remain player input. Existing Selections and explicit Character copies retain their own definition references. Class Level rows expose their class definition for Customize and Detach; detaching a Class retains the Character's Class Level state and repoints its class references, including favored-class settings. A Spell Effect's recorded caster level has a separate state-only form and writer adapter: it sends only caster level and optional active state, without resubmitting or validating shared definition fields. Its target uses the same adapter (`sheetEntries.setTarget`, from the calculated target options); a cleared caster level restores the calculated default. The full definition editor remains the path for one-off creation and Character-specific definition changes. These controllers prepare the remaining picker, Class Level controls and shared Spell Effect state presentation for the UI handoff.

- **Global:** the imported catalog, read-only for players. See "Global catalog import".
- **Campaign:** homebrew that anyone in the campaign can use and edit.
- **Character:** one-offs on a single Character, such as base scores, manual adjustments and tweaks.

Adding a one-off inserts its character-scoped Catalog Entry and its sheet entry in one mutation. "Save to catalog" rescopes a character entry to the campaign. "Detach" clones a global or campaign entry into a character-scoped one and repoints the sheet entry. "Customize for campaign" clones a global entry into campaign scope, repoints every sheet entry in that campaign, and makes the picker show the copy in place of the original for that campaign. A Grant keeps its Grant Key through either clone, so its recorded state stays (see "Grants and dormant entries").

Both clones record their immediate origin as `copiedFrom` and that definition's fingerprint at copy time, separately from the durable transitive `ruleIdentity` and effective Source they inherit. A copy's own fields never follow later changes to its original. Its retained references to global Catalog Entries follow the active Catalog Release: a copied magic weapon can still change when its global Base Item or Item Ability changes. These editing actions do not recursively freeze dependencies, and references to local entries keep their existing behavior; campaign departure preserves campaign dependencies as described below.

The upstream-change advisory compares the immediate origin's current definition fingerprint with the one recorded at copy time, only while the viewer can access that origin. An unrelated release does not warn. Neither provenance nor equality identity requires the original's current definition; references used to compute, grant or offer content are definition dependencies.

Prepared #308 verifies same-Source stacking and retained Grant Keys after the original becomes inaccessible. The #313 prerequisite engine compares copies' retained durable rule identities without loading their originals. Public calculation tests cover remapped feat possession, racial identities and retained Unchained feature names, preserving prerequisite results when a copied definition remains available and its original does not.

The definition editor reads persisted catalog fields rather than references projected for sheet calculation. Definition editing is unavailable while the raw catalog read is loading or omits the definition; projected sheet fields alone never grant edit permission. It sends only its editable name and Modifiers; the server preserves unedited definition fields and existing curated `stacksWithinEntry` exceptions through value edits and reordering. It matches unchanged Modifier facts first, then pairs remaining value edits by target, bonus type and condition. Each existing exception can be retained once; adding a duplicate Modifier does not create another exception. Clients cannot introduce that exception through one-off creation or editing.

Scope validation remains compatible with existing optional `characterId` and `campaignId` fields. Tightening the catalog schema into a scope-discriminated union requires auditing retained prepared/migration rows first; no deployed-row evidence is available for #308. The single `writeCatalogDefinition` helper instead validates the complete definition, scope and required references before inserting or patching Catalog Copy definitions. An additive index on campaign, scope, immediate origin and Campaign Catalog Preference supports bounded preferred-copy lookup without changing stored row shapes. The persisted `campaignPreference` field represents the glossary's Campaign Catalog Preference.

The general prepared catalog picker currently reads at most 4,096 definitions from each accessible scope and returns at most 8,192 definitions, prioritizing Character, campaign and then global definitions, with no pagination interface. This is a prepared-fixture limit, not evidence of complete large-catalog browsing. The separate #315 Spell browser uses bounded indexed pagination and summaries rather than this picker or full-catalog reads. Sheet reads separately load their referenced definitions and applicable Campaign Catalog Preferences; unrelated global or campaign rows do not consume the Character child-row limit. Large-catalog pagination for the general picker remains follow-up work before production activation.

### Campaign homebrew moving with a Character

Decided by [Decide how campaign homebrew moves with a Character](https://github.com/AndreasUnunger/EverythingPath/issues/244). This supplies the homebrew preservation mechanics for "Ownership and campaigns" and amends the retained-exception copying restriction under "Global catalog import"; ownership, departure authority and deletion policy remain unchanged.

- **Departure scope.** Campaign homebrew needed by the Character is copied into character scope. A carried homebrew class preserves its complete progression, future features, available talent choices and full spell list, including options never selected, together with their campaign dependencies. Unrelated campaign content stays behind. References to global Catalog Entries keep following the active Catalog Release; attribution holds still limit which content can be selected or granted.
- **Arrival and return.** Joining another campaign or returning to the original campaign keeps carried definitions until someone explicitly replaces them, even when that campaign has a different version. The destination's catalog preferences apply to future selections; joining alone never replaces existing choices or adds a militia roster assignment.
- **One class version.** All Class Levels of one class use one chosen definition. Adding another level continues it, regardless of the destination's catalog preference. Selecting a different copy is an explicit switch of the whole class, preserving all Class Level row IDs, order, HP, skill ranks, choices, favored-class state and casting-advance links. Matching Grants retain their state; removed Grants and displaced choices go dormant, and switching back restores them under "Grants and dormant entries". A switch may change calculated results because the chosen definition changes. The existing original-versus-Unchained policy is unchanged and is not the policy for Catalog Copies.
- **Rule identity.** A Catalog Copy retains the original rule identity for prerequisites, Grant Keys and same-Source stacking through edits. Creating a distinct Catalog Entry represents a distinct rule. Different copies keep their own definitions and saved state; sharing rule identity does not merge them. Durable identity and effective Source are retained directly, without privileged traversal of original definitions. Immediate copy provenance and its copy-time fingerprint are separate and never confer access.
- **Original-change advisories.** Check for changes only when the person viewing the Character Sheet can access the immediate origin. Without access, reveal no information about later changes. If access returns, compare its current definition with the definition recorded at copy time. Never update the copy automatically.
- **Held content.** A necessary departure copy or reference remapping may preserve the same Character's already-retained use of attribution-held content. It carries the hold, retained-exception reporting and notice requirements with it. This grants no new selection or Grant entitlement, admits no held revision and does not make future features or options available while held; the complete future homebrew repertoire remains subject to those holds. The exception permits lifecycle preservation only, not ordinary new copies.

**Dependency and identity invariants.**

- Start from all retained Character state, not only currently active entries: active, off, kept and dormant entries, orphaned Spells, saved Grant state, slots and Accepted Warnings, Class Levels, casting, Attack Routines and item magic state. Also include that Character's existing character-scoped definitions, so unused local customizations remain theirs. Preserve the Character ID, sheet and Class Level row IDs, their ordering and state links. A move neither repairs pre-existing broken Class Level links nor turns Grants into new Selections.
- Follow definition dependencies transitively, including catalog IDs and key-based joins. Include full class progression, future prompt options and whole-class spell lists even when they have no sheet rows, granted-spell lists, Base Items, Item Abilities, Archetype replacements and Racial Traits. Campaign members of a required keyed list remain dependencies even when the class definition is global. A reference used to compute, grant or offer content is a definition dependency regardless of how it is encoded.
- Copy required campaign definitions; reuse global identities, which continue following the active Catalog Release. Reuse existing character-scoped definitions only when they belong to this Character, remapping campaign dependencies inside them without overwriting their custom fields. Do not traverse `copiedFrom` or identity-only prerequisite and equality links as content dependencies: preserve their durable equality identity and already-held display facts without loading an inaccessible original payload.
- Deduplicate only repeated references to the same source definition within the move. Preserve divergent copies and existing customized character copies separately; a shared ancestor, rule identity or name does not justify coalescing definitions. Allocate the mapping before following dependent edges so cycles terminate and shared dependencies get one destination definition.
- Apply one consistent mapping to typed catalog references and scoped class and list keys, including Grant definition sources, Archetype and Racial Trait replacement targets, and slot links. Durable identities inside Grant Keys remain unchanged. Keep casting-advance and recorded-Spell links attached to the chosen class definition, and sheet-to-sheet links attached to the same rows. Preserve each copy's effective Source and canonical rule identity; remapping must never require access to its ancestors.
- Copying and remapping alone change no totals, Grants, stacking, prerequisite results, saved state or Accepted Warning acceptance. Warning fingerprints use semantic facts and durable identities, so new storage references do not reopen them. Independent edits, an explicit class-version switch or a Catalog Release can change underlying facts and use the ordinary recalculation and warning rules.

**Preparation and publication.**

- Prepare privately in bounded, resumable work. Staged copies and remaps never appear in pickers or partially redirect the live sheet. Preserve source definitions and dependencies until detachment or retained recovery finishes safely. Retrying the same move reuses its work and creates no duplicate definitions, rows or departure effects; after a lost response, inspect the committed operation before retrying.
- Track the inputs used for preparation, including the sheet, all source campaign and character definitions, ownership, authoritative account and membership state, relationships and the active Catalog Release. Relevant writes mark pending work dirty under the protocol in "Catalog releases". A move also participates in any pending release's dirty-work tracking. Reconcile intervening edits or release changes against current state; never restore a prepared snapshot over later player changes.
- At the final bounded transaction, verify current authority, destination access for a requested move, current input revisions and the active release, and that all preparation and reconciliation is complete. Publish the complete sheet-reference selection, campaign transition, Militia-only-to-Full change, departure Militia Correction, roster/officer/team-manager removals and affected Staged Action Choice review flags together. Staged data selected through pointers may keep this bounded, but every reader and writer must observe one complete selection. Militia Character Facts and any release work stay consistent with that same publication boundary.
- A failed voluntary move leaves the pre-move sheet, roster and campaign relationship unchanged. Automatic access loss revokes access immediately while preservation work retries; trusted system completion does not require the departed user's credentials. Recheck current ownership and authoritative lifecycle state before publishing, so stale work cannot undo reassignment, membership changes or account-deletion policy. Frozen Resolution Records, including superseded records, remain unchanged, and the existing deletion and ownerless-recovery rules still apply.

Prepared movement (#316) exposes `characterMoves:start`, `resume`, `cancel`, `status` and `destinations`. Only the current owner can request it, including after a campaign member takes ownership; requested destinations require current organization access. Fixture campaigns and private sheet demos retain the preactivation writer restrictions. Arrival changes the existing Character's campaign without adding roster or officer membership. A departure permanently selects Full presentation and removes the prior militia's live Character facts, roster person, officer roles and team-manager assignments through an automatic-reason Militia Correction. The same transaction records `reviewRequired` on affected saved Activity choices; explicit detail review clears it without changing the saved rolls or choices. Automatic review revisions retain scoped accepted-draft checkpoints in `canonicalDraftSourceReview`, so later edits and stale-edit checks can resolve their observed base revision; closed-draft retirement removes these snapshots in bounded batches. Unchanged flagged choices may remain during unrelated edits or move/swap, so obsolete choices can be corrected one at a time; new, changed or review-cleared choices must satisfy current-source references. Move/swap retains the flag, and Weekly Confirmation remains unavailable while a required choice review is outstanding. Frozen Resolution Records remain untouched.

`characterMove` checkpoints the request, owner, source/destination, source sheet revision, preparation generation, scan cursor and progress. `characterMoveReference` stores candidate IDs, required keys, destination Spell IDs and the definition frontier as indexed child rows; discovery appends only new references rather than rewriting arrays on the operation document. Each reference kind retains the existing 8,192-entry prepared-graph bound. One typed root list covers `characterSheetEntry` (including Archetypes, Selections and Attack Routines), Spell index/summary rows, linked-input choices and Accepted Warnings. Companion relationship sources use preserved sheet-row links and durable Grant Keys. Indexed source, global and destination Spell scans paginate at most 32 rows and approximately 1 MiB per command. Retained `classTag`, `castingClass` and `list` consumer fields identify required keys; only Spell `detail.levels` maps offer keyed membership. Equal consumer keys on unrelated Classes, prompt features or Modifiers do not create dependency edges; clients cannot supply `dependencyKeys` or `requiredDependencyKeys`, and those older optional schema fields are ignored. There is no independent option-list membership field in the current definition schema. Typed prompt and Grant references continue to supply their transitive content edges. Newly discovered required keys trigger another cursor pass until closure is complete. Unused own definitions, including browser definitions, remain roots. Catalog writers do not update the campaign document or use a campaign-wide catalog revision to reset preparation. `campaignSpellMembership` holds one indexed revision stamp per campaign. The central `writeCatalogDefinition` writer advances it only when a campaign Spell is created, deleted, changes campaign/scope/kind, or changes its sorted `detail.levels` keys; numeric levels, key order and unrelated homebrew fields do not advance it. A move captures both campaign stamps before its first discovery page and retains that baseline through additional key passes. Every resume compares the stamps before dereferencing saved candidates. A mismatch restarts discovery from the current sheet with clean candidates, including after a candidate was deleted. Final publication reads the two stamps and the required definition graph without rescanning any Spell catalog. Globals remain live, and discovery retains the original active-release fingerprint through every page and extra-key pass so a changed release restarts discovery before publication; the referenced-definition loader resolves global dependencies by ID rather than requiring all global Spell members.

Before deploying this narrowed operation schema over earlier prepared data, reconcile existing `characterMove` checkpoints. Nonterminal checkpoints need cancellation and restart with retired fields removed, or a bounded conversion of their persisted candidate IDs, destination IDs, definition IDs and required keys into `characterMoveReference` rows. Remove the retired arrays, campaign revision fields and source-preference map from terminal rows as well. Perform that compatibility cleanup or conversion before narrowing the schema; a cancelled state alone does not remove obsolete fields. The membership stamp table is new and needs no backfill: an absent row means revision zero, and an indexed read participates in transaction conflict detection against its first insertion. The two checkpoint stamp fields are optional for retained rows; an unstamped nonterminal checkpoint restarts discovery on resume, while terminal checkpoints retain their result. This fix does not run a migration or deploy, and completed live Character state remains authoritative throughout the checkpoint cleanup.

Definition snapshots live only in `characterMoveDefinition`, outside catalog and Spell browser readers. Every staging batch uses the same effective-definition reader, including carried aliases and campaign preferences. Each batch loads the current bounded effective graph and stages at most 32 definitions and approximately 1 MiB of payload, and explicit `resume` continues the workflow. The carried-reference map remains limited to 1,024 keys by Convex document structure; exceeding that bound refuses publication while preserving the old Character. The metadata document remains below 900 KiB. Publication compares each staged payload with the current effective definition; it re-stages only changed definitions in batches of 32 and retains unaffected preparation. A changed relationship or active release restarts discovery, and so does any sheet or definition edit that changes the required keys or definitions (#703, below). The freshness fingerprint includes player sheet entries, linked-input choices, Spell catalog/class/rule-identity bindings, base scores, campaign, owner and carried selections. It excludes Character revision and operation-attribution bookkeeping, regenerated Spell names/levels/summary counts and Accepted Warning rows. Those derived browser fields and warning acceptances are read live during publication, so their recalculation or pruning does not discard unchanged definition staging. A public catalog edit may update that bookkeeping across campaign sheets without discarding move preparation. Unrelated homebrew edits retain progress, and a staged definition edited through the public catalog editor refreshes its own snapshot. Publication allocates all copy IDs before applying cyclic references in one plan and transaction. `character.carriedCatalogReferences` preserves selected source dependencies of live global parents ahead of destination preferences; every mapped target must remain this Character's own definition or an explicitly saved definition in its current campaign. Mapped targets remain dependency roots after their direct Selections are removed; Save to catalog preserves their stable identity, and a later move remaps existing alias targets without replacing established source choices with destination preferences. Existing player selections and custom fields survive, while future explicit selections still use destination preferences. Copy provenance fingerprints refer to raw persisted origins, independently of the effective dependency graph. Campaign arrivals retain the existing `sheetDemo` permission. A fixture departure enables its private editor only when the owner already has private sheet demo access; without that preactivation permission it is refused before publication.

Final publication is one transaction, with current transaction metrics and an estimate of changed rows/bytes reserving headroom. The final sheet must still satisfy the prepared reader's 4,096 non-browser local-definition/entry limits and the existing Spell/companion limits. A graph or spell expansion that exceeds physical transaction/readability limits is refused atomically, leaving the prior campaign, sheet and roster authoritative; a selected-generation pointer implementation for larger sheets remains future production work. The destination Spell index uses discovered required global definitions along with carried copies and destination members, adding newly accessible keyed members and summaries while preserving carried variants and recorded links; it excludes unrelated definition kinds from discovery. Publication also makes the in-place spell-index repairs (#728): rows naming a deleted definition are no dependency of the move; they are removed and their Spell's rows rewritten from another definition of it, and each Spellcasting without rows for the Character's indexed Spells gets them, as when its class is added in place ([Spellcasting](spellcasting.md#recorded-spells)). Terminal and superseded private snapshots are cleaned in bounded scheduled housekeeping, and deleted Characters' move metadata is removed. Retrying a completed request acknowledges the same result rather than duplicating departure effects.

Prepared moves reconcile concurrent work (#703):

- **Restart or keep.** The boundary `fingerprint` covers campaign, owner, carried selections, Companion Relationships and the active release, and any change restarts discovery. Whenever a ready or staging move reads current inputs after discovery, it also recomputes the required keys and definitions. A new key, such as a campaign class edited to cast from another Spell list, or a changed definition set, restarts discovery so the new members arrive. Otherwise staged work is kept. During discovery, the last page rereads the sheet and scans again for any new key.
- **No overwrite.** Publication reads the live sheet in its one transaction. Edits from a second device or player, class switches, Keep/Discard and warning acceptances made during preparation are published with the move. Staged definitions changed meanwhile are re-staged.
- **`ownershipChanged`.** Each move records the `ownerLastOperationId` it was requested under. Any reassignment during preparation fences the move, even one that returns ownership to the requester: the move ends `cancelled` and the Character is unchanged.
- **`campaignChanged`.** A Character whose campaign changed outside the move, for example by a trusted return after membership loss, fences the move the same way.
- **`replaced`.** A newer move started from any device ends the pending one. The device that watched the replaced move reads its result through `status` with that operation's ID.
- **Waiting.** While the owner can't reach the destination campaign, `status` and `resume` report `state: 'waiting'` with `waitingReason: 'destinationUnavailable'`. This is not stored and not terminal: the move continues when access returns, and `cancel` ends it.
- **Retries and access.** `resume` authorizes the caller as the current owner before looking up the operation, so an outsider can't tell an existing operation, or an existing Character, from a missing one. Retrying `start`, `resume` or `cancel` after a lost response returns the committed result and repeats no copies, rows or departure effects. Source definitions stay in their campaign throughout, and copies exist only after publication.
- **Proof.** Closure through public reads is proven for class switches, whole campaign Spell lists including a list gained during preparation, Base Items with Item Abilities, dormant kept Grants with accepted warnings, and reference cycles (`convex/characterMoveClosure.integration.test.ts`, `convex/characterMoveReconciliation.integration.test.ts`).
- **Compatibility.** The two checkpoint fields (`ownerOperationId`, `cancelReason`) are optional and need no backfill. A retained nonterminal checkpoint restarts discovery once on its next resume, and one whose Character has since been reassigned is fenced.

Grouped movement (#711) uses the same per-Character preparation and one group publication transaction. The requested Character is the root; only recursively active same-owner Companions travel, up to 16 Characters including the root. Effective relationship status controls eligibility. `characterMove` adds optional `groupRootId` on member preparation and `groupCharacterIds`/`groupFingerprint` and bounded `groupMoveClaims` on the root. Claims capture each member's prior move identity and ownership-operation token; newer work is fenced by identity even when command timestamps match. Member work uses the root's operation ID, so a member's status, Resume and Cancel address the same group. Publication verifies the current group fingerprint and every member's ownership-operation token and campaign; a changed group ends `cancelled` with `groupChanged`, and any member's reassignment, campaign change or newer operation fences the whole group. Child preparation is never published independently. A member operation with the same identifier that belongs to another request fences the group rather than being reused; publication requires one correctly bound preparation for every captured member. Legacy nonterminal single-Character checkpoints that now have eligible Companions are cancelled for a fresh grouped request, while legacy terminal results remain readable. A terminal child result remains readable after its deleted associated Character's root checkpoint is cleaned up. Group progress sums staged definitions, with zero completed members until atomic publication; a member's changed closure advances the aggregate preparation generation.

The 16-Character cap is proven through public start/resume completion with enforced Convex transaction limits: the integration fixture moves sixteen third-level Fighters, each carrying seeded Class content, a Longsword created through the one-off editor, and a player-created homebrew Feat. Every resume preserves the complete source group until one publication selects all arrivals; calculated and permanent projections, sheet entries and Character-specific definitions survive unchanged. The cap also stays within the downstream sixteen-Character fact-refresh bound. Larger groups remain unsupported: publishing them across several transactions would violate the no-partial-group rule. Interrupt a Companion Relationship first to reduce the group. More elaborate sheets may still reach physical limits below the cap.

Group discovery, sheet/dependency reads, operation-reference and staged-definition reads, arrival indexing and downstream fact refreshes stream through budgets capped at 8 MiB and 8,192 unique references. Physical document reads have a separate limit taken from the transaction's measured remaining reads: ordinary per-Character work reserves 64 reads for bookkeeping, while group discovery reserves 1,024. Byte budgets leave 2 MiB. These apply in addition to the existing connected-graph bounds. Each refresh obtains a fresh remaining budget. Preparation reference inserts are preflighted against remaining writes and bytes, retaining 128 document writes and 1 MiB of byte-write headroom. Final preparation checks a combined 8,192 sheet-root/definition-record and 8 MiB input-body ceiling and leaves at least 2 MiB and 1,024 document reads for final work after staging is revalidated. Publication write estimates include changed copies, existing definitions and remapped sheet roots plus 256 reserved writes per member; the combined estimate must fit remaining document writes, with 2 MiB of byte-write headroom for corrections and facts. The existing 32-definition/approximately 1 MiB staging batches and per-Character graph/map limits still apply. Over-budget work refuses atomically while the original sheets, campaigns and militia assignments remain authoritative; the application never silently splits a group. Copies are separate for each Character, preserving divergent definitions and independent customization.

`characterMoves.preview` is an owner-only read of the moving group and staying endpoints/reasons. An oversized group returns a structured refusal with its size and the cap, so the owner sees the remedy in both Move and Leave. Only active incoming relationships list an associated Character as staying; replaced and interrupted history does not. Missing/deleted companions have an unavailable reason without a name or ID. Names and IDs require independent endpoint access. Every departing member receives the existing Full-presentation transition, assignment removals and Militia Correction; affected saved Activity choices require review. Arrival never adds any group member to a militia roster, and frozen Resolution Records remain unchanged.

Grouped publication participates in Catalog Release impact tracking: after selecting all campaign transitions, `updateCanonicalCharacter` marks each prepared member dirty for pending release work in the same transaction. Relationship reconciliation refreshes affected downstream companion facts through the existing canonical path, including their impact tracking. Current selected release and definition digests still fence and refresh move preparation; ordinary release publication stays separate from the initial migration freeze. A group published during reconciliation is re-evaluated in its destination, and its Character copies of campaign customizations keep following the release through their global references (#712, [Linked Companions, moves and keyed lists](../catalog-import/releases.md#linked-companions-moves-and-keyed-lists)). #706/#710 trusted access-loss and container-deletion returns use this same grouped move with the owner's stored account, so completion needs no credentials. The shared lifecycle driver chooses the highest active same-owner associated Character before starting a return, even when its Companion appears first in the index; voluntary Companion moves still travel downward only. The departure and deletion drivers continue each other's unfinished group return for the same owner. Account deletion retains its #708 policy and fences the whole pending group. A reassignment, campaign change or newer move fences trusted work exactly like a voluntary move. These prepared restrictions do not activate production Character Sheets.

Trusted return-root discovery uses a shared graph/source-sheet budget of at most 4 MiB and 4,096 document reads, reduced to leave at least 1 MiB and 1,024 document reads in the current transaction. Indexed relationship rows are accounted as they are read. A repeatedly failing root is set aside with the whole eligible group, so a later child cannot return alone; independent groups continue and the existing slower retry resumes the root. Domain discovery errors reach the existing nested-step failure handling rather than abandoning the lifecycle without a scheduled retry; unexpected errors propagate. Discovery shares the move reader’s budget accounting rather than keeping a separate physical-read counter.
