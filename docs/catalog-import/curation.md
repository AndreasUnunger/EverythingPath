# Note curation operators

`catalog:curate` drafts content-bound records; `catalog:preview` applies them and evaluates coverage together with attribution admission. This workflow prepares catalog content locally. It does not publish a release or change a Character Sheet.

## Commands

Use clean checkouts at the catalog pins. Both commands verify Git identity and the manifests. `--allow-unverified-checkouts` is the explicit fixture/development override; reports record it and it does not bypass either coverage or attribution admission.

```sh
# Full corpus (no batch bound)
pnpm -s catalog:curate --system /path/to/pf1 --content /path/to/pf1-content --out .scratch/catalog-curation/full-drafts
# One curation batch
pnpm -s catalog:curate --system /path/to/pf1 --content /path/to/pf1-content --candidates /path/to/batch-keys.json --out .scratch/catalog-curation/drafts
pnpm -s catalog:preview --system /path/to/pf1 --content /path/to/pf1-content --candidates /path/to/batch-keys.json --curation .scratch/catalog-curation/drafts/records.json --out .scratch/catalog-curation/preview
```

The default input overlay is [`scripts/catalog/reviewed-curation.json`](../../scripts/catalog/reviewed-curation.json), beside reviewed identity remaps. Content batches contribute their reviewed records there. An alternative file is supplied with `--records` to the drafter or `--curation` to preview. Commands reject source-overlapping output paths, unrelated output files and symlink report files before writing. A drafter can resume into the same directory when its `--records` is exactly that directory's regular `records.json`.

For a curation ticket, pass `--candidates path/to/keys.json` to both commands. The file is a JSON array of exact upstream keys, including any folder/excluded records in the ticket inventory. A selection accepts at most 100 unique keys and three class definitions; unknown keys are rejected. Without `--candidates`, both commands run over the complete import with no batch bound, as for a full drafter run or full preview. Source verification, source fingerprints, identity resolution and helper lookup still use the complete pinned checkouts. Reports include `candidateKeys`; inventory counts and `coverageComplete` describe only that selection. A bounded preview does not admit linked entries outside the selection: their absence can produce reference failures. Run a full preview as well to distinguish these from failures present in the complete import. This selector does not publish a release or establish whole-corpus coverage.

The drafter writes `records.json` in the canonical overlay form (see [Parallel batches](#parallel-batches)) and `curation.json`; extraction errors and malformed records write no new reports. Its successful exit means drafting completed, even if diagnostics remain. Preview writes `catalog.json`, `comparison.json`, `unsupported.json`, `curation.json` and `admission.json` before exiting nonzero for a coverage/admission failure. Named attribution holds remain holds; missing curation fails even when the content is held for attribution.

## Record contract

A record has `externalKey`, `kind`, `target`, `text`, `textSha256`, `status`, `outputs`, `rationale`, `diagnostics` and `seedBindings`. The strict schema and inferred TypeScript types live in [`scripts/catalog/curation.ts`](../../scripts/catalog/curation.ts). Identities use the reviewed remap's retained external key before matching. Repeated text on another entry never shares a record.

- `note` binds the Foundry target and exact raw note string, before sanitization. `textSha256` is SHA-256 of those UTF-8 bytes.
- `conditional` binds `actionId` and `conditionalId`, the ordered Foundry `target/subTarget` values, and the entire serialized conditional (name, formula, critical mode, damage type and other mechanics). The exact serialized payload is stored as `text`; its hash is calculated the same way. Reordering actions with stable IDs preserves bindings. A record without IDs falls back to position, so reorder requires fresh drafts.
- `itemAbility` binds the exact raw imported description, even when the ability has no notes or conditionals. Helper seed dependencies retain their own complete bindings, so changed helper mechanics invalidate a seeded draft even when the ability's description stays the same.
- `description` binds the raw description but belongs to the separate prose pass, outside the required note gate.

The output list contains strict discriminated variants:

| `kind`        | Output                                                                                                                                                                    |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `modifier`    | Closed runtime target/bonus type, finite number or `{ formula }`, optional condition and `stacksWithinEntry: true`.                                                       |
| `note`        | Plain text for rules not represented by structured output, optional closed target and Situation; absent target means entry-level text.                                    |
| `itemAbility` | `bonusEquivalent`, `damageDice` (`dice`, `on: hit/crit`, `damageType`, optional Situation), `doublesThreat`, `weaponDamageTypes`, `choice: creatureType`, or `sourceKey`. |

Modifiers append to the entry's `modifiers`. A race's record can apply to one of its standard Racial Traits instead: a note record goes to the trait whose note covers the same statistic, and the reviewed description re-homes move named outputs (see [Racial Trait Grants](README.md#racial-trait-grants)). The record still binds to the race's raw text. While the race's note record is checked, it stands in for that trait's own notes on the target that state the same numbers: they are not required inputs, the drafter does not draft them, and an existing draft for one is reported stale. Only a checked note record of the trait for the target supersedes the race's note: the race's note is then no longer a required input and its record is reported stale. A full drafter run therefore retires none of the checked race records. Before checking a trait's note record, check that it covers the race record's reviewed outputs; once it lands, remove the stale race record. Also check the import report's `latentOverlaps`. When an output's owning trait is outside the extraction, the output is not applied and the race reports it as a `curation.home` unsupported issue. Outside these cases, outputs apply to the record's own entry; Notes append sanitized plain text to `situationalNotes`. Foundry inline-roll delimiters and roll commands are removed, and formula references become readable labels (for example `+[[@resources.rage]]` becomes `+rage`); no expression is executed. Item Ability mechanics enrich `detail.kind: itemAbility`, using the data model's names, and damage dice from multiple outputs are preserved in order. A die may carry a shared, local or option Situation, and `foeEnhancement` sets how much better the weapon's enhancement is against the designated foe; an Item Ability record's Modifier may read `@item.enhancement`, the enhancement of the item part listing the ability (#764). Structured Item Ability mechanics do not produce duplicate description Notes; only uncovered nonnumeric rules remain Notes. `sourceKey` belongs to the common entry. Weapon/action Modifiers use `condition.weapon: '$self'`. A Modifier without a weapon condition, such as Shadow's Stealth bonus, follows the active item. The existing sheet resolver consumes the numeric/formula Modifier shape; attack and Item Ability consumers implement their model-specific weapon/dice/choice behavior in their own tickets.

An intentional `outputs: []` means explicit covered/no-output, with a nonempty rationale explaining what other record supplies the behavior. A prose draft that cannot be parsed can also have no outputs, but its review diagnostic means it is pending review rather than deliberately covered. Duplicate bindings, unknown output properties/targets/bonus types, mismatched text hashes and malformed review metadata are rejected. Unresolved numeric/action/helper Notes use the reserved text `Review required: replace this placeholder with readable rules text or structured outputs.` instead of raw mechanics or serialized conditionals. Checking a record or removing its diagnostics while that placeholder remains is rejected; replace the output with readable rules text, structured mechanics or deliberate covered/no-output first.

Both `drafted` and `checked` records apply under #228. The #303 workflow adds a conservative exception: drafted records carrying any diagnostic contribute no output until checked. Each diagnostic has `{ kind: 'unresolved' | 'review', text }`; its wording does not determine behavior. `checked` requires `reviewedBy` and a valid `reviewedOn` date. Check against the imported description and record the reason; this is distinct from the Attribution Assessment and does not establish permission or book-level attribution. Only checked records may set `stacksWithinEntry`. The drafter flags “stacks with” for review and never sets it itself. Curation status remains operator data.

Shared Situations are declared in `situations` with `key`, `label`, exact case-insensitive `aliases`, reviewer and date. Only those reviewed aliases map automatically; ambiguous/new wording stays local. Unknown shared keys are rejected, including keys in Item Ability dice. Keys are flat and imply nothing else. Promote a local Situation deliberately when a second entry names it.

## Draft, review and resume

The parser handles leading inline/plain numeric notes, several numeric clauses, multi-situation notes, recognized targets, granting-class formulas, readable prose Notes, action numeric conditionals, and bounded Item Ability patterns. The named Common Conditional Modifiers and Weapon Enchant Conditional Modifiers helpers remain excluded from catalog entries and the coverage requirement. The second helper supplies seeds to abilities matched by name; hit/critical dice remain distinct.

Conservative drafts preserve candidate outputs and diagnostics for mechanics the parser cannot complete, but diagnosed drafts do not apply them. Metadata such as an ability's price never covers an unparsed numerical effect. Target-dependent helper abilities require an operator to provide their Situation/choice rather than applying unconditional damage. Unsupported note formulas retain runtime-shaped candidate contributions, with readable Note text and a review diagnostic. The draft is held until checked; once checked, its unsupported formula warning remains and the formula contributes nothing, preserving #228's runtime behavior. The closed parser is reused; no Foundry expression is executed. Rewrites beyond supported variable mappings, such as complex `if(gte(...))` formulas, must be drafted into the closed arithmetic grammar by the operator.

The named Item Ability policies live in [`reviewed-item-ability-policies.json`](../../scripts/catalog/reviewed-item-ability-policies.json), beside the overlay. Each policy cites the exact offline pf1-content 11.4.0 data path, pinned commit and upstream book/page metadata, with a review rationale and date. The table supplies Speed's shared haste Source and the target-dependent helper holds. Draft rationales include the relevant citation. This parser-policy review used local pinned descriptions, without a network lookup or printed-book verification, and does not establish an Attribution Assessment or complete content review.

Read `diagnostics` and compare every output with the imported description. Complete or correct the outputs, clear resolved `unresolved` diagnostics, supply an explicit covered/no-output rationale where appropriate, and mark checked when reviewed. A diagnosed drafted record for a required note, conditional or ability fails coverage even though its binding exists and is not listed as missing. Checked records apply their outputs for either diagnostic kind; retained `review` diagnostics do not fail coverage, while retained `unresolved` mechanics still do. Prose-pass diagnostics appear in `unresolvedDescriptions` and remain outside the required gate.

Resume supplies the existing file:

```sh
pnpm -s catalog:curate --system /path/to/pf1 --content /path/to/pf1-content --candidates /path/to/batch-keys.json --records .scratch/catalog-curation/drafts/records.json --out .scratch/catalog-curation/drafts
```

Valid existing drafts, checks, rationales and outputs are retained. Only absent exact bindings are added. An unchanged rerun writes identical records and adds none. Changed source text/target produces a fresh record and the old binding is reported stale; it never applies. Changed helper seeds replace only the unusable seeded record, reporting `replaced` and resetting its status to drafted. Description/seed disagreements remain unresolved. Removed or retargeted records on present entries are stale; records for entries outside this import are `unused`, not falsely stale.

The prose-only pass visits description candidates containing “vs.”, “against” or “when”, independently of the note requirement:

```sh
pnpm -s catalog:curate --system /path/to/pf1 --content /path/to/pf1-content --candidates /path/to/batch-keys.json --records .scratch/catalog-curation/drafts/records.json --descriptions --out .scratch/catalog-curation/prose
```

It can produce ordinary overlay Modifiers. Unparsed or partially parsed prose receives a review diagnostic and no applicable draft output; it does not fall back to making the entire description a Note. Review and supply explicit outputs before checking it. Optional prose diagnostics do not turn a candidate into a missing-note failure. Reruns add only missing description bindings.

## Reports and the bounded demonstration

`curation.json` itemises `missing`, `stale`, `unused`, `applied` records by status, `unresolvedMechanics`, `unresolvedDescriptions`, and summary counts. `summary.required`, `drafted`, `checked` and `missing` count only required notes, action conditionals and Item Abilities. `summary.descriptions` reports optional prose candidates and their drafted/checked matches separately; prose diagnostics never fail the required gate. Held diagnosed drafts appear in the unresolved lists and matched status counts, but not in `applied`. Draft reports also list `added`, `replaced`, input verification/fingerprints and the canonical records fingerprint. Preview's admission report contains the coverage report and individual missing/unresolved failures; its extraction fingerprint covers applied outputs and curation report. A changed output therefore invalidates existing attribution content bindings.

[`tests/fixtures/curation`](../../tests/fixtures/curation/README.md) commits synthetic category fixtures, two real excluded helpers, initial drafts, the optional prose pass, fixture-only checked/no-output examples, gap-only resume, missing and covered preview reports, and the deterministic public import artifact. Observed command statuses and counts are in [`observed.json`](../../tests/fixtures/curation/observed.json). The tests exercise exact invalidation, raw sanitizer-equivalent changes, stable action IDs, identity remaps, partial resume, helper-only changes, schema rejection, unsupported formulas and real sheet calculation.

This establishes the workflow and bounded coverage gate for #303. It does not curate the upstream corpus, review real content records, complete per-entry attribution, or meet CRB launch review. The enumerated content batches own those steps and commit their own records and reports at each pin bump.

## Structure records (#716)

The archetype and prestige class import from PCGen and the PRD ([#716](https://github.com/AndreasUnunger/EverythingPath/issues/716)) reviews structure by hand before any mapper runs. Its records live in the overlay's `structures` collection, beside the note records; the schema, the gate and the application are in [`scripts/catalog/structure-curation.ts`](../../scripts/catalog/structure-curation.ts).

A structure record binds one entry, a set of its fields and the hash of the upstream records it was reviewed against, and names the review items it settles:

- `externalKey` is the entry's catalog key, usually `everythingpath/<id>`.
- `sourceSha256` comes from `hashStructureSource`: the SHA-256 of the entry's upstream records in merge order, each as its upstream key (`pcgen:<file>#<KEY>` or `prd:<path>#<id>`) and raw text. A PCGen entity is its record line and its `.MOD` lines (a prestige class: its `CLASS:` lines, its level lines and its applied `.MOD` lines); a PRD section is added when one supplies a field. It takes at least one record. Line numbers aren't hashed, since only the KEY is stable. Archer's hash covers `apg_abilities_class.lst:2102` and its `.MOD` line at `:3667`.
- `fields` maps each bound field to its reviewed value. A field is an imported entry field, such as `situationalNotes` or `sources`, or a property of a detail kind, such as `detail.featuresByLevel`. The entry's identity (`externalKey`, `upstreamKey`, `pack`), the whole `detail`, `detail.kind`, `provenance`, `unsupported` and `attributionFrom` can't be bound, and an unknown field such as `detail.parentFeatre` is rejected with the overlay.
- `resolves` lists the review items the record settles, each as `{ kind, id }`: a mapper item's kind and its identity among that entry's items of the kind (for example the PCGen token that raised it), or `{ kind: 'ownedFeature', id: <feature locator> }`.
- `noMechanics: true`, with empty `fields`, is the reviewed disposition that an owned feature has nothing to structure, such as Archer's Safe Shot: not provoking attacks of opportunity with a bow isn't calculated on the sheet. It settles only the owned features it names in `resolves`, never another kind of item.
- `status`, `rationale`, `reviewedBy` and `reviewedOn` work as for note records: `checked` needs a reviewer and date. A record is written `drafted`; a checked one also names in `receipt` the review that confirmed it, which binds its values and `resolves`, and only the orchestrator's record step marks it checked ([Review receipts](README.md#pcgen-sources-716), #757). The receipt check catches unreviewed or accidental `checked` claims, not a determined forger: run directories are ordinary writable files, so only the orchestrator runs the record step, and workers never do.

Records of one entry and hash bind disjoint field sets and settle each item at most once, and a `noMechanics` disposition is the only record for its entry and hash; the overlay is rejected otherwise.

**Application.** A checked record replaces the mapper's output for its bound fields on every entry with its key and source hash, and each replaced field's `provenance` names the record (`{ source: 'overlay', locator: { externalKey, kind: 'structure', target: <field> } }`). Before anything applies, each field must exist on the entry's detail kind and each value must parse unchanged against the imported entry schema: `name: null`, `sources: 0`, a source with a `page` instead of `pages`, or `detail.featuresByLevel` on a class feature fail as `invalid`. A drafted record applies nothing. When the entry's current hash differs from the record's, the record is `stale` and applies nothing: a changed PCGen line, a newly merged `.MOD` line or a PRD section added to the entry all reopen its review. Records for entries outside the import are `unused`.

**Source variants.** Same-key variants in different books stay separate entries with their own hashes (plan §5), so each variant's records apply only to that variant: ISWG's `Lawbringer ~ HK` can take its p.279 citation while AG's keeps its own. When records of two variants of one key bind the same field, they compete. A checked same-identity decision in the identity ledger settles that when it is current, every record it reviewed present at the hash it bound (#716 P6), and its `sources` include every competing variant: the variant it takes `mechanicsFrom` applies and the others are `superseded`. A change to any reviewed record, the superseded one included, makes it stale. Without one, or when a competing variant isn't among the decision's sources, the competing records apply nothing and the entry is held with a `conflicts` entry.

**Coverage gate.** The mappers hand to review what they can't decide: an unmatched replacement, an unchecked casting change, an unchecked requirement, a variant, a conflict, a Product Identity flag, an option or an unsupported kind. The prestige mapper (P4) raises an `uncheckedRequirement` for each requirement it leaves as an `unchecked` clause (its id is the PCGen token; the whole tree has 97), so a prestige class with readable but unchecked prose can't pass until a checked record that binds `prerequisites` settles each one. It also raises a `conflict` for each named requirement exception and PCGen data error, an `uncheckedCasting` for each advance the casting model can't express, `productIdentity` for NAMEISPI and `option` for a Pathfinder Society record. Each review item needs a checked record on its entry and hash that names the item's kind and id in `resolves`; an unrelated checked record doesn't settle it. When the item names fields, the settling record must bind them. Every feature record an archetype or prestige class grants directly needs a checked record naming it as an `ownedFeature`, with reviewed fields or a `noMechanics` disposition, so no feature passes unreviewed. Owned features count by locator: a same-key variant in another book (ISWG's and AG's `Discipline ~ HK`) has its own hash and needs its own record, and a feature two owners share needs one. An entry with an unsettled item, an unreviewed owned feature, an invalid record or a variant conflict is `held` and counted as hand review; the gate passes only when nothing is held. The report lists `held`, `handReview`, `unreviewedFeatures`, `invalid`, `conflicts`, `applied`, `superseded`, `stale` and `unused`, with counts in `summary`.

**Batches.** Each #716 batch ticket (#659–#702 for archetypes, #551–#576 for prestige classes) names its owners with an Import selector, such as `{"source": "#716 PRD/PCGen import", "kind": "archetype", "base_class": "alchemist", "max_candidates": 100}` or `{"source": "#716 PRD/PCGen import", "kind": "prestige", "name_initial": "A", "max_candidates": 100}`. `planImportBatches` in [`scripts/catalog/import.ts`](../../scripts/catalog/import.ts) picks the owners out (archetypes by PCGen's base class, which every archetype owner must name, prestige classes by the initial of their name), orders them by name and then locator, and packs them into ordered sub-batches of at most `max_candidates` keys, never over 100. A sub-batch counts each owner and each distinct feature record its owners grant directly, by locator; nested grants are reviewed with their owner and aren't counted. An owner and its features always share a sub-batch, so a feature two owners in different sub-batches share counts in each. APG's twelve fighter archetypes and their 86 directly owned features fit one batch of 98 keys. In the full PCGen inventory the fighter's 62 archetypes and 347 features take five sub-batches. A batch ticket curates its first sub-batch and reports the rest as separately reviewable overflow. A prestige class is a class definition, so a prestige sub-batch also holds at most three prestige records, the bound `--candidates` enforces. Records count separately, variants included, and same-name variants share a sub-batch where they fit: the three Pathfinder Savant records fill one. In the full PCGen inventory the 99 prestige records take 40 sub-batches over 18 initials. Archetype sub-batches select no class definitions and keep only the key limit.

The PCGen reader (#716 P3) and the mappers (P4, P5) supply the entries, their hashes, the review items and the owned features. The prestige mapper (`mapPrestigeClass`, [`scripts/catalog/pcgen/prestige.ts`](../../scripts/catalog/pcgen/prestige.ts)) supplies a prestige class's entry, hash and review items; its owned features wait for their feature entries. The archetype mapper (`mapArchetype`, [`scripts/catalog/pcgen/archetypes.ts`](../../scripts/catalog/pcgen/archetypes.ts), P5) supplies an archetype's entry, hash and review items, a class feature entry and hash for each feature it owns directly, and those owned features; review items about one owned feature, such as Dandy's Cold favored terrain, sit on that feature's entry, while Archer's Weapon Mastery is held on the archetype until a checked record binds its addition level and its alteration (`detail.adds`, `detail.featureChanges`). Two archetypes of one class that both change class skills each get a `conflict` item from `stackingConflicts`. Until the import wires the mappers in, `catalog:curate` and `catalog:preview` accept an overlay with structure records but don't draft, apply or report them; a drafter's `records.json` carries note records only.

## Admission policies

The owner settled two admission policies on 2026-10-13 (#735). They apply to every batch from then on; re-assessing the records held under the old reading stays under #735.

- **Later-book classes don't hold a spell.** A class from a later book in a spell's class list (`learnedAt.class`, such as arcanist, antipaladin or skald) does not by itself justify holding the spell. Decide the spell on the evidence for the spell itself (#735, S-03).
- **CRB feats on original-source evidence.** A CRB feat can be admitted when the evidence supports its mechanics as the original source states them. PCGen needn't reproduce its prose exactly, so a partial PCGen comparison is not by itself a hold reason (#735, S-04).

## Armor, shield and natural armor bonuses

Armor, shield and natural armor bonuses each have their own AC leaf: `ac.armor`, `ac.shield` and `ac.natural`. A Modifier on `ac` goes to the leaf its bonus type names, and an equipped armor or shield adds its bonus to its own leaf. Bonuses of the same type don't stack (CRB p. 12), but AC adds its leaves together without comparing bonus types across them. So one of these bonuses on `ac.other` stacks with a real armor, shield or natural armor bonus: Cooperative Swarmer's +2 shield bonus on `ac.other` beside a light steel shield (+1) adds 3 to AC instead of 2. Curate these bonuses on `ac` or on their own leaf.

[`tests/catalog/ac-other-defense-bonuses.test.ts`](../../tests/catalog/ac-other-defense-bonuses.test.ts) scans every curated record's Modifiers and fails on an armor, shield or natural armor bonus on `ac.other`, apart from the held violations #734 retargets before their holds clear: Swordplay Deflection, Shield Gauntlet Style, Improvised Defenses, Cornugon Shield (two Modifiers) and Cooperative Swarmer. It also fails on an allowlist entry that no longer matches, so the change that retargets one removes it. Its resolver case shows the stacking with an equipped shield.

## Reviewed change replacements

The overlay appends outputs; it can't replace or drop an upstream change. When the published rule contradicts a raw change's formula, a row in [`reviewed-change-replacements.ts`](../../scripts/catalog/reviewed-change-replacements.ts) replaces that formula for one record. The row names the pinned record, its exact raw change (target, formula and type), the replacement formula, the evidence, and the reviewer and date. The importer maps the replacement instead of the raw formula, keeping the change's target and bonus type. When the upstream change no longer matches exactly, the row stops applying and the raw change imports as before. A replacement changes the entry's content, so the change re-binds the record's Attribution Assessment and every assessment whose content covers the entry, lists them, and goes through the admission review.

## Reviewed description corrections

The overlay appends outputs and the description record binds the whole raw body, so neither can change what an entry's description says. When an owner decision corrects a stated value in the text, a row in [`reviewed-description-corrections.ts`](../../scripts/catalog/reviewed-description-corrections.ts) replaces one exact span of plain text in one record's raw description. The row names the pinned record's upstream key (`<repo>/<_id>`), the SHA-256 of its raw description body (`sourceBody`), the exact span (`from`) and its replacement (`to`), the evidence, and the reviewer and date.

- **Plain text only.** A correction changes text, never markup. The rule is an allow-list, not a list of markup syntaxes:
  - `from` and `to` contain none of `<`, `>`, `&`, `@`, `[`, `]`, `{`, `}`, `"`, `'`, backslash, or a line break. The module refuses such a row when it loads.
  - The span lies inside one text node of the body, parsed by the sanitizer's parser (parse5). That node's raw source must be exactly its text and contain none of those characters either.
  - So a span can't reach into a tag, attribute, entity or comment. It can't sit inside a text node that holds a `@UUID[…]{…}` link or a `[[…]]` inline roll. Nor can it assemble one from neighbouring text.
  - **What users see.** Comments and stripped or kept elements can split a roll or link around a plain node, as in `[[<!---->2d8*3<!---->]]`. So applying also checks the real sanitizer's output (`sanitizeDescription`) for the original and the corrected body:
    - Each span occurs exactly once in the sanitized original, outside every tag.
    - The text run around the span, between the nearest tags of the sanitized output, holds none of `[ ] { } @`.
    - The span intersects no construct (target, options or label) that the real grammar finds in the sanitized HTML or its visible text. The grammar is `constructGrammar`, copied verbatim from the code that reads descriptions, never hand-written. A test compares its PF1 patterns, pattern for pattern, with the pinned PF1 v11.11 source (`tests/fixtures/pinned/pf1/module/chat/text-enrichers.mjs` and `module/utils/lib.mjs`):
      - every PF1 v11.11 text enricher: `@Apply`, `@Toggle`, `@Save`, `@Ability`, `@Skill`, `@Use`, `@Action`, `@Heal`/`@Damage`, `@Browse`, `@Weight`, `@Distance`, `@Condition`, `@Draw` and `@Source`;
      - the PF1 and Foundry inline roll `[[…]]`;
      - the importer's own link and roll patterns;
      - Foundry's `@<Type>[target]{label}` document links, for any type name.
    - The sanitized correction equals the sanitized original with exactly those substitutions and nothing else, and the grammar's constructs (kind, text and order) are identical before and after.
  - Together, no catalog link or closure edge can appear, vanish or change, and no roll can change. Only the entry's own content fingerprint moves.
  - A value inside a table cell is corrected by its plain text: `100 lbs.` → `110 lbs.`, not the whole `<td>…</td>`.
- **Applying.** `mapEntry` applies a record's rows to its raw body, then sanitizes the result as the entry's `description`. A row applies only when the body's hash equals its `descriptionSha256`, its span occurs exactly once, and it passes the plain-text rule. Rows of one record apply together, against the original text.
- **Refused rows.** When any row of a record fails a check, none of that record's rows applies. The entry gets one `description.correction` unsupported issue per row. A refused row's issue says which check failed: the description changed since review, the span or replacement is not plain text, the span is missing or repeated, the span is not inside one plain text node, the spans overlap, or a sanitized-output check failed (the span isn't exactly once there, it's inside a tag, its text run holds `[ ] { } @`, it's inside an enricher, link or inline roll, or the sanitized result or its constructs change beyond the spans). The record's other rows report that they were not applied. A raw-text change already moves the record's content binding, so its assessment reopens anyway.
- **Loading.** The module also refuses, when it loads, a row with an empty or malformed field, and two rows of one record with the same span or spans that could overlap.
- **Derived texts stay raw.** Only the entry's own `description` changes. The description curation record (`collectDescriptionInputs`), the race description re-homes, the race ability-trait line and the inventory `descriptionSha256` keep reading and hashing the raw record.
- **Re-binding.** A row changes the entry's content, so adding one re-binds the record's Attribution Assessment and every assessment whose content covers the entry, lists them, and goes through the admission review, as for a change replacement.

The table holds four rows: the Elf and Half-Elf male base weights, corrected to PCGen's Core Essentials biosettings under the owner's 2026-11-01 decision (#328 Step B, [races-328.md](races-328.md#step-b-elf-and-half-elf-male-base-weight)). [`reviewed-description-corrections.test.ts`](../../tests/catalog/reviewed-description-corrections.test.ts) checks every rule with test-only rows on the pinned Elf and Half-Elf, sweeps every pinned pf1 and pf1-content description to show that every span touching markup is refused, and that every run inside a grammar construct is refused when comments split it into its own text node (by the text-run check) or a kept tag does (by the grammar). It checks that each production row applies cleanly to its pinned record, that the Step B rows equal PCGen's base weight and the range base + 2…16 × multiplier, and that the copied grammar equals the pinned PF1 source. The table isn't registered for automatic row merges between parallel batches (`table-merge.ts`, `prep_table_files`): its rows are built through `parseDescriptionCorrections` with shared fields, which the merge's literal-row parser can't split, so two batches that both add rows need a hand merge.

## Notice holds from content batches

A batch that cannot accept a notice records the hold in its legal evidence file under `scripts/catalog/legal/`, in one of two shapes: a `holds[]` entry with `id` and the held Registry `noticeKey` (notice-review batches such as #264/#265), or a `noticeRequirements[]` entry with a non-null `holdId`, whose `book` and `registryKeys` are held (content batches such as #328–#330). Several batches may name the same hold ID.

Two more evidence fields name held notices:

- `relatedNoticeKeys` on a `holds[]` entry lists further Registry keys the same hold covers, such as the other line of a variant comparison (#285). They are held notices of that hold, like its `noticeKey`.
- `previouslyReviewedIn` names the evidence file of an earlier batch that already reviewed a notice, so the later batch records no new hold for it. On an `inventoryOccurrences[]` entry it is one path or `null` (#271); on a `noticeRequirements[]` entry it is a list of paths (#523). Each named file must record an enforced hold on that notice. A requirement without a `holdId` must instead appear without a hold in each named file.

The admission gate enforces these holds through [`scripts/catalog/legal/held-notices.json`](../../scripts/catalog/legal/held-notices.json): one entry per hold ID with every held notice code and the evidence files that record it. Add each new batch hold there in the same change as its evidence; `tests/catalog/notice-holds.test.ts` scans every evidence file in that directory and fails on a recorded hold that is missing or narrower in `held-notices.json`, on an entry no evidence records, or on a `previouslyReviewedIn` notice that the named file does not hold. Remove an entry only with the evidence resolving the hold.

## Notice dependencies

A candidate whose rules depend on another book must list that book's notice in `requiredNotices`. `pnpm catalog:notice-deps` checks every curated candidate (one with `requiredNotices`) in the batch inventories under `scripts/catalog/legal/` against the inherited-rule dependencies the inventory itself records: `inheritedRuleNotices`, `fullContentReview.inheritedRules` and `inheritedNoticeReview` books; the cited sources of `inheritedRuleSourceEvidence` and `mechanicsReview.inheritedRuleEvidence` records (any one of a record's books suffices, so the rule can miss a gap but never fails falsely); and the notices of each `noticeHoldIds` hold. Each dependency's notice must be required, matched by code or Registry identifier, and be a reviewed Registry notice or held in `held-notices.json`. Prose is never read for this rule. Linked records are not dependencies, since links include prerequisite feats: a `linkedContentReview` record whose books are not required prints a warning, and links to records in other inventories are not checked. `tests/catalog/notice-dependencies.test.ts` runs the same check over the committed inventories.

A gap fails unless [`notice-dependency-waivers.json`](../../scripts/catalog/legal/notice-dependency-waivers.json) waives that candidate key and notice with a reason, reviewer and date. A waiver that no longer matches a gap fails as stale; remove it in the change that fixes the inventory. Record dependencies in these fields when curating; a dependency left only in prose is not checked.

The command also prints warnings, never failures, when a candidate's reviewed description names a term from the reviewed table in [`notice-dependencies.ts`](../../scripts/catalog/notice-dependencies.ts) without that book's notice: stamina (PZO1131), Story feat or Completion Benefit (PZO1125), mythic (PZO1126), advanced simple template (PZO1112), mascot (PZO9454), Wolf Style (PZO9439) and Linnorm Style (PZO9470). Each term cites the review finding it comes from (#337, #339, #341, #520 and #522). Check each warning against the text; record a real dependency, or leave a false positive as it is.

## Parallel batches

Two or three curation batches can run in parallel worktrees and land one at a time. Every batch edits five shared files: the Curation Overlay [`reviewed-curation.json`](../../scripts/catalog/reviewed-curation.json), [`attribution-assessments.json`](../../src/lib/catalog/data/attribution-assessments.json), [`attribution-evidence.json`](../../src/lib/catalog/data/attribution-evidence.json), the Section 15 Registry [`section15-registry.json`](../../src/lib/catalog/data/section15-registry.json) and [`held-notices.json`](../../scripts/catalog/legal/held-notices.json). Each file has one canonical form, written by [`scripts/catalog/data-files.ts`](../../scripts/catalog/data-files.ts), so a batch changes only the lines of its own entries:

- Top-level entries are sorted by stable identity: overlay records by exact binding (`externalKey`, kind, target, action and conditional IDs, text hash), structure records by `externalKey`, field set and `sourceSha256`, shared Situations by `key`, assessments by `externalKey`, evidence by ID, Registry notices by code and notice holds by `id`. Readers look entries up by identity, so this order carries no meaning. The drafter matches wording to the first Situation with that alias, so two Situations may not share an alias.
- Fields follow schema order; identity-keyed maps, such as an assessment's `evidenceFingerprints`, are sorted. Nested arrays (outputs, diagnostics, aliases, provenance, required notices, a hold's notices) keep their authored order. A structure record's `fields` are sorted by field, and an empty `structures` collection is left out.
- Two-space indentation and a trailing newline. The overlay escapes every non-ASCII character as `\uXXXX`; the other files keep UTF-8 text.
- The evidence file stores repeated evidence once (#744). Its root holds `evidence`, each entry by ID, and `shared`, blobs named by the first 24 hex characters of the SHA-256 of their text. Every JSON value of 512 bytes or more inside an entry's content is a blob, and blobs nest. An entry keeps its text either as literal `content` (prose, or JSON with nothing that large) or as `parts`: literal text and `{ "ref": … }` blob references, one per line, which join to exactly the reviewed content. Each entry's encoding depends only on its own content. Every reader, the admission gate and every fingerprint see the decoded `{ content, revoked?, conclusion? }` entries, through [`attribution-evidence-codec.ts`](../../src/lib/catalog/attribution-evidence-codec.ts), which refuses a missing, mismatched, cyclic or unused blob.

The drafter writes `records.json` in this form. After copying reviewed records into the overlay, or editing any of these files by hand, run `pnpm catalog:format`. Write a new or changed evidence entry with plain `content`; `pnpm catalog:format` encodes it and drops blobs no entry uses any more. It also accepts the earlier plain-map evidence file. `pnpm catalog:format --check` writes nothing and fails on any non-canonical file, including evidence still in the plain form, an unencoded large value or an unused blob, and on a missing or mismatched blob or an evidence ID or blob named twice; `tests/catalog/data-files.test.ts` runs the same check.

To land a batch after another has merged:

1. Rebase the batch branch onto the updated base: `git rebase <base>`.
2. When any of the five files or the two tables below conflicts, run `pnpm catalog:merge`. It reads Git's base, ours and theirs versions of each conflicted data file and merges them by identity: entries added on either side are kept, and a change or deletion made on one side wins. During a rebase, “ours” is the base branch and “theirs” is the batch commit being replayed. The merged file is validated and written in canonical form. Evidence merges by decoded entry, refuses an evidence ID named twice on any side, and accepts the earlier plain-map form on any side, so a branch from before #744 rebases the same way; the merged file keeps only the blobs its entries use. It merges the two TypeScript tables batches append rows to the same way, row by row: `reviewedChangeReplacements` in `scripts/catalog/reviewed-change-replacements.ts` (a row is identified by `externalKey` and `change`) and `danglingCatalogLinks` in `tests/catalog/cross-batch-bindings.ts` (by `uuid`). The result keeps the base's rows, then the rows ours added, then those theirs added, takes a row changed on one side only, and is formatted with Prettier. Resolve other conflicted files as usual.
3. `pnpm catalog:merge` refuses, and leaves that file untouched, when both sides changed the same identity differently (for example two different definitions of one shared Situation, Registry notice, notice hold or assessment), when one side deleted an entry the other changed, when two Situations claim one alias, when two Registry notices newly claim one identifier, or when the merged file fails its schema (such as a record naming a Situation the other side removed). For a table it also refuses a row removed or reordered on either side, a row both sides changed or added differently, and any change outside the table literal. Its report names each identity and the differing fields. Decide the correct content with both batches' reviews, edit the file, then run `pnpm catalog:format`.
4. `git add` the resolved files, then `git rebase --continue`.
5. Run `pnpm catalog:format --check`, then re-run the batch's gates: its tests, `pnpm test tests/catalog`, and the curation previews and admission runs its ticket documents. A merge of data files does not re-review content; a rebase that changes another batch's evidence or Registry entries can reopen assessments, which the gates report.

Explicit versions can also be merged into a file: `pnpm catalog:merge scripts/catalog/reviewed-curation.json --base base.json --ours ours.json --theirs theirs.json`. Without `--base`, the merge is a plain union by identity; a table needs `--base`.

`cur-prep.sh` and `land-queue.sh` (`scripts/orchestration/`) run `pnpm catalog:merge` when a rebase stops on these files only (`prep_merge_re` in `prep-lib.sh`); a conflict it leaves unresolved, or in any other file, stops them for a hand resolution.

## Preservation checks

A batch's tests check what the batch owns, not the rest of the repository. Owner decision of 2026-10-13 (#749), generalising the curation amendment of 2026-10-12:

- **Own rows, as recorded.** Each batch's description records, Attribution Assessments, evidence entries and holds stay as its inventory (`scripts/catalog/legal/<batch>.json`) recorded them: the checked description and its text hash (for an Item Ability, its checked `itemAbility` record, which binds the same description, since the prose pass skips Item Abilities: #501), the assessment's status, required notices, evidence ID, content and mapping fingerprints and whole-content hold, the evidence entry's fingerprint and source hash, and its notice holds with their notices. The evidence fingerprint comes from the inventory's binding snapshot; #343 and #345 to #347 recorded none, so [`recorded-evidence-baselines.json`](../../tests/catalog/recorded-evidence-baselines.json) keeps the evidence hashes that the next batch's historical manifest committed for them, derived once and checked against the data at the time. [`tests/catalog/batch-ownership.ts`](../../tests/catalog/batch-ownership.ts) implements these checks for the earlier batches; [`batch-ownership.test.ts`](../../tests/catalog/batch-ownership.test.ts) shows each one fails when such a row is altered or removed.
- **Shared files by entry.** The Registry, notice reviews, held notices, the Curation Overlay, assessments, evidence and the legal README are checked only for the batch's own entries, never byte for byte and never for other batches' rows. A Registry notice the batch's review cited must keep its key (and a hash key must still name the text the review hashed); its current text is checked only through the batch's assessment bindings.
- **Bindings against current data.** An assessment's notice fingerprints must match the current Registry, and a recorded binding snapshot must match the current binding's content, mapping and evidence fingerprints. A reviewed notice correction, whether a new record or an in-place edit, keeps earlier batches passing once it re-binds the assessments that require the notice.
- **Release fixtures against their own identity.** A committed release fixture is checked against the calculation identity it recorded, which must be one the identities module has known (current, retained prior or superseded), not against the current one. [Rotating the calculation identities](releases.md#rotate-the-calculation-identities) therefore leaves earlier batches passing.
- **No infrastructure freezes.** Tests do not hash `package.json`, the lockfile, Vitest or ESLint configuration, scripts, skills, brief templates, other batches' inventories or fixtures, or the repository's file list.

Earlier batches' whole-history manifests (`preserved.json`, `original-identities.json`, `protected-context.json` and the binding proofs) stay on disk unchanged until the historical cleanup (#744); their tests no longer check them. New batches add no such manifests: keep the shared files' diff to the batch's own keys and rely on `pnpm test tests/catalog`, `catalog:pin`, `catalog:notice-deps` and `catalog:format --check`.

### Protected and governing records

Batches before #749 kept some records' Notes empty so earlier batches' frozen bindings wouldn't change: protected roots, keys that appear in earlier batches' fixtures, and bodies that govern another entry. Since #749 the checks compare bindings with current data, so a batch completes such a record's Note from the evidence instead. A Note changes the entry's content fingerprint, so the curator lists, in the batch report, every content binding and dependent Attribution Assessment it changes: the entry's own, and each entry whose binding covers it as a governing or linked body, with its batch and the inventory and test that record it. The change re-binds each of them, and the curation review checks every listed one and that the list is complete. Filling the Notes earlier batches left empty, and the historical artifact cleanup, stay under #744.

### Cross-batch content bindings (#756)

An assessment's content fingerprint hashes every whole entry in its full-corpus content closure, curated Modifiers and Notes included. So when a batch curates an entry inside an earlier batch's closure (a linked body, a shared target, a related variant), the earlier assessment goes stale. The earlier batch's tests re-bind against its own fixture copy of that entry, so they keep passing. #370 found three such cases with #369 and #371.

**Rule:** the later-landing batch re-binds every earlier assessment whose closure it changes. It updates the earlier batch's fixture copy of the changed entry, re-binds the assessment with `buildAssessmentBinding` over a full `catalog:preview`, and updates that batch's inventory `currentBinding`. It changes no disposition, evidence, notice or hold, and lists each re-bound assessment in its report, as for [protected and governing records](#protected-and-governing-records).

**Check:** [`cross-batch-bindings.test.ts`](../../tests/catalog/cross-batch-bindings.test.ts) enforces the rule in prep and in the landing gate. It reads only committed fixtures (a few seconds, no preview run).

- **Staleness.** For every batch fixture (`preview.json`, `binding-preview.json`, and the registered #738 full-context supplement), the check compares each copy of an entry another batch owns with that batch's own fixture entry. That batch's tests check its fixture entry against a fresh import. It compares whole entries, every curation-derived field included: Modifiers, Notes, `detail`, `sourceKey` and the `unsupported` diagnostics. It normalizes only two proven import-scope differences:
  - A bounded import strips description links to entries outside its selection and reports each one as `description.link`.
  - A race lists only the Racial Traits its import included and keeps the mechanics of the rest (#719), so a race whose list is a strict subset of the other copy's is skipped. Curation never changes that list. An alternate trait's `replaces`, which #721 resolves through curation, is compared.

  Where a copy differs, the check re-binds the fixture batch's assessments with the owner's entry in place and fails on every binding that changes. The failure names the assessment, its recorded fingerprint, and the batch and entry that changed. Accepted stale bindings are pinned with their recorded and current fingerprints, so further drift fails too.

- **Coverage.** Every assessed record's closure must be committed in its batch's fixtures. A fixture file holds a closure when every key the closure reaches is in it, and no entry in the closure had a link to a catalog entry stripped. A bounded import strips links to entries outside its selection, so each stripped link into a pack the importer maps is a dependency the file lacks. Links into excluded or unassigned packs never resolve. One link into a mapped pack names a record the pinned sources lack, and is listed in the test. The check fails on any batch with an assessment whose closure no fixture file holds, or with no fixture entry at all. A new batch therefore commits its full-corpus closures, as the traits batches do in `preview.json` (`closure`) and #355 and #520 to #536 do in `binding-preview.json`. Batches with no links outside themselves, such as feats #334 to #366, need no copies.

The #738 supplement is registered with each owning batch for its 99 roots. Its entries never supply owner truth: both roots and dependencies are compared against the ordinary owner fixtures, including roots owned by the same batch. Its complete closures also participate in coverage checks; the historical bounded extraction assertions still replay separately.

The full-corpus re-bind stays the authority. The check's re-bound fingerprint can differ from it where the copy's own import scope does.

### Test memory

Each Vitest process gets an explicit V8 heap instead of the size Node derives from the cgroup: 2,096 MB under the curator caps (12G hard, 8G soft), which #536's test outgrew at #544, and 4,144 MB under the gate caps (15G, no soft limit: the smallest cap that keeps it; 14.5G and below give 2,096 MB; [gate memory](../agents/orchestration/operations.md#gate-memory)). The `test` and `test:watch` scripts give the parent 4,096 MB on its own `node` command line: it holds the module graph, and #538 was a parent OOM. Each worker, and every CLI a test spawns, gets 3,072 MB through `NODE_OPTIONS` (#744): Vitest passes its forks the environment but not the parent's flags, and a spawned CLI inherits the worker's environment. `tests/test-heap-limits.test.ts` checks the worker and CLI limit. `scripts/orchestration/triage-failures.sh` still exports 4,096 MB for its single-test retries, which run outside the scripts. A heap flag bounds one process, not the sum: at two workers that is 4 + 2 × 3 GB of ceilings, plus the CLIs the workers spawn and their esbuild, which no flag caps.

The CLI default paths (`catalog:preview` and `catalog:release` without `--attribution`) read the committed attribution files and decode them, as `catalog:conditions` does, instead of having tsx and esbuild compile the 93 MB evidence JSON into a module.
