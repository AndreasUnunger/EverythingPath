# Private Catalog Release preparation

Ticket [#310](https://github.com/AndreasUnunger/EverythingPath/issues/310) adds numbered immutable artifacts and private resumable preparation. These commands do not activate content, redirect active references, recalculate current Characters or change the initial migration's authority. #318 adds private bounded facts reconciliation below; activation remains a later ticket.

## Build the exact artifact

Use clean upstream checkouts at the pins documented in [the import runbook](README.md), reviewed attribution and curation inputs, and the required schema/calculation identities. The current calculation identity lives in [runtime-compatibility.ts](../../src/lib/catalog/runtime-compatibility.ts).

**Before first activation:** no Catalog Release has ever been activated, so the calculation compatibility identity is provisional. For an intentional calculator behavior change, review the change and its runtime dependencies. When calculator imports or reexports change, review new dependencies transitively and explicitly add any calculation implementation files to both `catalogCalculationV1Files` and the test's independent file list; update its exact import and reexport expectations as well. Keep the existing implementation files covered and the dependency assertions intact. Recompute SHA-256 using the unchanged algorithm in [catalogRuntimeCompatibility.test.ts](../../tests/catalogRuntimeCompatibility.test.ts): hash each path, a NUL byte, its exact file bytes and a NUL byte, in the explicit closure's order. In the same change, update the runtime pin, the test's independent literal expectation and current recorded expectations (including the build example below). Do not rewrite historical immutable artifacts or their observed evidence; any new preparation must use a fresh release number and the current identity. This procedure does not require a separate retained calculation implementation before first activation.

The earlier retained `sha256:65b39be01f2e0a0ab0abc5cf9c626b4344ed2e40f60fb1b4418ae7b9d509e6fd` identity is superseded and is rejected. This narrow adapter preserves that behavior because #318 leaves those default calculations and bundled casting-table bytes unchanged; its paired behavioral test also pins the exact bundled bytes.
```sh
pnpm catalog:release build \
  --number 1 \
  --schema character-sheet-v1 \
  --calculation sha256:10de1531a3f695d0eb5a42a632047548ca7f1afd4c8b59e48d9804ec940dbc07 \
  --system /path/to/foundryvtt-pathfinder1 \
  --content /path/to/pf1-content \
  --artifact .catalog-preview/release-1/release.json
```

`--attribution`, `--curation`, `--remaps` and `--legal` select explicit reviewed JSON inputs instead of the committed defaults. `--previous` supplies the complete artifact of the authoritative active release when one exists. The number must increase beyond that comparison base. The backend checks the declared base number and artifact fingerprint against its actual active release, so a prepared private artifact cannot masquerade as an active comparison base. A fresh local directory does not grant reuse of a number already registered with the backend.

`--rule-resources PATH` supplies an array of `{ "key": "builtin:stable-name", "payload": ... }` supporting-resource records. Their structured bodies are frozen in the artifact, not merely hashed as input. The application's `convex/lib/representativeClassCatalog.ts`, `convex/lib/representativeRaceCatalog.ts` and `convex/lib/representativeArchetypeCatalog.ts` seed sources and definitions are always captured as `builtin:representative-class-catalog`, `builtin:representative-race-catalog` and `builtin:representative-archetype-catalog`, with their source fingerprints and compatibility identities. The class resource also captures exact Fighter/Rogue feature schedules linked to the archetype resource. These representative fixtures do not certify complete class, race or archetype curation, and capturing them as supporting resources does not admit them as new selectable content. The reviewed `scripts/catalog/reviewed-casting-tables.json` resource is always captured as `builtin:casting-tables`, including its complete cited table rows and casting-class metadata, source fingerprint and compatibility identities. It supplies seven shared families through level 20 plus adept, extract, Unchained summoner and occultist overrides; occultist availability is explicit while its choice-dependent known count stays unspecified. This supporting resource does not admit class definitions as selectable content. [Reviewed CRB conditions](conditions.md) are local selectable content supplied through `appendConditionResources` and the ordinary attribution/curation seam. Preview opts in with `catalog:preview --conditions`; `catalog:release build` has no conditions flag. A programmatic release build must explicitly append the candidates and fingerprint their `conditionReleaseResourcePaths` as documented in condition curation. New local content must use the attribution/curation import seam rather than disguising selectable definitions as authored resources.

The output directory must be empty or contain only its release artifact, and cannot overlap source inputs. Output is written only after the admission, curation, inventory/structure/reference and legal gates pass. Holds remain valid individually reported outcomes, including changed accepted assessments. A failing gate creates no release artifact. Repeating an identical build at the same path leaves identical bytes; changed inputs/output at that path fail without overwriting it. The immutable backend binding also rejects reuse across independent local directories.

The manifest fingerprints nine explicit input categories: upstream pins/content and verification, remaps, curation, local data/comparison provenance, importer/parser dependencies, sanitizers, rule resources, legal inputs and attribution. The local source graph includes the importer's mapping, formula, inventory/configuration and curation dependencies. The parsers fingerprint includes `src/lib/character-sheet.ts` because its shared schemas validate and shape imported definitions. Editing that file changes a declared release input and requires a new release number, even when the particular fixture's normalized output stays equal. Parser dependency identities also include the installed versions and exact relevant lock entries/integrities for YAML, parse5, its entities dependency and Zod. No whole-repository or whole-lockfile hash is used, and unrelated application changes do not alter a release.

Input fingerprints bind required schema and calculation identities and the exact active comparison base. Each deterministic batch has a SHA-256 fingerprint, row count and UTF-8 byte count; the output fingerprint commits the ordered batch descriptors. The artifact fingerprint commits the complete manifest excluding only its own fingerprint. The shared JSON validator and SHA implementation run in both Node and Convex; hashing uses WebCrypto's `crypto.subtle.digest('SHA-256', ...)` without filesystem or Node crypto dependencies.

Batches contain at most 100 rows and 512,000 canonical JSON bytes. The manifest allows at most 1,024 batches and 131,072 bytes. A single oversized row or manifest fails clearly before remote preparation. Row ordering and batching are deterministic; manual edits to an artifact are rejected by independent output verification before any remote call.

## Prepare, resume and inspect

Preparation uses Convex's installed administrative HTTP client, including the same internal-function seam used by its CLI. JSON travels in request bodies, so large records are not constrained by shell argument lengths. It never pushes code or runs codegen. Name the target explicitly, supply its matching URL, and read the deployment credential from a separate non-environment file. The command does not read `.env` files or infer a deployment from environment variables.

```sh
pnpm catalog:release prepare \
  --artifact .catalog-preview/release-1/release.json \
  --deployment-name your-preview \
  --deployment-url https://your-preview.convex.cloud \
  --target-kind preview \
  --admin-key-file /secure/path/convex-admin.key \
  --write-epoch 0

pnpm catalog:release inspect \
  --number 1 \
  --deployment-name your-preview \
  --deployment-url https://your-preview.convex.cloud \
  --target-kind preview \
  --admin-key-file /secure/path/convex-admin.key
```

Target kinds are `preview`, `development` and `production`; naming the target does not deploy or activate it. Follow the repository's deployment-selection and production-consent procedure when an agent is authorized to issue remote operations. This implementation's evidence executes no remote commands.

`begin` registers the immutable candidate against the active comparison base. `writeBatch` validates a complete bounded batch and its committed fingerprint before transactional writes. `finalize` requires the complete batch inventory, all five gate-certified report summaries and legal inputs. Only then does status become `prepared`. These operator writers use the general Write Gate class: after initial cutover they can prepare candidates under sheet authority while ordinary gameplay continues. Legacy Character writers remain fenced under sheet authority. A closed maintenance gate blocks every gated writer, including preparation, and stale epochs reject both classes. `--write-epoch` defaults to zero and is passed unchanged to every mutation; use the current open gate's epoch from authoritative migration status. The command never refreshes an epoch or replays a refused gameplay command automatically.

After interruption or a lost response, inspect the authoritative candidate, then rerun the same `prepare` command and artifact. Preparation resumes at the recorded next batch; exact batch retries and prepared retries are idempotent. An input/output change requires a manually incremented number and a new artifact. Candidate definitions/resources/remaps live in separate private rows and never enter ordinary pickers or current sheets. Workers cannot replace an existing number's manifest or write after it is prepared.

Inspect report or payload rows with a bounded page:

```sh
pnpm catalog:release inspect \
  --number 1 --kind report --limit 25 \
  --deployment-name your-preview \
  --deployment-url https://your-preview.convex.cloud \
  --target-kind preview \
  --admin-key-file /secure/path/convex-admin.key
```

Use the returned `continueCursor` as `--cursor` for the next page until `isDone`. Kinds are `definition`, `resource`, `remap`, `report` and `legal`; every page enforces row and byte read limits. Status inspection returns the immutable manifest, state, base release, next batch and staged counts.

## Committed reports and legal data

The artifact stages only newly admitted upstream definitions/resources and reviewed applied remaps, plus explicit authored supporting resources. It always contains five report summaries and individually keyed records:

- `content`: normalized added/changed/unchanged definitions, complete inventory records/pack coverage and unsupported details.
- `resources`: normalized upstream/authored resource changes and captured identities.
- `holds`: individual holds, dependent omissions, retained exceptions, failures/outstanding notices and the exact retained-required-notice certificate.
- `retirement`: held/removed prior identities and their last usable bodies, kinds and fingerprints. These bodies propagate across successive held/retired releases and never become new selections.
- `curation`: passed coverage, counts, missing/stale/applied/unused records and unresolved mechanics/description records.

The four legal rows persist `requiredNotices`, `permanentNoticeSuperset`, the exact Section 15 registry and legal resources. Notice versions are preserved by `(id,text)` across prior releases. Held-only books never become requirements for unrelated content. Each outstanding retained notice must be covered by the gate's per-code retained certificate; an unrelated exception count cannot authorize a missing notice. The public legal read selects these inputs only through a prepared active release and returns null when none exists. The frontend uses committed defaults for null or unavailable backend queries, so publishing the frontend before the backend does not interrupt the legal page. Preparation does not alter that public selection.

The readiness query checks the prepared candidate's required schema/calculation identities and active comparison base. It is a compatibility hook for later activation and does not claim that facts, discovery, frontend readiness or cutover are complete.

## Reconcile candidate Character facts

After `prepare` has completed, run:

```sh
pnpm catalog:release reconcile \
  --number 2 \
  --deployment-name your-preview \
  --deployment-url https://your-preview.convex.cloud \
  --target-kind preview \
  --admin-key-file /secure/path/convex-admin.key \
  --write-epoch 0 \
  --max-steps 100
```

`start` registers a private impact run before discovery. Discovery processes batches of at most 4 candidate or comparison definitions, retaining both sides' keyed Spell Effect, casting-list and granted-list relationships. It then processes batches of at most 32 prepared Characters; legacy Characters are excluded by the sheet-mode index range. Old and new sheet/catalog references share the Catalog Copy reference-field list, including nested Grants, future class features, Archetypes, weapon references and dormant selections. Only local definitions actually referenced by sheet state begin the dependency traversal; unused customizations cannot fail a run. Changed Spell identities enumerate matching global and private imported definitions through `catalogEntry.by_ruleIdentity` in bounded batches, then use paginated reverse lookups through `spellCatalogIndex.by_ruleIdentity`, with `by_catalogEntryId` fallback for retained index rows, rather than walking every Spell in each casting list. Catalog Copies retain their own bodies: provenance alone does not make a copy depend on its original. Retained references to globals still follow candidate bodies. A calculation identity change includes all sheets; notices alone cause no candidate calculation.

While a run is active, every shared sheet update marks only that Character’s candidate work dirty in its active-write transaction. Edits never patch a shared run counter or control row; operators derive pending/failed counts from work state. Missing or inactive run registration leaves ordinary editing available and is reported through operator status. This includes base/local-definition edits, detach/customize, new sheets, newly introduced dependencies and archive/delete, including private Characters without a militia. The ordinary edit updates active facts normally and never calls the candidate calculator. Workers read the latest sheet and calculate candidate permanent facts with the same server facts mapping. `complete` checks the current run/base, the dirty revision and a fresh input/result fingerprint before clearing work. An intervening edit refuses that completion. Ready work records its facts comparison as `hasFactsChanged`; failed, unaffected, deleted or unprepared outcomes clear prior facts, that flag and impact reasons. Work inspection advances its cursor past refused completions so other Characters can progress, then starts a new pass if dirty work remains. No Character, campaign or militia snapshot is restored; current sheet selections and unrelated militia state remain live.

Output reports the run ID, `isDiscoveryComplete`, `pendingCount`, `failedCount`, `isReady`, `stepCount`, `staleCompletionCount` and why it stopped. Each dirty/failed status page reads at most 1,024 rows and 1 MiB; `hasTruncatedCounts: true` means the reported counts omit further rows and must not be treated as totals. `--max-steps` bounds each invocation; rerunning resumes the active run for the same immutable release. `--retry-failed` explicitly dirties failed Character work and retries a recorded discovery failure. A deterministic unsupported body or oversized dependency still fails visibly and requires correcting the implementation or preparing a new numbered artifact. After a lost response rerun the same command; completed revisions remain inspectable and cannot be replaced by an obsolete worker. Current-run, newest-preparation and immutable-base checks fence obsolete commands. All reconciliation mutations use the general Write Gate and unchanged explicit epoch; the command never reopens a closed gate.

`finish` rechecks discovery and dirty/failed work, marks a ready run and clears its control registration. The command reports `ready` only after this succeeds. Later edits keep active state current; starting reconciliation again creates a fresh run against those inputs. `abandon` marks the run abandoned and clears its registration without changing sheets or the prepared artifact; it refuses a ready run so retained evidence stays protected. Starting another run supersedes the previous registered run. Preparing a newer numbered candidate also supersedes active tracking and clears its registration. Status and `finish` recheck the current preparation and comparison base, so retained ready evidence does not certify a changed base.

For retention, invoke private `catalogReleaseImpact:cleanup` with `{runId, writeEpoch}` repeatedly until it returns `true`. Each invocation removes at most 32 work, edge or change rows, from one table at a time, then removes the empty run on a later invocation. Cleanup throws `Catalog impact run is still active; finish or abandon it before cleanup` for a still-current active run, so a repeat-until-`true` loop must stop on that error rather than retry; an obsolete comparison base or superseded preparation makes the run eligible. It clears matching control registration and retains the latest ready run per Catalog Release together with its evidence. A retained ready run returning `true` means cleanup is complete, not that its evidence was deleted. Earlier ready, abandoned and superseded runs are removable. Cleanup uses the same current Write Epoch and open Write Gate as the other operators; it does not run automatically.

This implementation certifies representative sheets with at most 128 sheet rows; 256 reachable catalog/keyed dependencies and 256 relationships; 32 resources per release; and 1 MiB bounded child/resource pages and a shared 1 MiB budget for raw candidate reads, including discarded release metadata and complete Grant/feature/campaign-copy target documents. A definition may supply at most 128 candidate class features, modifiers or keyed relationships. Definition discovery pages read at most 4 rows and 512,000 bytes; prepared-Character pages read at most 32 rows and 512,000 bytes; reverse Spell-index pages read at most 8 rows and 512,000 bytes, leaving room to validate each referenced body within Convex transaction limits; work inspection accepts 32 rows and 512,000 bytes. Exceeding a limit records failed work or a discovery failure and preserves active editing, rather than claiming reconciliation is complete.

The candidate adapter supports existing stable global identities, prepared imported Spells, representative normalized feat/trait/feature, class, race, Spell and Spell Effect bodies and existing-ID Grants. It follows retained local Grants by Catalog Entry ID and both old/new class-feature closures. Imported class features name stable `externalKey` identities that resolve to existing global Catalog Entry IDs; imported definitions do not declare arbitrary Grant bodies. A new referenced identity with no usable global row, an incompatible kind, unsupported casting metadata or a body the prepared resolver cannot validate produces failed work. Catalog Copy and homebrew bodies stay independent. Complete movement/link dependencies and the full imported body adapter remain later work.

`builtin:casting-tables` uses the production artifact wrapper's `definitions` field, validated by `reviewedCastingTablesSchema`, as explicit candidate resources. Both current and permanent projections consume those rows. `builtin:representative-class-catalog` and `builtin:representative-race-catalog` initialize recorded defaults and are not live calculation dependencies; publication never reapplies them. The current casting resource affects spell slots rather than Militia Character Facts, so worker evaluation returns bounded transient `castingEvidence` while persisting only facts. Unknown resources are not assumed to replace bundled calculations; future live resource types must add their dependency and resolver context before they can be certified.
