Ticket [#310](https://github.com/AndreasUnunger/EverythingPath/issues/310) adds numbered immutable artifacts and private resumable preparation. These commands do not activate content, redirect active references, recalculate current Characters or change the initial migration's authority. #318 adds private bounded facts reconciliation below; [#327](https://github.com/AndreasUnunger/EverythingPath/issues/327) adds explicit coherent activation for prepared/fixture data. ## Build the exact artifact

Use clean upstream checkouts at the pins documented in [the import runbook](README.md), reviewed attribution and curation inputs, and the required schema/calculation identities. The current, retained prior and superseded calculation identities live only in [calculation-identities.ts](../../src/lib/catalog/calculation-identities.ts); [runtime-compatibility.ts](../../src/lib/catalog/runtime-compatibility.ts) exposes the current one as `catalogRuntimeCompatibility.calculation` and owns the explicit calculation closure, `catalogCalculationV1Files`. The identities module names the hash of that closure, so it stays outside it. This page deliberately does not repeat the current hashes.

**Before first activation:** no Catalog Release has ever been activated, so the calculation compatibility identity is provisional. For an intentional calculator behavior change, review the change and its runtime dependencies. When calculator imports or reexports change, review new dependencies transitively and explicitly add any calculation implementation files to both `catalogCalculationV1Files` and the test's independent file list; update its exact import and reexport expectations as well. Keep the existing implementation files covered and the dependency assertions intact. Then rotate the identities as described in [Rotate the calculation identities](#rotate-the-calculation-identities), and update any other current recorded expectations in the same change. Do not rewrite historical immutable artifacts or their observed evidence; any new preparation must use a fresh release number and the current identity. This procedure does not require a separate retained calculation implementation before first activation.

```sh
calculation="$(pnpm -s catalog:pin)" &&
pnpm catalog:release build \
  --number 1 \
  --schema character-sheet-v1 \
  --calculation "$calculation" \
  --system /path/to/foundryvtt-pathfinder1 \
  --content /path/to/pf1-content \
  --artifact .catalog-preview/release-1/release.json
```

`pnpm -s catalog:pin` prints the identity recomputed from the working tree and fails if it differs from the pinned current identity, so the example stops before building with an unpinned calculator.

`--attribution`, `--curation`, `--remaps` and `--legal` select explicit reviewed JSON inputs instead of the committed defaults. `--previous` supplies the complete artifact of the authoritative active release when one exists. The number must increase beyond that comparison base. The backend checks the declared base number and artifact fingerprint against its actual active release, so a prepared private artifact cannot masquerade as an active comparison base. A fresh local directory does not grant reuse of a number already registered with the backend.

`--rule-resources PATH` supplies an array of `{ "key": "builtin:stable-name", "payload": ... }` supporting-resource records. Their structured bodies are frozen in the artifact, not merely hashed as input. The application's `convex/lib/representativeClassCatalog.ts`, `convex/lib/representativeRaceCatalog.ts` and `convex/lib/representativeArchetypeCatalog.ts` seed sources and definitions are always captured as `builtin:representative-class-catalog`, `builtin:representative-race-catalog` and `builtin:representative-archetype-catalog`, with their source fingerprints and compatibility identities. The class resource also captures exact Fighter/Rogue feature schedules linked to the archetype resource. These representative fixtures do not certify complete class, race or archetype curation, and capturing them as supporting resources does not admit them as new selectable content. The reviewed `scripts/catalog/reviewed-casting-tables.json` resource is always captured as `builtin:casting-tables`, including its complete cited table rows and casting-class metadata, source fingerprint and compatibility identities. It supplies seven shared families through level 20 plus adept, extract, Unchained summoner and occultist overrides; occultist availability is explicit while its choice-dependent known count stays unspecified. This supporting resource does not admit class definitions as selectable content. [Reviewed CRB conditions](conditions.md) are local selectable content supplied through `appendConditionResources` and the ordinary attribution/curation seam. Preview opts in with `catalog:preview --conditions`; `catalog:release build` has no conditions flag. A programmatic release build must explicitly append the candidates and fingerprint their `conditionReleaseResourcePaths` as documented in condition curation. New local content must use the attribution/curation import seam rather than disguising selectable definitions as authored resources.

The output directory must be empty or contain only its release artifact, and cannot overlap source inputs. Output is written only after the admission, curation, inventory/structure/reference and legal gates pass. Holds remain valid individually reported outcomes, including changed accepted assessments. A failing gate creates no release artifact. Repeating an identical build at the same path leaves identical bytes; changed inputs/output at that path fail without overwriting it. The immutable backend binding also rejects reuse across independent local directories.

The manifest fingerprints nine explicit input categories: upstream pins/content and verification, remaps, curation, local data/comparison provenance, importer/parser dependencies, sanitizers, rule resources, legal inputs and attribution. The local source graph includes the importer's mapping, formula, inventory/configuration and curation dependencies. The parsers fingerprint includes `src/lib/character-sheet.ts` because its shared schemas validate and shape imported definitions. Editing that file changes a declared release input and requires a new release number, even when the particular fixture's normalized output stays equal. Parser dependency identities also include the installed versions and exact relevant lock entries/integrities for YAML, parse5, its entities dependency and Zod. No whole-repository or whole-lockfile hash is used, and unrelated application changes do not alter a release.

## Prepare, resume and inspect

Preparation uses Convex's installed administrative HTTP client, including the same internal-function seam used by its CLI. JSON travels in request bodies, so large records are not constrained by shell argument lengths. It never pushes code or runs codegen. Name the target explicitly, supply its matching URL, and read the deployment credential from a separate non-environment file. The URL must be that deployment's own, `https://<name>.convex.cloud` or the regional `https://<name>.<region>.convex.cloud` (for example `eu-west-1`), with `<name>` equal to `--deployment-name` and nothing else: no port, path, query or further label. The operator refuses any other URL before reading the credential, for every target kind ([`deployment-url.ts`](../../scripts/catalog/deployment-url.ts); owner decision 2026-10-16, #753). The command does not read `.env` files or infer a deployment from environment variables.

```sh
pnpm catalog:release prepare \
  --artifact .catalog-preview/release-1/release.json \
  --deployment-name your-preview \
  --deployment-url https://your-preview.convex.cloud \
  --target-kind preview \
  --admin-key-file /secure/path/convex-admin.key \

pnpm catalog:release inspect \
  --number 1 \
  --deployment-name your-preview \
  --deployment-url https://your-preview.convex.cloud \
  --target-kind preview \

```

Target kinds are `preview`, `development` and `production`; naming the target does not deploy or activate it. Follow the repository's deployment-selection and production-consent procedure when an agent is authorized to issue remote operations. This implementation's evidence executes no remote commands.

`begin` registers the immutable candidate against the active comparison base. `writeBatch` validates a complete bounded batch and its committed fingerprint before transactional writes. `finalize` requires the complete batch inventory, all five gate-certified report summaries and legal inputs. Only then does status become `prepared`. These operator writers use the general Write Gate class: after initial cutover they can prepare candidates under sheet authority while ordinary gameplay continues. Legacy Character writers remain fenced under sheet authority. A closed maintenance gate blocks every gated writer, including preparation, and stale epochs reject both classes. `--write-epoch` defaults to zero and is passed unchanged to every mutation; use the current open gate's epoch from authoritative migration status. The command never refreshes an epoch or replays a refused gameplay command automatically.

After interruption or a lost response, inspect the authoritative candidate, then rerun the same `prepare` command and artifact. Preparation resumes at the recorded next batch; exact batch retries and prepared retries are idempotent. An input/output change requires a manually incremented number and a new artifact. Candidate definitions/resources/remaps live in separate private rows and never enter ordinary pickers or current sheets. Workers cannot replace an existing number's manifest or write after it is prepared.

## Committed reports and legal data

The artifact stages only newly admitted upstream definitions/resources and reviewed applied remaps, plus explicit authored supporting resources. It always contains five report summaries and individually keyed records:

- `content`: normalized added/changed/unchanged definitions, complete inventory records/pack coverage and unsupported details.
- `resources`: normalized upstream/authored resource changes and captured identities.
- `holds`: individual holds, dependent omissions, retained exceptions, failures/outstanding notices and the exact retained-required-notice certificate.
- `retirement`: held/removed prior identities and their last usable bodies, kinds and fingerprints. These bodies propagate across successive held/retired releases and never become new selections.
- `curation`: passed coverage, counts, missing/stale/applied/unused records and unresolved mechanics/description records.

The four logical legal inputs persist `requiredNotices`, `permanentNoticeSuperset`, the exact Section 15 Registry and legal resources. A Registry that exceeds the 512,000-byte batch cap uses a `registry-chunks-v1` descriptor in the `registry` row, with chunk count, canonical byte count and a whole-Registry fingerprint; numbered `registry:chunk:000000` rows carry its canonical JSON text across bounded batches. Preparation rejects missing, duplicate, unexpected, malformed or altered chunks. Readback reconstructs and verifies every notice field and provenance byte before returning the ordinary legal-input shape. Previously prepared single-row Registries keep their encoding and readback without migration. No row/batch limit changes. Notice versions are preserved by `(id,text)` across prior releases. Held-only books never become requirements for unrelated content. Each outstanding retained notice must be covered by the gate's per-code retained certificate; an unrelated exception count cannot authorize a missing notice. The public legal read selects these inputs only through a prepared active release and returns null when none exists. The frontend uses committed defaults for null or unavailable backend queries, so publishing the frontend before the backend does not interrupt the legal page. Preparation does not alter that public selection.

The readiness query checks the prepared candidate's required schema/calculation identities and active comparison base. It reports that activation is implemented but remains a compatibility check and does not claim that facts, discovery, frontend readiness or cutover are complete.

```sh
  --target-kind preview --admin-key-file /secure/path/convex-admin.key
```

The internal `catalogReleaseActivation:activate` mutation validates the current artifact comparison base, newest candidate and run, prepared gate inventory, discovery certificate, schema/calculation compatibility, and indexed absence of dirty/failed work. It performs a bounded selection write, reading no Characters and replacing no militia snapshot. That selection binds definitions, supporting resources, legal data, calculation identity and the run's versioned facts together. An edit that commits first dirties work and refuses publication; an edit retried after the selection reads the selected calculation and updates its live facts. The operator passes the explicit Write Epoch unchanged and never reopens a maintenance gate.

`catalogReleaseActivation:status` and `catalog:release active` report the authoritative release, artifact fingerprint, impact run, activation identity, schema/calculation and enforced fixture-only mode. If the response is lost, inspect this status, then retry exactly the same activation request. That retry returns the same selection. Reusing the activation identity with different inputs fails; competing requests publish at most one selection. A candidate based on an obsolete release must be rebuilt with a new number and reconciled against the current base. Resolver-only releases use this same protocol. Content rollback is a new release evaluated against current sheets, preserving accepted edits; see [Retire or roll back content](#retire-or-roll-back-content).

Each completed work row carries the selected facts and inherited Character generation, including unaffected outcomes. Normal writes maintain `catalogCharacterFacts` overrides for the selected release, including private and no-militia Characters, so candidate evidence cannot overwrite later edits. Campaign generation evidence tracks whether any current candidate facts differ and increases once per affected campaign. Equal facts keep the generation; unrelated campaigns and empty rosters inherit their prior generation. The militia review revision combines its ordinary source revision with that selected campaign generation.

Canonical integration reads `selectedCanonicalMilitiaState` for ledger reads/corrections, draft workspace and edit preconditions, and Confirmation preview/confirmation. Setup options/review checks, Character readers/writers, Catalog Copy operations and linked inputs use the same selected definition/resource/calculation helpers. Current source overlays replace only Character facts; treasury, reputation, assignments, roster Hit Dice overrides, saved Weekly Drafts and other militia data stay live. Historical reads continue using frozen records. A public History Rewrite workflow does not yet exist; the storage-only historical append preserves its frozen source and is not a live-state publisher. History Rewrite publication is an explicit follow-up dependency: before that writer can ship, current-input reads, effective-revision preconditions and publication must use the selected-state helper, frozen historical sources must remain unchanged, and the writer must enter the migration inventory with public behavioral coverage.

Prepared adapter limits remain explicit: stable references resolve already seeded Catalog Entry IDs; this ticket does not allocate the initial production import's new identities. Definition discovery records a bounded identity-coverage certificate, exposed as `identityCoverageComplete` and `missingIdentityCount` in run status. An admitted definition without a seeded global identity (or an existing private imported-Spell identity) cannot activate, even when it affects no current Character. Seed/install supported identities before starting a fresh reconciliation run; successful private preparation and facts reconciliation alone do not certify this activation gate. Imported supported bodies and retained `retirement:<key>` bodies share one adapter; retained entries resolve existing uses but stop new selections. The Spell browser publishes immutable release metadata with the same selection. This fixture protocol bounds the changed, retained and inherited Spell overrides selected by one artifact to 256 metadata entries and 1 MiB, with at most 32 class-list tags per Spell. Discovery compares candidate definitions to the base release (or the seeded global or private imported definition when no base exists), stages changed overrides and carries previously selected overrides into later releases, while certifying unchanged bodies through the same stable-kind adapter. Thus a release may contain thousands of unchanged Spells with only a few changes. Their existing indexed rows remain available through selected projection; the limit does not apply to the entire artifact. A release whose selected overrides exceed the cap fails visibly before readiness/activation and requires a future scalable preparation path. Missing stable IDs, unsupported imported bodies and full production catalog materialization remain outside the prepared adapter's supported scope.

Resource discovery certifies the supported resource inventory, bounds and casting-table schema independently of Character inventory. Every admitted seeded body and retained global/private imported body also passes its stable-kind adapter before readiness. Thus an unused malformed definition or an empty roster cannot bypass compatibility checks.

Supported retirement covers manually selected definitions, Catalog Copies, recorded Spells and, since #411, automatic Grant targets: existing uses remain readable; new choices, copying, new Grants and offered Spell browser results exclude held identities. Existing copies keep their own fields. Legacy Spell indexes without their optional durable key resolve through bounded stable-ID lookups. The rules for Grants and moves are in [Retire or roll back content](#retire-or-roll-back-content).

Observed local evidence in `convex/catalogReleaseActivation.integration.test.ts` drives preparation/reconciliation/activation, lost-response inspection/retry, competing activations, edits after finish, selected facts and targeted stale reviews, untouched drafts/overrides/treasury/history, consecutive notice releases and prior-calculator resource behavior. It also rejects unsupported Spell metadata and malformed resources/retained bodies before selection, and covers held copies and legacy Spell indexes. Retirement of automatic Grant targets and rollback are proven in `convex/catalogReleaseRollback.integration.test.ts`. Client hook tests retain the complete prior sheet, browser metadata, page and release-derived selection/mode until the new complete view arrives. These tests and operator adapters execute locally; no remote command, codegen, deployment, migration or production activation was run.

Spell browse pages bound definition hydration as well as indexed pages. Candidate and baseline rows share sequential accounting for raw definition and release-body reads; a page that exceeds its requested byte or row budget fails clearly before hydrating further rows. Pages with many descriptions may require a smaller requested page. An individual body larger than the maximum page budget requires a future bounded-body browsing design.

## Linked Companions, moves and keyed lists

[#712](https://github.com/AndreasUnunger/EverythingPath/issues/712) completes ordinary release reconciliation for homebrew moves and linked Companion facts (PRD Implementation Decisions 13, 15, 16 and 18). It adds no table, index or writer.

**Linked candidates.** Candidate work for a Companion, and for any Character with Companion Relationships, now calculates instead of failing closed. The worker reads each linked Character's recorded sheet once and calculates it under the candidate release: candidate definitions, casting resources and retirements, with the Character's own existing Grants of retired targets. It then projects the Companion with the ordinary `applyCompanionToSheet` over those candidate sheets. A familiar's master, an eidolon's summoner and every Character upstream of them are read at the same release boundary as the Companion. The comparison facts project the selected release's sheets the same way. Facts stay the ordinary permanent statistics the live writer stores. They never use effective familiar Hit Dice, a progression level, Cohort Equivalence or a viewed Combined Form, and linked Temporary Effects stay filtered. A Companion whose required inputs are missing keeps them unresolved (`unresolvedAbilities`, `actualHitDice: null`), never failing, reusing a stale value or using zero. Discovery already gave a Companion the reasons of every non-replaced associated Character upstream. The work's input fingerprint covers those Characters' inputs and the relationship rows.

**Dirty revisions.** These writes already recalculate each affected Companion through `updateCanonicalCharacter` (#423), which marks its candidate work dirty in the same transaction:

- link, replace, interrupt and restore;
- source, allocation and linked-input fallback changes;
- ownership reassignment;
- sheet and definition edits on an associated Character;
- Character moves and trusted membership returns.

`complete` refuses a worker that evaluated before any of them. Its revision and input/result fingerprint check covers the whole linked group.

**Moves.** A grouped move or trusted return published during reconciliation dirties every member. Re-evaluation records the destination, or no campaign, as the work's facts campaign. The source campaign's facts generation then drops the departed change, and the destination's counts it. Character copies made by the move follow the release through their retained global references. That includes a Character copy of a campaign customization, an indirect copy of the global definition. A move prepared across activation still restarts discovery (#703).

**Keyed lists.** Discovery follows every keyed list a reached definition consumes: the `classTag`, `castingClass` and `list` fields the move closure reads, not only a class's own casting list. So a changed Spell on another class's list affects an Archetype that casts from it, such as the Questioner investigator casting from the bard list.

**Character lists.** A prepared Character's list row reads the selected militia projection when its campaign's militia holds that Character's facts. Otherwise, including outside a militia and for a Character the militia projection doesn't yet hold, the row reads its facts at the selected boundary through `readSelectedCharacterFacts`. Both are the same selected boundary (Implementation Decisions 16 and 18), so the code keeps both paths. After activation the list agrees with the sheet, instead of showing the stored ledger facts from before activation. Activation doesn't refresh those stored copies; the next write does.

**Reads and writes.** Each discovery stage keeps its existing per-batch bounds. Keyed lists add one edge per consumed key, inside the existing 256-dependency limit. The following were measured with Convex transaction metrics on the representative test sheets:

| Stage                                                                                   | Index ranges | Documents read | Bytes read                     | Writes |
| --------------------------------------------------------------------------------------- | ------------ | -------------- | ------------------------------ | ------ |
| `evaluate`, elf wizard with a familiar                                                  | 105          | 36             | 16 KiB                         | 0      |
| `evaluate`, its cat familiar                                                            | 137          | 52             | 24 KiB                         | 0      |
| `evaluate`, either, with a base release to compare                                      | up to 206    | up to 78       | up to 50 KiB                   | 0      |
| `complete`, which repeats `evaluate`                                                    | up to 216    | up to 85       | up to 54 KiB                   | 1–2    |
| Character list, per prepared row without militia facts, plus one boundary read per list | 1–2          | 1–2            | one facts row and one work row | 0      |

`complete` writes its work row and up to two campaign facts rows. Activation still reads no Characters.

**Evidence.** `convex/catalogReleaseCompanions.integration.test.ts` covers these cases, each against CRB p. 22's elf Ability Scores, admitted before their Modifiers were curated:

- A cat familiar (CRB p. 82) of a 2nd-level elf wizard keeps its facts and generation while the wizard's change stales the reviewed week once. The saved draft survives, and readers show the complete old view until activation. A resolver-only successor then keeps every generation, and the fresh review confirms. This test cannot tell a candidate master read from an active one: no familiar or eidolon militia fact depends on the master's changed scores. Same-boundary linked facts are proven structurally, because the worker passes its candidate reader (`readCandidate`) to `applyCompanionToSheet` for every linked endpoint.
- Linking after discovery, choosing the creature, a third wizard level and an owner reassignment during reconciliation dirty the familiar and refuse each obsolete worker. Its Intelligence becomes 7, and outsiders and production activation stay refused.
- An APG Biped eidolon without counting sources keeps its unresolved facts through the real operator command until a restored source resolves them.

`convex/catalogReleaseImpact.integration.test.ts` covers the Questioner's borrowed list. All of these run locally against isolated fixture data; production keeps legacy authority until #413.

That work belongs to #319, with #714's cutover rehearsal as its gate; see [the initial backfill runbook](../initial-character-backfill.md#validation-and-capacity). The staged elf release in the evidence is an accepted test scenario, not a real artifact.

## Retire or roll back content

[#411](https://github.com/AndreasUnunger/EverythingPath/issues/411) implements PRD Implementation Decisions 17 and 18 for retirement and rollback. A rollback is another manually numbered release, built with `--previous` set to the active release and prepared, reconciled and activated by the protocols above. It is evaluated against current sheets and local definitions; no Character, campaign or militia snapshot is restored. Entries added since the rollback target become `retirement:<key>` reports with their last usable bodies. Defaults are not reapplied and finished weeks are not rewritten.

**Building a release.** Every build rechecks attribution against what earlier releases learned:

- Evidence revoked in any earlier release stays revoked, even when the build uses an older release's attribution inputs. The holds report carries the permanent `revokedEvidence` list forward. A re-review records evidence under a new identifier.
- A retained exception reported by the comparison base stays reported while its content is still not admitted and the new inputs don't redeclare it. The builder carries the use and its exception forward, so its notices remain required or outstanding.
- The permanent notice superset only grows, as before.
- Restoring a retired entry for selection takes a later release whose admission gate admits it again under its stable identity.

**Existing and new uses.** After activation the selected release decides what each Character may keep:

- **Selections and Catalog Copies.** Existing Selections and edited copies keep counting with their own fields. A new Selection, a second Selection by the same Character, a copy and a campaign customization of the retired identity are refused, including through an existing campaign copy. A Character may continue its own uses: switch its Selection off and on, return to its own race row or alternate trait, toggle its Archetypes, and add levels of a retired class it already has, which shows the acceptable `retiredClassInUse` advisory. Starting a retired class, race or Archetype from scratch stays refused. The read's catalog view lists the offered definitions that are held (`heldDefinitionIds`), and the class, race, Archetype and feat/trait pickers show them unavailable with a short reason, except the Character's own continuing uses.
- **Automatic Grants.** Grants come from race traits, class-feature schedules, Archetype additions and ID-based `grants`. When a release retires such a target, reconciliation records in each Character's work the Grant Keys the Character already had (`retainedGrantIds`), counting or recorded. Grants the active release had already blocked are not counted as existing. Sheet reads use the selected run's record. Any other Grant of the target is dormant with reason `retired`; Keep cannot make it count. Leaving a source and returning restores the same Grant Key. A Character created after activation has no existing Grants. Each later release records the Grants again from the then-current sheets, so retained Grants carry forward while a target stays retired.
- **Moves.** A move copies held content only where the Character uses it: a Selection or recorded Spell, or an ID reference from a carried definition. The copy keeps the identity, so it stays held. Held Catalog Copies reached only through list membership, such as an unrecorded campaign Spell on a casting list, stay behind, and the move removes their Spell browser rows. Arriving in another campaign makes nothing selectable.

**Evidence.** `convex/catalogReleaseRollback.integration.test.ts` drives the operator commands for these cases:

- a retired Keen Senses racial trait (CRB p. 22), through a campaign copy of the elf, with a concurrent edit during reconciliation and unchanged fact generations;
- a Cleave (CRB p. 119) rollback with a newer Selection made during reconciliation, an edit after the run is sealed, an edited campaign copy, refused production activation and restoration by a third release;
- moves that carry a used held copy and leave an unused held Haste (CRB p. 293) copy behind;
- a Character returning to its retired race;
- a fighter (CRB p. 55) adding levels and the Archer Archetype (APG p. 104) after the fighter is retired, with the advisory, while another Character can't start it.

Sheet reads check retirement once per distinct rule identity among the sheet's Grant targets and classes, bounded by the sheet's 4,096-row read limit; seeded character-scope definitions need no check. One selected boundary read serves the whole sheet read. A fighter 1/rogue 1 elf sheet with an active retirement reads 538 documents per `characterSheet:read`, down from 543.

`convex/catalogReleaseActivationMilitia.integration.test.ts` proves that a notice-only release, adding the reviewed CRB Section 15 notice, keeps fact generations and the reviewed week. `tests/catalog/release.test.ts` proves that the builder carries revoked evidence and retained exceptions through a rollback build. All of these run locally against isolated fixture data; production keeps legacy authority until #413.
