# Gate modes: rule detail

Reference for the optional `gate.json` modes in [operations](../orchestration/operations.md). The operations file says when to use each mode and what to do on a refusal; this file is the exact rule each one enforces, as implemented in `scripts/orchestration/`. Read it when a mode refuses for a reason the summary doesn't explain, or before changing one of these scripts. Root's qualification plans for each mode are in [qualification](qualification.md).

## Remote heavy checks

Owner, 2026-10-30 (`$EP_ORCH/mvp-20261023/owner-decision-20261030-remote-heavy-checks.md`): a verified Boat run of typecheck, lint and the full suite for the exact candidate tree may count for the landing gate. `scripts/orchestration/remote_checks.py` is the verifier; its tests are `remote-checks.test.py`.

- **Publication:** Boat creates `$EP_ORCH/remote-checks/<runId>/` (create-only; `runId` matches `^[a-z0-9-]+-\d{8}-\d{6}-[0-9a-f]{6}$`), writes the logs and `full.json`, writes `manifest.json` (`remote-heavy-checks-v1`) last and then `chmod -R a-w`. Boat writes nothing else under `$EP_ORCH` and never edits the repo, wrappers, locks or policy. The orchestrator, not Boat, names a manifest in `gate.json`.
- **Tree-only CI commits** (owner 2026-11-02, `$EP_ORCH/mvp-20261023/owner-decision-20261102-tree-only-ci.md`): root publishes a candidate with `scripts/orchestration/gate-push.sh <REVIEWED> <BASE> <label>` (tests: `gate-push.test.sh`): a parentless `git commit-tree` of `REVIEWED^{tree}` whose message carries the trailers `Gate-Reviewed`, `Gate-Base` and `Gate-Tree` (full SHAs; dates are `REVIEWED`'s committer date, so the same inputs give the same commit), pushed to that one checked URL, named in the push rather than `origin`, as `<commit>:refs/heads/gate/<label>` and no other refspec, never `--all`, `--mirror` or tags. It refuses, before reading anything, a set `GIT_CONFIG` (any value, empty too: only `git config` honours it and a selected file skips `include.path`, so the URL checked could differ from the one pushed; `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_NOSYSTEM`, `GIT_CONFIG_COUNT`/`KEY_<n>`/`VALUE_<n>`, `GIT_CONFIG_PARAMETERS`, `HOME` and `XDG_CONFIG_HOME` apply to both and are allowed), then abbreviated SHAs, `REVIEWED` not descending from `BASE`, a dirty worktree (every untracked file whatever `status.showUntrackedFiles` says, a failed `git status`, or an index entry marked assume-unchanged or skip-worktree), an `origin` without exactly one push URL (with two, one could accept the push while the other refuses it; the values of `remote.origin.pushurl`, else `remote.origin.url`, are read NUL-separated, and one that is empty, starts with `-` or holds a control character, newline and CR included, is refused), a `url.<base>.insteadOf` or `pushInsteadOf` rewrite that applies to that URL or has no value, a remote named by that URL (`git push <url>` would use its URLs instead) and any tree file of 100,000,000 bytes or more, naming each. The integration branch and its history are never pushed; GitHub sees only the candidate's current files. CI checks the commit out with `fetch-depth: 1`; `remote_ci.py probe` (the job's first step, also in the run summary) and the manifest's `source` record the commit, its tree, its parents read from the raw commit object (a shallow clone hides them from `rev-parse`), its message and every trailer Git parses from it, and the job stops before any command on a checkout that is not clean or a commit that `remote_checks.gate_commit` refuses: parents, or a message whose trailers are not exactly the three. The trailer block is the message's last paragraph, every line `Key: value`; any other key there (another `Gate-*`, any case, or a non-gate trailer), a repeated key, a value that is not a full SHA, a missing trailer, a non-trailer line in the block or a gate key anywhere else in the message is refused, as is a `Gate-Tree` other than the tree. The gate host applies the same check to the recorded message and requires the recorded trailers to be the message's.
- **Runner** (root 2026-11-03): `ci.yaml`'s `remote-checks` job runs on Blacksmith's `blacksmith-4vcpu-ubuntu-2404` (GitHub's Ubuntu 24.04 image, x64) and logs `nproc`, `lscpu` and `free -g` before the heavy checks; the light `checks` job stays on `ubuntu-latest`. The Blacksmith GitHub app must be installed for the repository, or the job waits for a runner indefinitely.
- **Host audits** (owner 2026-11-02, `$EP_ORCH/mvp-20261023/owner-decision-20261102-w1-host-audits.md`): the catalog provenance audits need sources only the gate host has (`~/repos/everythingpath/sources/{foundryvtt-pathfinder1,pf1-content,prd-2026-10-20}` and `~/repos/everythingpath/.ep-cache/pcgen-<pin>`), so they skip by their `skipIf` in CI, which runs plain `pnpm test`. `scripts/orchestration/host-audits.json` (`host-audits-v1`: `kind`, `sources`, `tests` as `{file, fullName}`, sorted and unique) pins exactly those tests and, since CI has no history, the tests that need it: `attribution-evidence-codec.test.ts`'s two tests that read historical blobs skip only when a blob is absent (the list's sources name the history). It was derived by running the whole suite with `HOME` pointed at an empty directory and collecting every skipped test, cross-checked against the `skipIf` sites; the two `win32` skips in `tests/local-convex-development.test.ts` are not in it, because the job runs on Linux and the verifier binds the platform to the gate host's. A test that starts needing a host source goes into the list in the same change.
- **Bindings:** source tree = `TREE` and the queue's `HEAD^{tree}`; the remote commit is parentless (`parents: []`) and its `Gate-Tree` equals that tree; `Gate-Base` = `BASE` and the queue's pinned base; `Gate-Reviewed` is a commit on the gate host whose tree is `TREE` and which descends from `BASE` (the operator also requires it to be `REVIEWED` or the prepared squash), so ancestry is checked locally, never from the remote; `source` has only `commit`, `tree`, `parents`, `trailers`, `message`, `status` and `root`, and the message's trailers are only the three, each once, as recorded; empty source status; `pnpm-lock.yaml`/`package.json` hashes equal the candidate's blobs and the installed-lock hash equals the worktree's after the queue's reinstall; `hostAudits: {file, sha256}` names `scripts/orchestration/host-audits.json` and its sha256 equals the candidate's blob; node, pnpm, platform and arch equal the gate PATH's; the effective `timeZone` equals the gate host's (Boat sets `TZ`); `CI=true`, `LC_ALL=C.UTF-8`, `VITEST_MAX_WORKERS=2`, no `NODE_OPTIONS` or other `VITEST_*`; only `GOMEMLIMIT` as a resource override; exact argv in the order install, typecheck, lint, suite; integer zero exits and `completed: true`; an all-green suite (`success`, no failed or todo test, no failed or pending suite, every suite and file passed; Vitest 4 counts a file or suite of skipped tests as passed) with no snapshot write, where the only tests allowed to be skipped or pending are listed ones and every listed test is present (skipped or passed); the remote file set equals the local `vitest list --filesOnly`. Referenced files are hashed, relative, regular, read-only and inside the run directory. The exact format is in `remote_checks.py`.
- **Where:** `authorization()` verifies the manifest at every phase. The queue verifies it again after the pin (`remote.log`, record `remote-evidence/remote-verification.json`). In `replace` it then skips typecheck, lint and triage and runs `host-audits.sh` (`host-audits.log`): exactly the listed tests for the candidate commit, in a fresh `ep-gate-audits-*` checkout under `heavy.lock` inside the gate's bounded unit (without the light lane's read lock, like the rest of a `replace` gate), as `pnpm test <listed files> --testNamePattern=<one pattern anchored on the listed full names>` with the JSON reporter (Vitest 4 matches the describe titles and title, not the file). `remote_checks.py audit` requires Vitest exit 0, every listed test (every repeat) passed, every other test in those files filtered out (skipped), no other file and the remote suite's file and suite verdict, with the list equal to the manifest's; it writes `remote-evidence/host-audits.json` beside `host-audits-list.json` and `host-audits-report.json`. In `compare` the local full suite already runs the listed tests: the queue runs typecheck, lint and triage and requires the remote suite as `verify` judges it, the local suite all green under the same verdict, outside the list an equal (file, test, status) multiset, every listed test passed locally, and equal totals except that each listed remote skip moves one test from passed to pending (suite totals stay equal) (`remote-comparison.json`, which also references the list). Preflight, the identity checks and checked `land.sh` are unchanged. Collection adds `remoteChecks` and, in `replace`, `hostAudits` (the record re-judged from its list and report) or, in `compare`, `remoteComparison`; it takes `originalSuite` from the remote `full.json` under the same listed-skip rule in `replace`, references the manifest, logs and records, and records `suite: {source, manifest}` with source `remote+host-audits` (plus `hostAudits`, the record) or `local+remote-compare`; the completion scope names the remote suite and, in `replace`, the host audits.
- **Stop conditions:** A refused `gate-push.sh` (nothing is pushed), a CI checkout that is not a tree-only gate commit (the job stops before any command), a remote commit with parents, a missing, extra, repeated or abbreviated gate trailer (or a gate key outside the trailer block, or recorded trailers that are not the message's), a `Gate-Tree` other than the tree, a `Gate-Base` other than `BASE`, a `Gate-Reviewed` that is not the reviewed or prepared commit, unknown here, of another tree or not on `BASE`, a manifest of the W1 shape (`source.base`), a remote failure, a refused or stale binding (tree, base, lockfile, host-audit list, toolchain, timezone, environment, argv, completion, suite or file set), an unlisted remote skip or todo, a listed test missing from the remote report, in `replace` a host-audit test skipped, failed or missing on the gate host (or an unlisted test run, or a non-zero Vitest exit), or, in `compare`, any difference outside the list or a listed test not passed locally blocks landing; each has its own message, and there is no fallback to a local or partial pass.
- **Trust:** The manifest and its files are writable local artifacts pinned by sha256 in `gate.json` and the queue argv: this detects corruption, moved directories, stale scope and unsupported pass claims; it is not cryptographic attestation against an actor rewriting every file.
- **Not supported:** pairs (`--pair`, `LAND_PAIR_MANIFEST`), more than one queue item, remote curation prep and author validation receipts. Curation prep plans and their reuse are unchanged.
- **Resources:** a `replace` gate's unit cap is 10 GiB with a 16 GiB launch guard. `compare` keeps 15 GiB and 21 GiB, because it runs the local full suite. `gate-2` admission is unchanged in every mode. See [Gate memory](../orchestration/operations.md#gate-memory). The replace cap rests on measured kernel peaks: `catalog:pin` at 0.13 GiB with a 9 MB V8 heap, the writer check at 0.24 GiB, remote verification's local path at 0.14 GiB, the real e2e preflight at 0.21 GiB, the host audits at 4.79 GiB, codegen at 4.96 GiB, and the whole sequence at 6.59 GiB. Root qualifies it, with its wrapper change, on the first `replace` gate.
- **Timeouts:** GitHub's runner ran the suite 1.7–1.9× slower than the gate host in runs 41593918959 and 41596995308, and single tests up to 3.06× slower. With `CI=true`, `vitest.config.ts` gives tests and hooks 120 s. A test that needs more sets its own limit: at least 3× its slowest CI duration.
## Mechanical-rebase proof

Owner, 2026-10-31, item 1 (`$EP_ORCH/mvp-20261023/owner-decision-20261031-process-overhead.md`): a rebase-only change is a mechanical check, not new reviews. A code gate whose `gate.json` carries `rebaseProof: {oldBase, accepted, acceptedTree}` (exactly these keys, full SHAs) accepts Standards/Spec reviews bound to `(accepted, acceptedTree)` as well as `(REVIEWED, TREE)`. NEW_BASE is `BASE` and HEAD is `REVIEWED` by construction; they are not restated.

- **Rule:** `gate_core.rebase_proof` compares plumbing raw tree deltas, `git diff-tree -r --no-renames --no-abbrev -z`, byte for byte with no normalisation. Both chains, `oldBase..accepted` and `BASE..REVIEWED`, are non-empty and linear with the same count; each commit pair has an equal delta (`c^ c`) and an equal message body; the net deltas `oldBase accepted` and `BASE REVIEWED` are equal. So every path the slice changes has the same old and new objects on both bases: `REVIEWED`'s tree is `BASE`'s with the accepted slice's blobs.
- **Where:** `authorization()` re-verifies the proof from Git objects at every call (prepare, submit, collect, complete and each periodic integrity pass), after checking the field's shape, the code kind and `accepted^{tree} == acceptedTree`. It precedes the attempt directory, so a refusal launches nothing. Without the field, reviews bind `REVIEWED`/`TREE` exactly as before, and the completion scope is unchanged; with it, the scope adds `reviews accepted at <accepted> on <oldBase> carried by the mechanical-rebase proof`.
- **Stop conditions, each with its own message:** a malformed field or a curation kind; an unmoved base (`oldBase == BASE`); a missing `accepted`/`oldBase` object; an accepted tree mismatch; `oldBase` not an ancestor of `BASE`; an empty or non-linear (merge) chain; a different commit count; a commit pair whose delta or message differs; a different net delta (overlap with the base movement or changed content); no review binding `accepted`. Any overlap between the slice and the base movement refuses, even a clean rebase: overlap means full independent reviews. There is no fallback to a normalised or partial pass.
- **CLI:** `python3 -B scripts/orchestration/rebase-proof.py WT OLD_BASE ACCEPTED NEW_BASE` (full SHAs) requires a clean WT whose `HEAD` descends from NEW_BASE, runs the same function and prints one JSON object: `{verdict: "PASS", oldBase, accepted, base, reviewed, commits, paths, tree, rebaseProof}` (exit 0), whose `rebaseProof` goes into `gate.json` as is, or `{verdict: "FAIL", reason}` (exit 1). `--head SHA` reads objects only and skips the clean-worktree check. It writes no files; the operator does not import it.
- **No chain:** after repeated rebases, prove from the original accepted commit on its review base straight to the current head. Keep `accepted` reachable with an archive ref (for example `refs/archive/RUN/<slice>/accepted`); a missing object refuses.
- **Trust:** verified from Git objects at every authorization; the full gate suite remains authoritative for semantic interaction (the base changing something the slice calls), which no textual proof can see.
- **Not supported:** curation (refused), pairs (they do not use this config) and overlap. A review of a content-different earlier commit (owner item 2) is carried only by a [single-axis fix review](#single-axis-fix-review).
## Single-axis fix review

Owner, 2026-10-31, item 2 (`$EP_ORCH/mvp-20261023/owner-decision-20261031-process-overhead.md`): when only one axis had findings, only that axis re-reviews the fix; the other axis's LAND stands unless the fix touches behaviour it judged. A code gate whose `gate.json` carries `carriedReview: {axis, commit, tree, attestation: {path, sha256}}` (exactly these keys; `axis` `standards` or `spec`; `commit`/`tree` full SHAs) accepts the carried axis B's review at the earlier commit E = `commit` together with the other axis A's fix review at the head H.

- **Frame:** if A binds `(REVIEWED, TREE)`, then H = `REVIEWED` and the frame base F = `BASE`; if `rebaseProof` is present and A binds `(accepted, acceptedTree)`, then H = `accepted` and F = `oldBase`. Otherwise A refuses with today's `Wrong reviewed scope: <A>`.
- **Rule:** `gate_core.carry_proof(root, F, E, tree, H)` uses plumbing only. E's object exists and `E^{tree} == tree`; `F..H` is non-empty and linear; E lies strictly inside it (not F, not H). It returns `{base, carried, head, paths}`, where `paths` is the sorted `git diff-tree -r --no-renames --name-only -z E H`. A's report (its reference verified) must contain the literal `E..H` with full SHAs. B must bind exactly `(E, tree)`; every other review check (task/run, terminal, identity, crossing the author model, independence, an unused rebase proof) is unchanged.
- **Attestation:** root writes one JSON file, referenced by `{path, sha256}`, with exactly `{version: 1, axis: B, carried: E, head: H, paths, statement, attestedBy}`. `paths` must equal `carry_proof`'s, so produce it from the same call (or `git diff-tree -r --no-renames --name-only -z E H`, sorted); `statement` (root's judgement that the delta stays within A's findings and touches no behaviour B judged) and `attestedBy` are non-empty strings.
- **Where:** `authorization()` checks the field's shape and the code kind, then, before the review loop, re-verifies the frame, `carry_proof`, A's report and the attestation at every call (prepare, submit, collect, complete and each periodic integrity pass). It precedes the attempt directory, so a refusal launches nothing. Without the field every check and message is today's, and the completion scope is unchanged; with it, the scope adds `; <B> review accepted at <E> carried over the <A> review of <E>..<H> by attestation <path>` after any rebase suffix.
- **Stop conditions, each with its own message:** a malformed field (`Invalid carried review`) or a curation kind (`Carried review is supported for code gates only`); A at neither frame head; a missing object; a carried tree mismatch; an empty or non-linear (merge) chain (`Carried review chain is empty or non-linear`); E outside the chain, including E = F and E = H (`Carried commit is not in the fix review's chain: <F>..<H>`); a report that does not name the full-SHA delta; an attestation reference or sha256 mismatch; an attestation key, value or path list that differs (`Carried review attestation mismatch: <key>`); B not bound to `(E, tree)`, including B at `REVIEWED` (`Wrong carried scope: <B>`, so an unused field refuses). There is no fallback.
- **Composition:** fix first, rebase last. Fix-then-rebase passes: A binds `accepted`, B binds E in `oldBase..accepted`, and the unchanged rebase proof carries the whole chain, E included, to `REVIEWED`. Rebase-then-fix refuses: with A at `REVIEWED` and E on the old base, E is outside `BASE..REVIEWED`, so `Carried commit is not in the fix review's chain` fires first (before `Unused rebase proof`); B then gets an ordinary delta review.
- **Trust:** Git objects, the report bytes and the attestation's keys and paths are verified at every authorization. The `statement`, and A's confirmation that the delta stays within its findings and touches nothing B judged, are recorded judgement, as with every review ("the parent supplies authentic observations"). The full gate suite remains authoritative for semantics.
- **Not supported:** curation (refused), pairs (`paired-gates.md` uses its own bindings) and rebase-then-fix (refused). A fix broader than the findings goes to both axes.

## Conditional LAND

Owner, 2026-11-04 (`$EP_ORCH/mvp-20261023/owner-decision-20261104-review-freeze-ci-conditional-land.md`): a review that answers "LAND once X is fixed" with a machine-checkable X needs no further review round once root has verified X. A code or curation gate whose `gate.json` carries `conditionalLand: {axes, commit, tree, paths, message, attestation: {path, sha256}}` accepts the reviews of `axes` at the reviewed commit E = `commit` together with the repaired head H.

- **Field:** exactly these keys. `axes` is a sorted, non-empty list of the kind's review axes (`standards`, `spec`; or `curation`). `commit`/`tree` are full SHAs. `paths` is the sorted, unique list of files the conditional named; `message` is `true` when it named the commit message. At least one repair is named.
- **Frame:** H = `REVIEWED` and the frame base F = `BASE`; with `rebaseProof`, H = `accepted` and F = `oldBase` (fix first, rebase last).
- **Rule:** `gate_core.conditional_proof(root, F, E, tree, H)` uses plumbing only. E's object exists, `E^{tree} == tree` and E is not H; `F..H` is non-empty and linear. Either E lies strictly inside it (`relation: "descendant"`: later commits make the repair) or E is an amend of H's tip (`relation: "amend"`: E's only parent is H's parent, as when a count or a curation prep commit's message is repaired in place). It returns `{base, commit, head, relation, paths, message}`: `paths` is the sorted `git diff-tree -r --no-renames --name-only -z E H`, and `message` is whether an amend changed the commit message (always `false` for a descendant, whose later commits carry their own messages).
- **Exactness:** `paths` must equal the named `paths`, and `message` the named `message`. A broader delta, a path outside the named set, a named path the repair left alone, an unnamed message change and a named message repair that is absent all refuse.
- **Reports:** each listed axis's report (its reference verified) names E's full SHA, and at least one contains the verdict "LAND once" (case-insensitive).
- **Attestation:** root writes one JSON file with exactly `{version: 1, kind: "conditional-land", axes, commit: E, head: H, relation, paths, message, check: {command, output, commit}, statement, attestedBy}`. `relation`, `paths` and `message` equal `conditional_proof`'s. `check` records root's mechanical check of X: the command, its output (both non-empty) and the commit it ran at, which is `REVIEWED`, the commit being gated (after a rebase, rerun it on the rebased head). `statement` (root's judgement that the repair is X and nothing more) and `attestedBy` are non-empty strings.
- **Where:** `authorization()` checks the field's shape, then, before the review loop, re-verifies the frame, `conditional_proof`, the reports and the attestation at every call (prepare, submit, collect, complete and each periodic integrity pass), and `gate-run.py` runs the same check in its mode prechecks. The listed axes must bind exactly `(E, tree)` (`Wrong conditional LAND scope: <axis>`); every other review check is unchanged, and an axis not listed binds `REVIEWED`/`TREE` (or `accepted`) as before. With a rebase proof whose accepted commit no review binds, the conditional LAND's repaired head uses it. Without the field every check and message is today's. With it, the completion scope adds `; <axes> review accepted at <E> with a conditional LAND, repaired to <H> (<paths and/or the commit message>) by attestation <path>`.
- **Stop conditions, each with its own message:** a malformed field (`Invalid conditional LAND`); a combination with `carriedReview` (`Conditional LAND does not combine with a carried review`); a missing object; a tree mismatch; E = H (`Conditional LAND needs a repair`); an empty or non-linear (merge) chain (`Conditional LAND chain is empty or non-linear`); E neither inside the chain nor an amend of its tip, including E = F, a side commit and an amended merge (`Conditional LAND commit is neither in the chain nor amended at its tip: <F>..<H>`); a path or message mismatch (`Conditional LAND path mismatch`, `Conditional LAND message mismatch`); a report that does not name E, or no "LAND once" verdict; a missing attestation file, a changed sha256, or an attestation key or value that differs (`Conditional LAND attestation mismatch: <key>`). There is no fallback.
- **Fail-open class:** what the gate cannot check is whether the named paths' content is X and nothing more, and whether the recorded check proves X. Root's attestation records that judgement and its check, as the single-axis attestation records root's. The named path set bounds the delta; the full gate suite stays authoritative for semantics.
- **Not supported:** pairs, `carriedReview` together with it (refused), rebase-then-fix (E on the old base outside `BASE..REVIEWED` refuses) and a repair that changes a commit before the tip in place (an amend deeper than the tip refuses).

## Light landing lane

Owner, 2026-11-01 (`$EP_ORCH/mvp-20261023/owner-decision-20261101-no-unneeded-full-gates.md`): "dont run full gates when it is provably not necessary". **Basis, owner 2026-11-01 (`$EP_ORCH/mvp-20261023/owner-decision-20261101-light-lane-bounded-risk.md`): bounded risk.** The lane establishes that a full gate is *very likely* unneeded, not a strict proof. Every later code slice still runs the full gate on a tree that includes the change, so a dependency the lane missed fails that next full gate, and triage points at it. A reviewed, mechanical rule decides, never a reviewer's judgement. A code gate whose `gate.json` carries `lane: {mode: "light", rule: "light-lane-v1", paths}` (exactly these keys) skips codegen, the pin, typecheck, lint, the full suite and the E2E preflight. Identity, review binding (with `rebaseProof` and `carriedReview` unchanged), the exact-tree squash, the bounded unit, `impl_prep` (rebase, `pnpm install --offline`, writer check), `check:artifacts`, the checked `land.sh`, collect and complete still run. Research: `$EP_ORCH/research/light-landing-lane.md`.

- **Rule** (`scripts/orchestration/light_lane.py`, `verify(root, base, commit)`): computed from Git objects only (`GIT_OPTIONAL_LOCKS=0`, no working-tree read).
  - **R1 Shape:** the delta `git diff-tree -r --no-renames --raw --no-abbrev -z BASE C` is not empty, and every entry is A or M with mode 100644 on each present side. Deletions, renames (a D), symlinks, executables and submodules refuse.
  - **R2 Allowlist (default deny):** `AGENTS.md`, `CLAUDE.md`, `docs/standards.md`, `.claude/settings.json`, `.gitignore`; `*.md` at any depth under `docs/agents/`, `docs/product/` and `.agents/skills/`; `.claude/agents/<name>.md` at depth one.
  - **R3 Census** (`needles`, `needle_table`, `minimal_literals`, `grep_lines`, `census`): for each changed path the needles are (1) the full path with no name character `[A-Za-z0-9_.-]` on either side (`/` is a boundary, so `$repo/docs/...` is a hit); (2) the basename quoted or after `/`, closed by a quote; for each ancestor directory, (3) the ancestor followed by `/` and `*`, a quote, `$`, whitespace or the end, (4) the ancestor quoted alone, (5) the ancestor as a `{a,b}` member, and (6) for an ancestor of two or more components, the bare ancestor not continued by a name character or `/` (added after the base census found `curate.sh`'s `templates=$repo/docs/agents/orchestration/templates`). Each needle contains a literal (the path, the basename or the ancestor). The literals are reduced to a minimal set (a literal is dropped when it contains a shorter kept one, since a line holding it also holds the shorter one), and one `git grep -n -P -I -z` over their escaped alternation at C, with pathspec `. ':!*.md' ':!*.mdx'`, selects the candidate lines (Markdown, MDX and binary files are not searched); each needle's regex then decides on the lines that contain its literal. Every hit `(file, needle)` must be in `REFERENCES`, the reviewed table in `light_lane.py`: one reason per entry, keyed by file and needle, never by line. A `*` entry admits every needle in that file; there are seven, each with its reason: the rule's own `light_lane.py` and `light-lane.test.py`, the reader guard `tests/light-lane-reader-guard.ts` and its test and the read lock's test `scripts/orchestration/lane-lock.test.sh` (all three pinned by R4), and the two frozen hash manifests `tests/fixtures/spells-53{5,6}/preserved.json` (209 needle hits each; tests only count their `rawCommitments`, `tests/catalog/preserved-manifest.ts`, #749). The other entries are dispatch tools the queue never runs, comments, exclusion lists and temporary-repository fixtures.

- **Light checks** (`light_checks`): a strict JSON parse of each changed `.json` (duplicate keys and `NaN`/`Infinity` rejected), and each relative Markdown link (`[text]` followed by a parenthesized target) on an added line of a changed `.md` (anchor stripped; `http:`, `https:`, `mailto:`, `#`, absolute, `$` and `<` targets skipped) must exist in C. Added lines are the new blob's lines that a line diff (`difflib`) of the old and new blobs inserts or replaces, numbered in the new blob; binary or non-UTF-8 Markdown fails. These are failures, not refusals: the full gate would accept the defect too, so the fix is a fix round.
- **The read lock (Vitest)**: every full gate that runs the suite locally runs every Vitest process of it under `lane-lock.sh`: `triage-failures.sh` wraps the full run and each rerun in its own disposable clean checkout (reruns of the feature head in `MAIN` are comparisons and stay unlocked; the owner's checkout is never chmodded). For exactly that process, every tracked regular file R2 allows except `.gitignore` (`light_lane.py lockable`) is mode 000, so any reader of one, in-process, a child process (`cat`, a spawned script) or another tool, gets EACCES and fails the full gate that adds it; lane-eligible files stay unread by the suite by construction. The list is taken and the checkout's own index refreshed before the lock, and no queue git command runs inside it; the locked process alone gets `core.trustctime=false` as `GIT_CONFIG_*` environment (never MAIN or the worker checkout, and never repository config, which a linked worktree shares), so git the suite runs compares stat data without re-hashing a file whose content and mtime are unchanged and only its ctime moved. The one such reader is `check:artifacts`, which `tests/catalog/launch-document.test.ts` runs; the light lane runs `check:artifacts` itself on every candidate, so that dependence on lane-file sizes is covered without the lock. The command runs in its own process group: when it exits, or on INT or TERM, the whole group gets TERM and, after a bounded grace (`LANE_LOCK_GRACE`, default 10 s), KILL, and the modes come back only once no process of the group is left; an unrestored mode, or a group that outlives KILL, fails the stage. Each run writes `lane-lock-<report>.json` beside its report (files, command, exit code, sha256 of the restored `<mode> <path>` lines); collection references them with the triage evidence. File contents never change, so the landed tree is the tested tree, and identity checks run on the candidate worktree, which is never locked. The in-process reader guard (`vitest.setup.ts`, `tests/light-lane-reader-guard.ts`, a Vite plugin in `vitest.config.ts`) stays as the fast, explicit diagnostic for in-process reads; R3 still covers literal references outside the suite.

- **Mechanically guaranteed:**
  - the allowlist (R2) and the shape (R1): no code, test, data, deletion, rename, symlink or executable lands through the lane, and no config except the two R2 names: `.claude/settings.json` (read only by Claude Code; strictly parsed as JSON by the light checks) and `.gitignore` (bounded by R5);
  - the pinned configs and implementations (R4): the typecheck, lint, Vitest and e2e configs, the `catalog:pin` script and its direct imports, the codegen entry, the content-independent e2e readers, the reader guard and the read lock; changing any of them refuses the lane until a reviewed re-pin;
  - the census (R3): no non-Markdown file names a changed path outside the reviewed table;
  - R5: `.gitignore` only gains blank lines, comments or literal `.claude/` paths;
  - the in-process guard: a Vitest test that reads a lane file through `fs` or a Vite load fails;
  - the Vitest read lock: in every full gate whose suite runs locally through `triage-failures.sh`, a suite process (or its child) that opens a locked lane file fails, and on every way out (exit, HUP, INT, QUIT, TERM) the lock stops its whole process group before restoring, so no process of the group runs with restored modes; a signal that arrives while the command is being launched, before its group id is recorded, is held and acted on right after, and nothing is restored in between. **Exception, a lock that dies before restoring:**
    - **When:** the lock process is killed by SIGKILL (for example the OOM killer, or a unit stopped without a grace period), or exits while the command is being launched and its group id is not yet recorded.
    - **What is left:** the lane files stay at mode 000, and the command (with any descendants) may still run.
    - **Scope:** only the gate's own disposable triage checkout (`../ep-gate-<worktree>-*`), which is the only checkout the lock is ever given; never `MAIN` or a worker checkout.
    - **Effect:** the suite run was cut short, so the gate has already failed and nothing lands.
    - **Record:** `lane-lock-<report>.json.active` beside the report in the triage evidence. It holds the checkout, every locked file with its original mode, the lock id (also in the command's environment as `LANE_LOCK_ID`) and, once known, the command's process group.
    - **Recovery** (the gate operator's job, as part of diagnosing the failed attempt before any fresh one; collection's `observedCleanup` check already fails on a leftover `ep-gate-*` checkout):
      1. Find leftovers by the record's group (`kill -0 -- -<group>`) or, without one, by its lock id (`grep -lz LANE_LOCK_ID=<lockId> /proc/[0-9]*/environ`).
      2. Kill that process group, or those processes (`kill -TERM`, then `kill -KILL`), and wait until none is left.
      3. Either restore each file's mode from the record, or simply delete the disposable checkout: `chmod -R u+rw <checkout>`, then `git worktree remove --force` or `rm -rf`. `triage-failures.sh`'s own exit cleanup already removes it when only the lock died. A gate with `remoteChecks` in `replace` mode skips local triage, so its suite runs without the lock (`compare` mode still runs the local suite under it);
  - the default path: without `lane`, the operator argv, the queue stages and logs, the result fields and the completion scope are today's; the only addition is the Vitest lock window and its records.
- **Not guaranteed (bounded risk, caught by the next full gate):**
  - adversarial or unusual readers: a test or script that reads a lane file's content through Git objects (`git show HEAD:<file>`), through `.gitignore` (readable by any process; R5 bounds only its ignore semantics), through a process outside the lock's group, or in a skipped-stage implementation beyond the pinned entry points (for example codegen's `scripts/local-convex/generate.ts`);
  - remote suites: a `remoteChecks` gate in `replace` mode takes its suite from the remote manifest and runs no local triage, so the lock does not apply to it; the remote protocol does not require the lock;
  - metadata: mode 000 leaves size, existence and directory listings observable, so a test asserting a lane file's exact size or presence is not caught. `check:artifacts`, which the lane runs, enforces the only size limits a lane file is checked against (the unbudgeted limits: a new file of at most 1,000,000 bytes, at most 5,000,000 bytes of growth and 50,000 added lines); a test's own size assertion is not one of them.
- **CLI:** `python3 -B scripts/orchestration/light_lane.py check ROOT BASE COMMIT` writes nothing and prints one JSON object: `{verdict: "PASS", rule, base, commit, tree, paths, references, pins, lane}` (exit 0), whose `lane` goes into `gate.json` as is, or `{verdict: "FAIL", reason}` (exit 1 for a refusal, 2 for a light-check failure). `verify WT BASE COMMIT EVIDENCE_DIR` runs the same checks for `cur-land.sh`, prints `light ...` lines and, on a pass only, creates `EVIDENCE_DIR/light-verification.json` (the result plus `passed: true`); an existing `EVIDENCE_DIR` refuses.
- **Where:** `authorization()` checks the field's shape, the rule, the code kind and the absence of `remoteChecks`, then re-proves the rule for `REVIEWED` on `BASE` at every call (prepare, submit, collect, complete and each periodic integrity pass); its tree must be `TREE` and its path list `lane.paths`. It precedes the attempt directory, so a refusal launches nothing. The operator passes `LAND_LANE=light LAND_LIGHT_EVIDENCE=<attempt>/light-evidence` after any remote argv. `land-queue.sh` refuses another value, `--pair`, more than one item, a curation item and `LAND_REMOTE_CHECKS`; `cur-land.sh` runs `light_lane.py verify` after the artifacts stage (`light.log`), then the final identity check and `land.sh`. Collection replaces `originalSuite` with `lightLane` (the record binds the rule, `BASE`, the squashed candidate, `TREE` and `lane.paths`, and the rule is re-proved for the candidate), references `light-evidence/*.json` and records `suite: {source: "none", lane: "light", rule}`. The completion scope becomes `Authorized light landing lane (every changed path is outside the full queue's pinned inputs under rule light-lane-v1, bounded risk, owner 2026-11-01; codegen, pin, typecheck, lint, the full suite and the e2e preflight not run) and checked completion only; no Cloud/GitHub/promotion qualification`, followed by any rebase and carry suffixes.
- **Stop conditions, each with its own message:** `Invalid lane: exactly mode "light", rule and paths`; `Light lane rule mismatch: <rule>`; `Light lane is supported for code gates only`; `Light lane does not combine with remote checks`; `Light lane refused: empty delta`, `<path> <status> mode <old>-><new>`, `<path> is outside light-lane-v1`, `<path> is referenced by <file>:<line> (<needle>)`, `reader pin changed: <name>`, `.gitignore removes or changes lines`, `.gitignore line is not a literal .claude/ path: <line>`; `Light lane path list mismatch`; in the queue, `unknown lane '<x>'`, `light lane does not apply to pairs`, `light lane binds one item`, `light lane is for code items only`, `light lane does not combine with remote checks` and `light lane refused (see <log>); not landing`. A refusal never falls through to the full stages: the operator writes a config without `lane` and runs a fresh full gate.
- **Trust:** Git objects at every authorization and again in the queue and at collection, under the bounded-risk basis above: what is not mechanically guaranteed is listed, and a missed dependency surfaces at the next full gate. Semantic interaction between code and docs does not arise, because a light candidate contains no code.
- **Not supported:** curation, pairs, `remoteChecks` and more than one item (refused); `README.md`, `GLOSSARY.md` and non-Markdown files under `.agents/skills/` (outside the allowlist until a reviewed rule bump).
- **Re-pin:** a `reader pin changed` refusal or a new census hit means the full gate now. Updating the rule (pins, allowlist or `REFERENCES`) is its own reviewed workflow slice, which must state why the changed reader still ignores the allowlist.
