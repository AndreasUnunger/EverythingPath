# Validation and gate operator: full contracts

The base text of the validation-evidence and gate-operator sections of [operations](../orchestration/operations.md), kept verbatim. Operations carries the summary an operator acts on; this file is the complete contract, as `scripts/orchestration/validation.py`, `gate_core.py`, `gate_operator.py` and `gate_monitor.py` implement it. Read it when a gate pauses, refuses or needs recovery, when deciding whether a receipt can be reused, or before changing those scripts.

## Frozen evidence and adoption

Use repository tooling for new operations. Active external frozen bundles, old failed inputs/helpers/reports and authentic review/admission evidence remain immutable history. Changing repository scripts does not qualify them or amend a frozen operation. The parent owns adoption and live-state migration after review and qualification.

## Validation evidence

Before coding, select one impact-based plan. Name why each check is necessary and the configuration/runtime inputs it reads. Package scripts are authoritative for commands and heaps: `pnpm -s typecheck`, `pnpm -s lint` (including its 8192-MB old-space and 256-MB semi-space ESLint options), `pnpm test <paths>`, writer/artifact checks, and local codegen/browser checks when affected. Existing orchestration shell tests may be selected by their exact `scripts/orchestration/*.test.sh` entry path; the recorder executes no shell expressions or callback strings. Keep the original full queue mandatory. Shared-code regressions remain blocking outside a selected content slice.

Resolve actual configuration paths in this checkout; the example is a shape, not a claim that those paths exist. Include backend image/configuration or browser runtime input files when relevant. Keep private environment files out of inputs. Run the recorder directly; it caps its child command. Record and verify serially with the same explicit public environment:

The public recorder and full reuse boundary reject every `CAPPED_*` and `ADMISSION_*` override and every `BOUNDED_*` override except the canonical `BOUNDED_WORKERS=2` and `BOUNDED_CPU=600%` (or their equivalent unset defaults). In particular, leave `CAPPED_KIND` unset: the actual capped wrapper classifies the planned command. Do not wrap the recorder itself in `capped.sh` or supply a reservation/library/state override. Its own capped child generates the required internal reservation safely; bound-only periodic proof verifies immutable records without treating that generated child state as public reuse authority. Current receipts explicitly bind the canonical effective wrapper-control contract; receipts recorded under the earlier 1-worker / 400% contract need fresh recording for reuse. Older receipts missing that contract remain historical evidence and need fresh recording for reuse; their absent overrides cannot be proved retrospectively.

`run` resolves required tools, proves their resolution under an explicit PATH containing their selected directories and standard utilities, and invokes the planned command through shared `capped.sh` with that PATH; the result records completion, actual exit, elapsed time, tested commit/tree, lockfile/installed-lock and declared inputs, tool bytes/versions, public environment, plan and log reference. Local codegen/browser receipts also bind the pinned backend source and actual Docker image; full browser runs hash installed browser executables. Each result directory is create-only, including failures. Version-2 receipts bind the canonical directory, original nonce-bearing attempt, exact attempted context, actual launched PID/argv/completion and output hash. Verification requires that original attempt and execution record; copied, missing, corrupted or mismatched records fail. These locally writable records detect corruption and unsupported pass claims; they are not cryptographic attestation against an actor rewriting the entire evidence set. Earlier uncommitted author logs remain author evidence and cannot be promoted retrospectively to reusable receipts. `verify` reports a reason when content, dependencies, configuration, tooling, runtime inputs or environment change. A SHA change alone is insufficient: reuse checks both trees and an empty content diff. Unused ephemeral session PATH entries do not invalidate reuse; changed effective tool paths/bytes, execution options and dependencies do. Full boundary verification shares one tool/context capture across the applicable receipts. Tree-identical squash does not repeat author checks. Changes that invalidate a check get a new evidence directory; retain the failed/obsolete result and reference it with the reason in the report.

Existing specialized curation prep receipts remain authoritative for light/full catalog preparation, affected older batches, post-rebase counts, branch/path and full-plan escalation. Their exact-context rules still apply. Author receipts supplement them; they do not relax prep or promotion validation. A canonical landing gate runs its complete checks and original suite independently of author-check reuse; only a configured, verified [remote heavy-check manifest](gate-modes.md#remote-heavy-checks) (owner, 2026-10-30) replaces its local typecheck, lint and full suite.

## Gate operator

`scripts/orchestration/gate-operator.py` owns the focused single-item prepare/freeze/submit/observe/collect/complete sequence. It runs the existing `land-queue.sh` in a bounded gate unit; the queue owns rebasing, specialized curation prep, full validation and checked `land.sh`. It is neither a scheduler nor a replacement receipt authority. Paired operations continue through the repository’s [paired procedure](../orchestration/paired-gates.md), with its retained assembly, staged reviews and split diagnosis. Unflagged queue lists remain serial.

Each review declares `commit`, `tree`, `taskId`, `runId`, actual `target: {providerInstanceId, model, options}`, `task: {path, sha256}`, `report: {path, sha256}`, `disposition: "accepted"` and `unresolved: []`. A review's `commit`/`tree` are `REVIEWED`/`TREE`; when `rebaseProof` is present, a review may instead bind its `accepted`/`acceptedTree`, and at least one must, unless `conditionalLand` uses the proof for its repaired head. When `carriedReview` is present, its axis binds exactly the carried `commit`/`tree` instead, and the other axis's fix review binds `REVIEWED`/`TREE` (or `accepted`/`acceptedTree` with a proof). When `conditionalLand` is present (it never combines with `carriedReview`), its listed axes bind exactly its `commit`/`tree`, possibly every axis, and the repair to `REVIEWED` (or `accepted`) must lie inside the scope their reports' `LAND once fixed:` lines permit. The bindings and refusals are in [gate modes](gate-modes.md#conditional-land). Task metadata must show the original run terminal/completed with no pending children and exact model/options. The parent supplies authentic observations; files do not attest authorship. A correction review’s report carries prior acceptance and the delta/closure disposition. Record promotion still requires [T3 capture evidence](../orchestration/t3-reviews.md) and explicit `catalog-record-review.ts --verify`.

For new preparation, use `preparation: {mode: "squash", archive: "refs/archive/RUN/reviewed", message: {path, sha256}}`. Preparation preserves the reviewed chain under the archive, creates one exact-tree commit with the frozen base as sole parent, compares the complete content and records `mapping.json`. It never soft-resets the owner checkout. Curation must already be one specialized-prepared, reviewed commit; preparation preserves that commit and its exact-context prep receipt rather than re-squashing it. Curation must complete specialized prep and review before submission; a mismatching prep receipt stops for fresh prep/review rather than silently accepting a new amended scope.

For an already prepared candidate, use `preparation: {mode: "prepared", archive: "refs/archive/RUN/reviewed", candidate: "FULL_SHA", mapping: {path, sha256}}`. The mapping must bind `BASE`, `REVIEWED`, `TREE`, `WT`, `BR`, `ARCHIVE` and `SQUASHED`. Existing historical mapping formats are consumed without modification; exact Git tree, parent, diff, registered checkout and archive are rechecked. This creates fresh attempt evidence without re-squashing or overwriting old attempts.

## Control and cancellation

Control shape: `{state: "active", taskId: "ACTUAL_TASK", runId: "ACTUAL_RUN", reviewed: "FULL_SHA", tree: "FULL_TREE", base: "FULL_BASE"}`. Set `state: "stopped"` to stop; `finish-current` plus `phase` restricts continuation to that phase. Finishing observation includes required terminal evidence collection; successful terminal evidence remains resumable, and completion waits for active continuing authority. The immutable configuration authorizes the selected sequence once. Submission requires `observe`, `collect` and `checked-land` together, since a successful canonical queue lands within the same invocation. A `finish-current` control restricted to submission refuses before launch because it cannot authorize continuing observation. A run without submission authority can prepare only. A pause reports the actual blocked phase (`prepare`, `submit` or later); it never implies completion is next before submission. After a claim, any refused control/validation handoff or observer failure cancels only the invocation proven by the captured return and original claim, without re-entering the failed validation path. `cancel` bypasses the forward-operation sequencing lock so an active or failed caller cannot block a safety stop. `cancel` and terminal `collect` remain available under stopped controls to preserve failed evidence. An otherwise successful terminal invocation defers collection with `nextPhase: collect` when the caller is stopped, finishing another phase, or has a mismatched frozen public environment (including `LC_ALL`). This writes neither a failed result nor a stop marker. Re-enter from the recorded operator environment and continuing authority; a collector mismatch is not gate-failure evidence. Actual receipt failure, observer/stop markers, identity tampering and resource failures still block completion. A genuine failed/stopped/resource invocation cannot complete or resubmit. Cancellation after a canonical terminal receipt does not add a retrospective stop marker. Repeated run/collect/complete calls verify and return the existing immutable result/completion without rewriting it or submitting again.

## Runtime entry, chaining and failures

The small MAIN bootstrap imports no operator modules before selecting and verifying the attempt’s complete immutable runtime. Use the retained `$GATE_ENTRY` for every later `resume`, `collect`, `cancel`, `complete` or repeated `run`, including after MAIN deletes or replaces its bootstrap/modules. `runtime` selects the handle only after successful preparation. Initial `run` prepares and re-executes that frozen entry automatically; callers who need later re-entry should retain its known absolute `attempt/operator-runtime/gate-operator.py` path. Use `run` to chain a fresh authorized attempt; `resume` reuses a completed preparation and the same saved invocation. There is no permission handshake between successful phases already in `phases`. A create-only claim precedes the only submission. Lost/ambiguous returns, failures, identity drift, unexpected controls or resource violations stop the chain. Inspect the existing canonical invocation, never resubmit it. A safe setup omission found before any child launch may be corrected in-task with evidence that no claim/child exists. Diagnosed implementation or test-fixture failures may be fixed and rerun at the affected seam in the same task within scope, retaining the red result. They do not require a parent handoff merely because a fixture models an instrumentation error. Live gate failures, resource violations and observer safety events retain their actual failed receipts and require diagnosis before a fresh attempt; those stop conditions and caps remain unchanged. Partial launched attempts remain historical.

## Preparation and observation internals

Preparation verifies review/record receipts and history, freezes executed operator/monitor bytes and base Git-object provenance separately from the reviewed queue snapshot, pins bounded admission/outcome callbacks to those frozen base bytes through their existing wrapper options and explicitly binds `BOUNDED_STATE_DIR` to the shared ORCH for outer classification, inner reservation, payload and terminal release/receipt, verifying the actual ledger before submission, checks executable entries separately from readable sourced libraries and declaration imports, and freezes transitive runtime/config dependencies. The monitor runs from the frozen operator runtime. Continuous foreground observations and one supervised integrity child remain, with a new complete terminal pass required. Each periodic pass performs preparation/identity, authorization, control and snapshot proof once. MAIN identity reads share a lock with the canonical checked fast-forward, covering Git’s worktree/index/ref transition without accepting a partial checkout. Lock identity is frozen and the existing ten-second observation-loss boundary stays binding. Expected base-to-candidate script replacement/deletion does not invalidate immutable base/snapshot provenance; dirty, wrong-tree or external tampering still fails. Historical evidence indexes are verified at prepare/collect and referenced once; their thousands of file entries do not enter each live poll.

## Submission and collection

Submission retains the canonical bounded invocation. Collection references canonical receipts/logs and original-suite JSON; it does not recopy full snapshots/reports. A failed receipt, stopped monitor, missing resource observation, non-green original suite or incomplete checked landing cannot finalize. Canonical triage diagnostics and the existing local-preflight retry remain; LOAD/NEW verdicts never authorize landing. Existing host/storage/Docker guards, memory/CPU caps, admission and locks stay binding. Every new runtime/script version needs appropriate qualification before live adoption; synthetic fixtures prove contracts only. Run the runner/receipt/transition fixtures with `pnpm -s test:workflow`; shell queue/prep/pair tests remain separate relevant checks.
